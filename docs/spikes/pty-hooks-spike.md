Status: sets A and B implemented and passed on macOS; sets B and C ran once on native Windows (facts in §3). The Windows follow-up run (§1 D, §4.10, §5 phase 3) is implemented and type-checked for Windows, not yet run there. Canonical constraints: `AGENTS.md`, `docs/architecture.md` §4 (PTY Seam), §5 (External Quirks), §6 (Verification). Prior-art survey: `docs/prior-art.md`.

The spike answers five questions with evidence. It does not build the daemon; nothing here is a public contract except where it pre-validates the irreversible core (architecture §2: hook emitter, Bearer + Host auth, Job Object / pgid cleanup).

Versions observed while writing this design (2026-11-21, macOS arm64): `claude` 2.1.322, `codex-cli` 0.170.0, `rustc`/`cargo` 1.96.0, `portable-pty` 0.8.1 (latest stable is 0.9.0; we stay on `=0.8.1`), `alacritty_terminal` 0.26.0 (published 2026-04-06, latest on crates.io). ## 0. Sequencing Constraint (owner decision, binding)

- **Order: macOS first, Windows second.** All real-CLI verification is planned for this macOS session. Full Windows support and ConPTY tuning happen later on the owner's native Windows machine.
- **Do not over-invest in speculative Windows code on macOS.** Windows code in this spike is the minimum needed to compile, pass FakeCli scenarios, and run the go/no-go probes in set C and the follow-up probes in §1 D. No tuning, no alternative mechanisms beyond what a probe needs.
- **Do not defer architectural risk.** Set C exists so that anything forcing a major architecture or technology change on Windows (ConPTY unusable, no tree kill, no reattach path, unavoidable console windows) is found by one owner run of the same binary, before more macOS work builds on it.
- **Cross-platform hygiene from day one:** the control path is localhost HTTP only (no Unix domain sockets, no signals as IPC); the hook emitter is one Rust binary; every OS-specific PTY/process call sits behind one boundary module (`src/os/{unix,windows}.rs` under `cfg`), and the rest of the code is OS-agnostic.

Owner approvals in force: real-CLI paste API usage on both OSes; rewriting the real `~/.codex/hooks.json` only if session-flag hooks cannot persist trust (§4.3). Codex is measured both with `--no-daemon` (containment baseline) and in default mode.

## 1. Purpose Layer: Acceptance Criteria

Three sets. "Source" is the requirement origin; every AC is verified against the real thing (real PTY / ConPTY, real CLIs where named, real process tables). **O** marks an owner action or judgment. Each case outcome is `pass`, `platform_fail` (only with positive evidence of what the CLI or OS did: bytes compared and differing, a successful enumeration showing an escapee, positive death evidence), `harness_fail` (setup, relay, gate, writer, lookup, enumeration, or observer failure), `missing` (no result, e.g. a hook that never arrived), or `not_exercised`. Completeness is checked first: a scenario is `inconclusive` when any required case is `missing`, `harness_fail`, or `not_exercised`, even if another case failed; otherwise `pass` when all passed, else `fail`. A skipped real check, an expected session witness that never attested, ambiguous attribution, or an uncalibrated observer is never `pass`. Codex findings are reported as "observed on codex `<ver>`, source `<x>`, mode `<no-daemon|default>`".

### C. Windows real-device go/no-go probes (owner runs `chs win-probe all`)

Each probe answers "is there an architectural blocker?", not "is Windows support finished?". A **blocker** forces a change to the architecture or technology choice (portable-pty / ConPTY, Job Objects, daemon-owned PTY, Rust emitter) and stops further macOS-only investment on that seam. A **tuning issue** goes to the Windows backlog. Probes are independent; a failure in one does not skip the others. The harness does not classify: each probe reports `go` (every required case passed), `fail_observed` (complete, with at least one `platform_fail`), or `inconclusive` (completeness first, as above). The orchestrator reads the raw evidence behind every probe verdict, `go` included, before classifying: `go` stands only if that evidence shows each required case actually exercised, residual races in which only a harness event could be misattributed are checks the orchestrator performs on that evidence, and each `fail_observed` is classified against the two columns below. Windows-only code gets no further read-only review rounds; the owner's real run is the next evidence.

portable-pty 0.8.1 (source, `~/.cargo/registry/src/index.crates.io-*/portable-pty-0.8.1/src/`):

- Unix spawn calls `setsid()` in `pre_exec` (`unix.rs:220`), then `TIOCSCTTY` (`unix.rs:229-237`), after resetting SIGCHLD/HUP/INT/QUIT/TERM/ALRM to default (`unix.rs:208-217`). Child pid = pgid = sid. `killpg` targets that process group only; a descendant can move to another group (`setpgid`) while staying in the session, or leave the session (`setsid`).
- `Child::kill` on Unix sends SIGHUP to the single pid, polls 5×50 ms, then SIGKILL on that pid only (`lib.rs:330-353`); the cloned killer sends only SIGHUP (`lib.rs:314-318`). Not a tree kill.
- Windows kill is `TerminateProcess` on the direct child only (`win/mod.rs:41-43`, `:71-72`). No Job Object anywhere in the crate. `WinChildKiller::kill` inverts the result: it returns `Err` when `TerminateProcess` succeeds and `Ok` when it fails (`win/mod.rs:70-79`), so the harness's `child_killer.kill=true` step on Windows means that call failed (expected after `TerminateJobObject` already ended the process).
- Unix `pre_exec` calls `close_random_fds()` (`unix.rs:239`), which runs `read_dir("/dev/fd")` and grows a `Vec` (`unix.rs:118-143`): allocation between `fork` and `exec`, not async-signal-safe.
- `CreatePseudoConsole` flags are `RESIZE_QUIRK | WIN32_INPUT_MODE` (`win/psuedocon.rs:86`); no `INHERIT_CURSOR`. `CreateProcessW` uses `EXTENDED_STARTUPINFO_PRESENT | CREATE_UNICODE_ENVIRONMENT`, a one-entry attribute list, and drops the thread handle (`win/psuedocon.rs:124-147`, `:165`): no `CREATE_SUSPENDED` and no job list through the crate.
- A `conpty.dll` on the DLL search path is preferred over kernel32 (`win/psuedocon.rs:51-58`); which provider actually loaded is recorded via `GetModuleHandleW("conpty.dll")` + `GetModuleFileNameW`, not by checking for a sibling file.
- `ClosePseudoConsole` runs on drop (`win/psuedocon.rs:72-75`); the child exposes `as_raw_handle()` (`win/mod.rs:118`) for `AssignProcessToJobObject`.
- Dropping the Unix writer writes `\n` + VEOF to the PTY (`unix.rs:350-361`).
- Windows lookup walks `PATHEXT` (`cmdbuilder.rs:532-548`) and may pick `codex.cmd`, which `CreateProcessW` cannot run directly; real probes therefore take pinned native binaries.

### 4.3 Hook injection, receiver, emitter

Fixed artifacts: emitter at `R/bin/chs-hook-emit`, under an owner-private root (`~/.chs`, mode 0700, on macOS); on Unix `install-emitter` checks ownership and write permissions from the spike root down and refuses any group- or world-writable directory there (Windows `C:/chs/bin/chs-hook-emit.exe`: forward slashes for Git Bash, no spaces so cmd/PowerShell/bash parse it unquoted). Command string: `<abs emitter> claude` or `<abs emitter> codex`; the event comes from the payload's `hook_event_name`.

Per-launch environment on the `CommandBuilder`. Before setting it, the harness removes inherited agent identity variables: `CLAUDECODE`, every `CLAUDE_CODE_*`, `CODEX_THREAD_ID`, `CODEX_SESSION_ID`, other `CODEX_*` session variables, and any inherited `CHALDEA_*` (the harness may itself run inside Claude Code).

Codex (production must use the real `CODEX_HOME`, so that is what is measured; no disposable profile, which would need the auth credential copied):

- Trust keys are found structurally (F-3b). Each key is split from the right into `<source>:<event>:<group>:<index>` (the source may itself contain a drive colon, as in `C:\…`); a key is under test when its source path's last two components are `<session-flags>` and `config.toml` (either separator), its event is `session_start`, and its group and handler indices are non-negative decimal integers. Receiver: std `TcpListener` on `127.0.0.1:0`, one request per connection (`Connection: close`), thread per connection (max 16; a connection past the limit gets its 503 written and its write side half-closed on the accept thread, then the drain below runs on its own thread, at most 4 at a time, beyond which the connection is closed right after its response and recorded as `drain_limit`; each gets its own record, and stopping the receiver waits for these drains). Each connection gets an absolute 5 s request deadline; every read recomputes its timeout from `deadline - now`, and the response, including a 408 sent because that deadline passed, gets its own 500 ms write budget after the decision, and the drain below has its own deadline; the whole connection is capped by an absolute bound of 7 s from accept (5 s request + 0.5 s response + at most 1.5 s drain), which every step's timeout is clipped to; the wait for the launched CLI's pid and the fixture store get the remaining time, and a hook or witness request past its deadline is answered 408 without publishing (checked again under the state lock). The head is read up to its `\r\n\r\n` boundary (at most 8 KiB; no body byte is consumed before the checks) and parsed with `httparse` (32-header array); then, before any body byte: method/path `POST /hook` or `POST /witness` (plus `/probe/*` only while C-4 or C-5 runs; `GET /probe/screen` is bodyless and needs no `Content-Length`) else 405/404; exactly one `Host`, equal to `127.0.0.1:<port>` or `localhost:<port>`, else 421; exactly one `Authorization`, Bearer compared with `subtle::ConstantTimeEq`, else 401; any `Transfer-Encoding` → 400; exactly one `Content-Length` ≤ 4 MiB on POST else 411/413. Accepted bodies are stored byte-for-byte as `fixtures/<agent>/<cli-version>/<launch-id>/<Event>-<seq>.json`, where `<launch-id>` is unique per launch, `<Event>` is a known event name from the parsed payload or `unknown`, and `<seq>` is a report-wide counter; `.meta.json` holds only allowlisted fields (receive time, run id, thread id, agent, emitter version, emitter ancestry). Rejections are counted, never stored, and never mark readiness. After a rejection response is written, the receiver half-closes (`shutdown(Write)`), then reads and discards unread request bytes until the peer closes, the drain deadline (1 s after the response, clipped to the connection bound) passes, or min(declared `Content-Length`, 4 MiB) + 64 KiB bytes have been read (4 MiB + 64 KiB when no valid length was declared), and only then closes; discarded bytes are never parsed, stored, or used for readiness. Each request's decided status, response bytes written and write result, drained bytes and the reason the drain stopped, and timing are logged in the receiver summary (`connections`), so B-8 correlates decided, written, and client-observed status per request. B-8's ordering cases send the head and withhold the body until the response has been read, which shows the decision came before any body byte; one extra case (`reject_with_body_sent`) sends the body up front to exercise the drain.

Binding: Claude events bind by the predetermined `--session-id`. For Codex, the first `SessionStart` whose `X-Chaldea-Thread-Id` matches the launch and whose emitter's nearest CLI ancestor (Codex or FakeCli process in the chain) is our launched CLI pid binds that launch's `session_id`; a nested CLI inheriting the env fails this test. Every other event is kept as `raw_unknown` (`foreign_session`); unparseable JSON as `raw_unknown`. More than one candidate = `inconclusive`: ambiguity revokes the launch's writer gate for good (bumping its generation, so a queued paste is dropped before its first byte), and launch verdicts are taken from the receiver's final summary after it has stopped and drained. Witnesses (`POST /witness`) are liveness assertions only and never add a pid to the kill set (§4.6); the survivor rule applies to expected session witnesses, and the `unrelated` fixture is a negative control whose survival passes.

Emitter (`chs-hook-emit`): if URL or token is missing, or the URL is not exactly `http://127.0.0.1:<port>/hook` or `http://localhost:<port>/hook`, exit 0 at once without reading stdin. Otherwise read stdin up to 4 MiB + 1; if over, log and exit 0 without POST. POST the raw bytes with `Authorization: Bearer`, `Host`, `X-Chaldea-Thread-Id`, `X-Chaldea-Agent`, `X-Chaldea-Emitter-Version`, and `X-Chaldea-Emitter-Ancestry` (own pid, then up to 8 ancestors as pid + name); connect 1 s, total 3 s including the stdin read. Always exit 0; never write stdout (Claude injects hook stdout into context; exit 2 would block the prompt). Windows: console-subsystem binary that allocates no console; a `windows_subsystem = "windows"` variant is built for C-5's mitigation re-run of Claude and FakeCli launches. Codex launches never use it: Codex keys hook trust by source, event, and position and keeps one trusted hash per key (codex-rs 0.169.0 `hooks/src/lib.rs`, `hooks/src/engine/discovery.rs`), so trusting the GUI emitter's command at the same position would turn the console command's trust into `Modified`.

### 4.4 PTY I/O, input gating, paste, VT

- One reader thread drains PTY output continuously into `pty-output.bin` and the `vte` processor feeding `Term`. One writer thread owns the PTY writer and a channel; VT replies (`PtyWrite`, `ColorRequest` with fixed fg `#d0d0d0` / bg `#1e1e1e`, `TextAreaSizeRequest` with 8×16 px cells) share that channel so they stay ordered with input. `query_log` records each query, reply content, latency, and whether the harness wrote the reply.
- Input gating: automated paste is sent only after a bound SessionStart and while `TermMode::BRACKETED_PASTE` is set. The bound SessionStart is the readiness signal; DECSET 2004 alone is not (Codex sets it while a hook-review dialog is up, §3). For Codex the positional first prompt is turn 1, so A-6 waits for its `Stop` before the first paste and counts pasted turns after it. This reads a terminal mode flag the app set, not screen text, and only gates input; it never infers thread state. If the mode is never set, the paste stays `unconfirmed`, is reported as `readiness_gate_failed`, and is not retried. `write_key` is not gated: it is the emergency keypad path for startup prompts, used only by an attending owner (C-2) or a probe client (C-4); A-7 sends no input at all.
- Paste: validate (reject ESC and C0 other than TAB/CR/LF; zero bytes written on reject); map line endings per `--paste-newline` (LF and CRLF in the payload both map to the chosen form); write `ESC[200~` + payload + `ESC[201~`; after the write completes, wait `--enter-delay-ms` (300 ms), then send `CR` as a separate write. The delay is a tested setting, not proof that the app consumed the paste. `--chunk N` splits the paste into writes of about N bytes: a cut that would fall inside an escape sequence (from ESC through its final byte, including `ESC[200~` / `ESC[201~`) moves to the sequence's end, while cuts inside multi-byte UTF-8 characters stay (conhost drops a split escape prefix, §3; split UTF-8 is coverage we keep). Oracles: FakeCli compares wire bytes against the mode's mapping; real `UserPromptSubmit` compares logical content (both sides LF-normalized), all other bytes exact, except for known CLI input transforms, each checked explicitly: TAB expanded to 4 spaces (`tab_expand`), NFC composition (`nfc`, `unicode-normalization` pinned exact), and Claude's large-paste wrapper `\n\n<pasted_content id="ID">\n…\n</pasted_content id="ID">\n` stripped by that exact pattern (`paste_wrapper`). A prompt equal after the smallest such set is `pass` with `cli_transform` in its evidence; only a difference none of them explains is `platform_fail`. C-1's real cases use the same oracle.
- Corpus (`out/corpus.json`): ASCII; `日本語の入力テスト、句読点。「括弧」`; `ｶﾀｶﾅ`; astral `𠮷野家`; `😀`, `👨‍👩‍👧‍👦`, `🇯🇵`, `❤️`; decomposed `か\u{3099}`, `e\u{301}`; multi-line CJK with LF and with CRLF; 4 KiB+1 and 64 KiB mixes (64 KiB FakeCli only; real CLIs ≤ 8 KiB). The required subset for C-1 is the Japanese, astral, and decomposed entries plus one multiline Japanese entry.
- Input encoding is an adapter capability, `input_encoding(agent, os)` in `paste.rs`, chosen from the OS name at runtime (no `cfg`): `win_keys` for Codex on Windows, `bracketed_paste` for everything else. DECSET 2004 never selects it. `--input-encoding` overrides it for experiments.
- `win_keys` (Codex on Windows, F-1): validate as for paste (zero bytes on reject). Lossy input is checked next (F-1d): leading or trailing whitespace Codex would trim (Unicode whitespace, so U+3000 and a trailing LF count) and any TAB make the encoder report `lossy_input` with the reason and write nothing (state `rejected`), unless `--allow-lossy trim` / `--allow-lossy tab` accepts it; an accepted TAB is sent as a literal TAB inside the same write as the text around it, because Codex inserts Tab as text only inside a burst or within 8 ms of the last character (§3), and is otherwise its queue key. Composition works on extended grapheme clusters (`unicode-segmentation`): a cluster is NFC-composed when it holds any combining or extending character (canonical combining class > 0, or general category Mn, Mc, or Me, so U+09C7 U+09BE becomes U+09CB although U+09BE has class 0); every other cluster is sent unchanged. A CJK compatibility ideograph (U+F900–U+FAFF, U+2F800–U+2FA1F) is kept as it is even inside a composed cluster: only the characters after it are normalized, so U+FA19 U+0301 keeps U+FA19 (whole-prompt NFC would turn U+FA19 into U+795E). A sequence with no precomposed form stays as it is (F-1e records what arrives). Then map CRLF, CR, and LF to one newline; prefix one space and append one space (Codex trims both on submit, §3; this disarms `/`, `!`, `?` at the start and an `@` popup at the end); write the text as one write per line, and each newline as its own single write of the newline key: `csi-u` = `ESC[13;2u`, `w32` = win32-input-mode Shift+Enter key-down and key-up records `ESC[13;28;13;1;16;1_ESC[13;28;13;0;16;1_`. All writes are queued as one `WriteMsg::Data` so nothing interleaves. Then, after `--enter-delay-ms` (default 300 ms), CR as a separate write. The delay is a heuristic: it is measured from our last pipe write, not from Codex's processing, and is meant to exceed Codex's 120 ms Enter window and 60 ms Windows idle flush; the report records the write-to-`UserPromptSubmit` latency per case so the margin is visible. Readiness is the bound `SessionStart` plus the end of turn 1 (`Stop`), and the writer re-checks only the launch's revocation before the first byte (a `Keys` guard mode in `pty.rs`); DECSET 2004 is recorded, not required, because Codex ignores bracketed paste here. The send result lists the adapter-side changes (`compose_marks`, `escape_space`, and any accepted lossy reason).
- `win_keys` oracle: exactly one `UserPromptSubmit` per sent case, observed after the bootstrap turn's `Stop`, whose `prompt` equals the expected form byte for byte (the composition above, LF newlines, nothing else; with an accepted lossy reason, the trimmed form or the literal TAB), followed by a `Stop` whose `turn_id` equals the submit's. The submit and that `Stop` share one fixture deadline (120 s); after the `Stop` the receiver and Codex stay up for the full 5 s settle interval (a settle the run cutoff cut short is never `pass`), then the session is stopped and the case is decided from the drained receiver summary, so a late second submit still fails the case and a matching submit without its turn's `Stop` is `missing`. A case that did not complete gets a snapshot before the session stops. No CLI transform is tried. A prompt holding more literal `[13;2u` than the expected form is classified `csi_u_not_reassembled`; a marker the payload itself holds is text. An input whose expected prompt is empty is rejected before any write.
- Corpus F (`--subset f1`, Codex on Windows): ASCII; `日本語の入力テスト、句読点。「括弧」`; astral `𠮷野家`; `👨‍👩‍👧‍👦`, `🇯🇵`; decomposed `か\u{3099}` and `e\u{301}`; `神` (U+FA19, must arrive unchanged); 3-line Japanese with LF, with CRLF, and with a blank middle line; one line each starting with `/review の件`, `!ls は実行しない`, `?の意味`, and ending in `@README.md`; a 2-line entry whose second line starts with `/` and `!`; a multiline Japanese entry of more than 1000 characters (about 3.5 KiB, so Codex's `[Pasted Content N chars]` path is reached if the input bursts). Recorded only: `ㇷ゚` (U+31F7 U+309A); `　一行目\n二行目\n` with `--allow-lossy trim`; `列1\t列2` with `--allow-lossy tab`.

### 4.5 FakeCli modes

`chs-fake-cli --mode <echo|queries|stall|banner|attachable|spawn-tree|sleeper>`. Raw mode (Unix termios; Windows `SetConsoleMode` + `ENABLE_VIRTUAL_TERMINAL_INPUT`, `ReadConsoleW` → UTF-8), then `ESC[?2004h`. Every FakeCli process registers `(pid, start_time, role)` via `POST /witness` at start (liveness assertion only).
- `echo`: sends SessionStart; on CR after `ESC[201~` sends `UserPromptSubmit` with the pasted bytes through the real emitter; `--nested` starts a nested FakeCli `echo` that inherits the same env and sends its own `SessionStart` before and after the parent's (B-11); `--ignore-input` stops reading (B-10).
- `queries`: sends DSR 6/5, DA1, DA2, OSC 10/11, `CSI ? u`; checks reply content; exit 0 only if all arrive within 500 ms.
- `stall`: draws the fixed expected grid (CJK, combining, emoji) and never sends SessionStart; `--silent` draws nothing. `banner`: draws a fake trust prompt and sends a valid SessionStart (B-6).
- `attachable` (C-4, C-5): sends a bound SessionStart first (so the paste gate opens before any nonce), then prints an incrementing marker every 500 ms and records every value emitted; reports pasted nonces, received key events (Down, Enter, Esc, plain VT or win32-input-mode), and its console size with every marker to the receiver.
- `spawn-tree`: at t=0 spawns `sleeper` children: plain, SIGTERM+SIGHUP-ignoring, double-forked (reparented, same PGID), and a separate `setsid` escapee (Unix); on Windows a child spawned immediately and one requesting `CREATE_BREAKAWAY_FROM_JOB`. It reports the first live descendant so `--hold-assign-until-child` can delay job assignment until then. Every sleeper takes `--max-life-secs`, so a fixture that escapes containment still ends by itself; `--escape-orphan` (the escape probe, §4.6) adds a `setsid` grandchild whose parent exits at once; `--emit-output` (F-2c `after-spawn`) keeps writing a line every 10 ms, so output is pending whenever the launch is aborted.
- `sleeper`: minimal MCP stdio server (answers `initialize`, empty `tools/list`), so real CLIs keep it alive; registered as MCP server for real tree-kill (for Claude, an `--mcp-config` entry with `"type": "stdio"` and an explicit `env` holding the launch's `CHALDEA_HOOK_URL` / `CHALDEA_HOOK_TOKEN` / `CHALDEA_THREAD_ID`, since Claude does not pass its env on; written per launch to a new 0600 file in the run dir, which is removed with it; `-c mcp_servers.chs.command=…` with `env_vars` for Codex). In MCP role it attests via `/witness` only after `initialize` completes; A-8 requires that attestation before stop.
- `unrelated` negative control: a `sleeper` the harness starts outside the session; it registers via `/witness`, and its survival passes B-7.
- `window-calibrate` (C-5 calibration, Windows): started by the detached harness inside an observation job, with the window observer already running. It waits for `go` on stdin (sent after the job assignment), registers a window class, creates and shows one visible top-level window of its own (so the event's owner pid is its own pid), shows a caret first (a non-window control event), writes its pid, start time, and the hwnd to `--report-file`, keeps the window up 1 s, destroys it, and exits. With `--at-exit` it shows the window only in its last 50 ms before exiting.

### 4.6 Process-tree cleanup

Enumeration: macOS `proc_listallpids` + `proc_pidinfo(PROC_PIDTBSDINFO)` (pid, ppid, pgid, start time) plus `getsid`, with the process name taken from the executable image (`proc_pidpath`) and `pbi_name` only as a fallback; Windows `CreateToolhelp32Snapshot` + `GetProcessTimes`, plus `JobObjectBasicProcessIdList`. Kill set = harness-established ownership only: the process group (Unix), job membership plus the retained child handle (Windows), and pids the harness recorded by its own ppid walk and (Unix) pgid/sid scan from the child before stop, seeded only from identities (pid + start time) it verified. Witnesses never enter it; an expected session witness alive after stop is a survivor (fail); the `unrelated` negative control must survive. Before any fallback kill, (pid, start_time) is rechecked to avoid pid reuse. Containment limit: on macOS a `setsid` grandchild whose parent has already exited cannot be contained by pgid or ppid (no subreaper); `fake tree-kill --escape-probe` (not part of `fake all`) documents it (`containment_limit: true`; the orphan, a fixture the harness spawned, is removed afterwards through its verified witness identity and reported as `fixture_cleanup`), and A-8 with real CLIs shows whether real MCP servers do this.

- macOS: `killpg(SIGHUP)`, `killpg(SIGTERM)`, 2 s grace, `killpg(SIGKILL)`; then SIGKILL each recorded pid still alive (`escaped_primary`, `killed_by: fallback`). portable-pty's `Child::kill` is not used.
- Windows assign-after (B-7, C-3, real probes): `CreateJobObjectW` + `KILL_ON_JOB_CLOSE`, `AssignProcessToJobObject(child.as_raw_handle())` right after `spawn_command`. `--hold-assign-until-child` (FakeCli only) waits until `spawn-tree` reports a live descendant before assigning, forcing the race once. Stop: record job members, `TerminateJobObject`, check job members and escapees separately, run the fallback on recorded escapees, and only then close ConPTY (closing it can itself kill console clients and hide the result).
- Windows raw backend (`--pty-backend raw`, inside `os/windows.rs`; portable-pty is not patched or vendored): own `CreatePseudoConsole` (flags from `--conpty-flags`) + `CreateProcessW` with one attribute list holding `PROC_THREAD_ATTRIBUTE_PSEUDOCONSOLE` and `PROC_THREAD_ATTRIBUTE_JOB_LIST`, so the child is a job member from creation; the `CREATE_SUSPENDED` + assign + `ResumeThread` branch ships in the same binary and runs only if JOB_LIST fails, and counts only if `ResumeThread` returns 1. Every launch records its branch (`job_list` or `suspended`) and the loaded ConPTY module. A backend candidate is selectable only on the `job_list` branch, which production would use; the suspended branch is covered separately by F-2c's forced-failure case. The session's tree is that job, so `--hold-assign-until-child` does not apply (exit 2). Ownership is explicit from acquisition: each pipe end, the job, the process and thread handles, and the pseudoconsole are held by owning wrappers the moment they are created, so every early return releases them in a fixed order (terminate the job and process if one exists, then close the pseudoconsole, then the pipe ends). The output drain thread starts right after `CreatePseudoConsole`, before `CreateProcessW`, and keeps reading on every path until `ClosePseudoConsole` has returned (on Windows builds where `ClosePseudoConsole` waits for its output to be read, an undrained pipe would block it). If the drain thread cannot be started, the host's output read end is closed instead before anything else is released, so `ClosePseudoConsole` cannot block on it. The drain does not depend on its consumer: after a successful setup it forwards to the session's PTY reader through a channel until EOF, also during the master's teardown (so a child's final output still reaches the attached reader), and when that consumer is gone (failed reader start, abort) it keeps reading and discards until `ClosePseudoConsole` has returned. Output before the reader attaches is held up to 1 MiB; more than that makes the reader start fail (incomplete evidence, never a silent loss). The drain records how its read loop ended, `eof` or the read error (an error is never taken for EOF). The drain is OS-agnostic code (`src/os/drain.rs`) so its rules are tested on macOS. `ClosePseudoConsole` runs on a helper thread with a 3 s deadline; a close that does not return in time is recorded as hung (`close_hung`) and its thread abandoned. Every raw launch's record carries its teardown record (close result, `close_hung`, and how the drain ended): an ordinary launch its master's, a failed launch its setup's; the teardown list is cleared at each launch, so a launch that held nothing to tear down carries none rather than an earlier launch's. The session's child identity is its pid and the creation time read from the process handle the launch holds (the process table on Unix); a pid or start time of 0 fails the launch once the session guard exists, so the child is killed. On a setup error the process handle is released only after a bounded wait on it confirms the exit (`process_exit`). Each creation attempt is recorded with its branch, stage (`attr_list`, `attr_pseudoconsole`, `attr_job_list`, `create_process`, or `injected`), and Win32 result; `job_list_rejected` is set only when `CreateProcessW` with the job list itself failed, and a launch whose branches all failed still leaves its record in the report (`failed_launches`). Kill set, verification, and fallback are the same as assign-after, and run before ConPTY is closed. C-3's `job_first` case launches FakeCli `spawn-tree` through this backend (it established feasibility with zero escapees, §3); F-2 runs real CLIs through it. Production vendoring or patching is decided from F-2 (§1 D).

### 4.7 Lifecycle, deadlines, temp files

- The `Session` guard exists from the instant `spawn_command` (or the raw backend's `CreateProcessW`) returns, before job assignment or I/O setup, and owns the kill handles: the child killer and handle (usable even if job or pgid setup failed), pgid / job, and recorded pids. On Unix the parent's slave handle is dropped right after spawn so EOF reaches the reader.
- Teardown order: kill tree → check owned processes and witnesses → fallback on recorded escapees → drop the Unix writer (avoids the stray `\n` + VEOF reaching a live CLI) → close ConPTY while the reader keeps draining → join threads with a bound → stop receiver → remove `R/runs/<id>` unless `--keep-temp`.
- Watchdog thread with an independent stop path: at the scenario cutoff, `--deadline-secs` minus 10 s, it kills every registered tree directly through the guard's kill handles (using the retained child handle whenever job assignment or pgid setup did not succeed, even if a job exists), never via the writer thread, so teardown finishes inside the hard deadline; at the hard deadline, on Ctrl-C (`ctrlc` flag), or on panic (`catch_unwind`) it also kills, restores a real-home `hooks.json` if one is installed, writes `report.json` from what is known, and calls `process::exit`. Normal teardown and the watchdog share one kill path under one lock; a tree is marked done only after its kill and fallback completed, so a Ctrl-C that lands mid-teardown still kills. Blocked writer or reader threads are abandoned, not joined. No separate supervisor process.
- Bounded waits: SessionStart 20 s; UserPromptSubmit 30 s real / 5 s fake; query replies 500 ms; emitter 1 s / 3 s; receiver 5 s per request; kill grace 2 s + verification 5 s; scenario budget `--deadline-secs` − 10 s.
- Short paths: roots `~/.chs` (macOS) and `C:\chs`, 8-hex run ids, `CARGO_TARGET_DIR=C:\chs\t`.

### 4.8 Windows probes (set C, minimum implementation)

- `paste` (C-1): `fake paste` in all newline modes plus `real claude-paste` / `real codex-paste` with the required subset. Records code page, the ConPTY module loaded after each child's first PTY launch, and whether `CSI ?9001h` appeared; a bracketed paste is never switched to win32-input encoding. The probe derives its required child cases from the encoding each agent actually uses (`<agent>/<mode>/c<chunk>/<entry>` for bracketed paste, `<agent>/keys/<newline-key>/<entry>` for `win_keys`), so a child report of either shape is aggregated without `missing` cases.
- `startup` (C-2): `real claude-hooks` and `real codex-hooks --launches 3 --codex-mode both`, `codex-warm`, from `--cwd "C:\chs\work\日本 dir"`, plus one attended launch in a fresh folder: `chs` shows the snapshot and relays the owner's Down/Enter/Esc keypresses as ungated `write_key`; the attended case passes only if at least one key was written through the relay while unbound and SessionStart arrived after the writer reported that write done; otherwise it is `not_exercised`. An out-of-context `SetWinEventHook(EVENT_OBJECT_SHOW)` observer on its own thread with a message loop records, at callback time, each event's time, `dwmsEventTime`, `idEventThread` and that thread's process, hwnd, `idObject` / `idChild`, window class (`GetClassNameW`), owner pid and thread, owner image (`QueryFullProcessImageNameW`), owner ppid and start time, and whether the owner is in the observer's own observation job (`IsProcessInJob`); there is no callback-time visibility filter, so a flash already hidden still counts. Each observer owns its state (events, job handle), so a thread abandoned by a stop that timed out never writes into a later launch's evidence; only one observer thread may be alive at a time, so arming while an abandoned one remains fails (`harness_fail`), and the readiness report is a rendezvous: the thread counts it as received only when the starter took it, so a thread whose report came after the starter stopped waiting unhooks and exits at once. Only `OBJID_WINDOW` / `CHILDID_SELF` events are classified, for calibration and launches alike; other events are recorded and ignored. The observer is armed before the observed process is created, and stopping it is bounded: after the observed process ends it keeps pumping for a 500 ms drain interval so callbacks already queued are delivered, then posts `WM_QUIT`; a zero-event result counts only when that drain and the shutdown completed (otherwise `harness_fail`). Each observed launch (the calibration helper and every matrix child) runs in its own observation job (`KILL_ON_JOB_CLOSE`), assigned before the child does anything: the child waits for `go` on stdin until the parent has assigned it. The host's default-terminal setting (`HKCU\Console\%%Startup` `DelegationConsole` / `DelegationTerminal`) is recorded as the raw CLSID values, resolved to an executable only through a plain `HKCR\CLSID\{…}\LocalServer32` default value and recorded as `unresolved` otherwise. Classification of each window event during a launch:

  - `ambiguous`: the owner is `conhost.exe`, `OpenConsole.exe`, or `WindowsTerminal.exe` and not `ours`, the owner could not be resolved (no pid, process gone, broken ancestry), or the hwnd's owner at callback time is not the event thread's process (when that process cannot be resolved, not the event's thread): a reused handle. This check runs first.
  - `other`: any other owner (recorded, ignored).

Stopping the observer reports its health with the events; a failed `WM_QUIT` post, a thread that does not exit, or a message loop that ends on an error is `harness_fail`, as is an observer that fails to start. On a flash, the same Claude or FakeCli launch (same cwd and hook delivery) is re-run with the GUI-subsystem emitter, and its hook must still deliver; a flashed Codex launch is not re-run, because the GUI emitter's command cannot be trusted next to the console emitter's (§4.3), so its `no_flash` failure stands alone. The launching process waits up to 120 s for a valid URL for that run, then (printing the phase every minute) for `matrix_done`, and only then tells the owner to close the terminal and prints the `attach-client` command; without a URL, or when the matrix does not end by the child's deadline, it says why, tells the owner to keep the terminal, and points to step 5 (survival then stays `not_exercised`, which F-2 does not need). A terminal opened during an observed launch would be an `ambiguous` window, hence the wait. Finally, with `attachable` still running, the owner closes the launching terminal and runs `attach-client --confirm-close` from a new terminal: it asks the owner to confirm the close and records it via `/probe/confirm`, then a fresh nonce, from a request that started after the confirmation, must round-trip through the same `/probe/input` route to the same child, with the credential on stdin; anything less is `not_exercised`. identities that already exited are listed separately and need no membership; an unknown liveness or a failed membership query is `harness_fail`, as is any gap in the census, each recorded in the proof: a failed final process scan (`scan_error`), a job member whose identity read from its own handle is neither a recorded one nor created at or after the launch start, a reused pid from before the launch or one without a readable identity included (`unreconciled_members`; ## 6. Prior Art

Full survey with evidence: `docs/prior-art.md`. Rows that drive this design:
- Windows tree kill (1a, 1b): Job Objects are the only surveyed mechanism that catches detached descendants; Zed documents the assign-after race; no surveyed project combines `PROC_THREAD_ATTRIBUTE_JOB_LIST` with a pseudoconsole, which C-3 then verified with FakeCli on one host (§3); F-2 carries real CLIs through it.
- ConPTY backend and input (1d, 3b, 4d): portable-pty's Windows defects (§3) and conhost's own query answers and input parsing (§3) drive F-2 and F-3e.
- Bracketed paste (4a, 4c, 4e): every surveyed tool brackets only when DECSET 2004 is on; newline handling inside brackets is split (hence `--paste-newline`); herdr waits 300 ms before Enter.
- Codex trust (6b): session-flag keys are cwd-independent in source; trust can flip on upgrade (openai/codex#58011).
- Nested agents (6c): herdr scrubs inherited agent identity env and drops foreign `session_id` events.
- Reattach (8): herdr serves attach clients for daemon-owned ConPTY panes on Windows and checks for a kill-on-close parent job.

## 7. Open Questions and Risks

Owner decisions: O1 trust clicks on both machines and snapshot legibility (A-7); O2 whether a `codex-home` source is built and run if A-3 shows session-flags cannot persist trust (approved conditionally; the owner sees the result first); O3 running set C; O4 running §5 phase 3. C-2's attended cases stay `not_exercised` (no key was relayed in phase 2) and are not part of phase 3.

Orchestrator may choose: timeout and corpus defaults.

Risks:
- R1. Session-flag hooks may not persist trust; the fallback, a global `codex-home` source, is built only after A-3 shows that.
- R2. Codex may filter env for hooks under some `shell_environment_policy`; per-session data would then need another path (lookup by `session_id`).
- R3. Inbox conhost handling of `WIN32_INPUT_MODE` (0x4) is unknown; open-source OpenConsole ignores the flag. With 0x6 on the owner's inbox conhost, Claude's bracketed pastes arrived intact (§3); F-2b compares 0 and 0x6. Behavior varies by Windows build and loaded ConPTY module.
- R4. Hook shells differ on Windows (Claude: Git Bash; Codex: unknown); the fixed command must parse in each.
- R5. Codex trust can flip to `Modified` after an upgrade (openai/codex#58011), so A-3 holds for one version only. The adapter must treat a post-upgrade review prompt as an expected landmine handled by the A-7 snapshot path, and record the CLI version with trust keys.
- R6. The assign-after race is timing-dependent; one clean run does not prove absence, which is why job-first feasibility decides C-3.
- R7. Set C is a go/no-go screen from one owner run, not a support claim.
- R8. VS16 emoji width differs between `alacritty_terminal` and the CLIs; affects snapshot layout only.
- R9. The absolute emitter path ties the hook string to an install location; moving it re-triggers Codex review once.
- R10. A 20 s SessionStart timeout may fire on a loaded host (T3 Code allows Claude 5 min); the latency recorded in every run checks it.
- R11. Conhost may parse `ESC[13;2u` as a CSI sequence and swallow it instead of producing seven key events. F-1b judges the `w32` record on the same corpus, so either variant can carry F-1. A sequence that reaches Codex but fails reassembly delivers a literal `Esc`, Codex's interrupt key.
- R12. Conhost's VT input parser loses an escape sequence split across our writes (§3); a long single write may also be split at conhost's own pipe reads, which we do not control (no failure seen at chunk 0 up to 64 KiB). Production writes keep every sequence in one write.
- R13. On Windows a terminal query the app sends mid-paste is answered by conhost inside the paste body (§3); a real CLI then sees a CPR reply in its pasted text. Not observed with real CLIs; the adapter cannot reorder it.
- R14. Conhost accepted 64 KiB into a non-reading child without backpressure; its input buffer may grow without bound (F-3e records how far).
- R15. `win_keys` rides on Codex 0.169.0 internals (paste-burst timing, the Shift+Enter reassembly, composer triggers); a Codex upgrade can change any of them, so the adapter records the Codex version with each Windows input result.
- R16. C-5 treats every console-host or terminal window that cannot be proven ours as `ambiguous`, so on a host that hands console windows to Windows Terminal a real flash from our tree may only show up as `not_exercised`; the recorded class, image, and timing let the orchestrator read it.

Known constraints (accepted; the orchestrator checks them on the evidence):
- K1. Ambiguity and gate revocation are separate steps: after the receiver publishes a conflicting SessionStart, one queued paste write can start before the revocation callback runs. The drained receiver summary still makes that launch's verdict inconclusive, and that paste is not counted as evidence.
- K2. B-10's Ctrl-Break delivery runs under the `CREATE_NO_WINDOW` wrapper on Windows and is verified only by the owner's run; a B-10 `inconclusive` or `harness_fail` there is a harness issue, not a platform finding.
- K3. Version-named native Claude binaries (e.g. `~/.local/share/claude/versions/2.1.161`) are refused by the binary-name check; on this Mac the mise-installed `claude` binary is the supported path.

## 8. Out of Scope

`chaldea attach` (only the C-4 feasibility probe), Windows tuning beyond set C and the F probes, patching or vendoring portable-pty (the raw backend is spike-internal and Windows-only), Android PWA, SQLite event store and sync, daemon architecture, adapter capability tables beyond `input_encoding`, worktree management, Rescue tokens/A2UI, CI, Claude's native `"type": "http"` hooks.
