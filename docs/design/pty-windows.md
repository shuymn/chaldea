# Design: Windows ConPTY Backend (MVP PR 4)

Status: implemented in PR 4. Scope is the PR 4 row of `docs/mvp-design.md` §4 (cited as "mvp §N"): the Windows backend of `PtyRuntime`, an own `windows-sys` backend with `CreatePseudoConsole` flags `0` from `kernel32.dll` only, `CreateProcessW` with `PROC_THREAD_ATTRIBUTE_PSEUDOCONSOLE` and `PROC_THREAD_ATTRIBUTE_JOB_LIST` (the child is in a kill-on-close job from creation), `CREATE_SUSPENDED` + assign + resume as the fallback when the job list is rejected, stop by job termination plus the recorded-descendant kill, and a bounded pseudoconsole close. Its design obligations: FakeCli `spawn-tree` survivors and the unrelated negative control on Windows; injected setup failures leave no process or handle (spike F-2c); the job-list branch actually taken is recorded. It also adds the FakeCli features PR 3 deferred to PR 4 (`docs/design/pty-unix.md` §2.8): the `breakaway` role, the Windows console size for `attachable`, and `--emit-output` for the F-2c cases.

The contract implemented is `docs/design/pty-runtime.md` (cited as "PR2 §N") §2.1 "What each backend must supply"; the sibling backend is `docs/design/pty-unix.md` (cited as "PR3 §N"), whose spawn rule (PR3 §2.1) and ownership rule (PR3 §2.4) this backend follows in their Windows form. No trait or public type of PR 2 or PR 3 changes; additions are new `fake`-feature functions, new FakeCli flags, modes, and events, one additive `Cleanup` method, new values of `KillReport::method`, and crate-internal changes to `drain.rs` (`close_bounded` is removed; the Windows close worker replaces it) and `spawn.rs` (a guard type for the spawn lock). One caller obligation is made explicit for both OSes: `kill_tree` receives the caller's full list of recorded descendants on every call (§2.5).

Out of scope: daemon wiring and the daemon-in-a-job check (PR 8), input encoders including `win_keys` (PR 5), the gate and send path (PR 10), attach (PR 11), and Codex hook trust (PR 14).

## 1. Goal and Files

**Goal.** A Windows backend that opens a pseudoconsole at the requested size from the inbox `kernel32.dll` with its close worker already running, drains its output from before the child exists, starts the CLI with exactly the requested argv, cwd, and environment inside a kill-on-close job from its creation (job list, else suspended + assign + resume, else no launch), records which branch ran, kills the tree by job termination plus the verified recorded descendants the caller passes on each call and proves death from the job's own state and the handles it holds, closes the pseudoconsole within the caller's deadline, and releases everything on every failure path or reports what it could not prove. FakeCli gains what the Windows tests need. Every claim of §6 is checked by a named test on `windows-latest` with a real ConPTY; `macos-latest` builds everything and runs the platform-independent parts.

### 2.1 Public Additions and the Process Rules in Windows Form

```rust
/// The native backend of this OS (macOS: PR 3; Windows: this document).
#[cfg(windows)]
pub fn native() -> Arc<dyn PtyRuntime>;

// spawn.rs, crate-internal
pub(crate) struct SpawnGuard { _guard: MutexGuard<'static, ()> }   // private field: only spawn_lock() builds one
pub(crate) fn spawn_lock() -> SpawnGuard;                // was MutexGuard<'static, ()>
```

`with_spawn_lock` is unchanged. A `SpawnGuard` can come only from `SPAWN_LOCK`, so a function that takes `&SpawnGuard` cannot be called under some other mutex (a plain `MutexGuard<()>` could come from any). The macOS backend's `wake_pipe` takes `&SpawnGuard` the same way; the mutex and the RAII scope around `wake_pipe(&spawn_lock())` and the Unix `cmd.spawn()` are unchanged, so neither critical section changes. The field is named `_guard`, so holding it only for its drop raises no unused-field warning under `-D warnings`. Under `cfg(all(windows, any(test, feature = "fake")))`, the same cfg as the call trace that reads it (testkit links this crate with `fake` and without `cfg(test)`), a `SpawnGuard` also sets a thread-local flag while it lives, and `spawn_lock_held_here()` reads it; the flag, the helper, and the guard's instrumentation compile under that cfg only, so macOS builds have no dead code. A trace thus records whether the tracing thread holds the lock, not whether some other test thread does. The existing `spawn_lock_held()` stays for the macOS tests that use it (`unix/sys.rs`).

**The spawn rule on Windows.** Every child the daemon creates is created under `SPAWN_LOCK` (PR3 §2.1). On Windows the hazard is handle inheritance, not a fork: an inheritable handle that exists while another thread runs `CreateProcess` with `bInheritHandles = TRUE` and no handle list goes to that unrelated child. std's own lock covers only std spawns (W6), and `CreatePseudoConsole` itself holds inheritable duplicates of conhost's pipe ends while it starts conhost (W3); an unrelated child that inherits the output pipe's write end keeps the session's output from reaching EOF until that child exits. So this backend holds the lock **around `CreatePseudoConsole`** (the inheritance window W3 establishes) and **around each `CreateProcessW` attempt** (the uniform rule that every child is created under the lock; the call creates no inheritable handle, so this costs only the call's duration). It does not hold the lock for `AssignProcessToJobObject` and `ResumeThread`: a child created suspended runs no instruction until resumed, and neither call creates a handle, so another spawn in between changes nothing. Every wait and release of a failure path (stage 5.4's bounded wait, `release_early`) runs without the lock, so a failing spawn cannot stall other spawns. `sys::create_pseudo_console` and `sys::create_process` take `&SpawnGuard` (§2.7). Everything else the backend creates is non-inheritable from creation (`std::io::pipe`, `CreateJobObjectW(NULL, NULL)`, handles from `CreateProcessW`, `OpenProcess`, and `DuplicateHandle` with `bInheritHandle = FALSE`), and its own `CreateProcessW` passes `bInheritHandles = FALSE`, so it neither gives nor takes an inherited handle. **Constraint:** a library that creates children outside the lock with `bInheritHandles = TRUE` can still catch W3's duplicates; the daemon uses none (a PR 8 / PR 10 obligation, as on macOS).

**Ownership on Windows.** The backend holds the leader's process handle from `CreateProcessW` until the `WindowsChild` drops. Windows has no reaping: the exit code stays readable through that handle, and the process object, with its pid, cannot be reused while the handle is open. So ownership cannot be lost to another waiter, and no `lost` state exists. The one daemon-side rule is that no code closes a handle it did not open (every handle is an `OwnedHandle`; no `CloseHandle` on a raw value), since closing the backend's handle by mistake could free the pid.

**Identity format** (`ProcessIdentity`): `pid`; `start_time` the process creation time from `GetProcessTimes` on a handle to that process, a `FILETIME` as decimal 100-ns units since 1601-01-01 UTC, used only for equality; `group` is `job:<leader pid>` for the leader and for job members the kill reports, and empty for a process outside the job, including a suspended child whose assignment failed (D12). The creation time is wall-clock: nothing orders processes by it.

**Validation** (before anything is created; a failure is `NeverStarted` with `Cleanup::Confirmed`). It also builds the UTF-16 buffers, so no buffer error can happen after a resource exists.

**Buffers** (`cmdline.rs`, pure):

- *Application name*: `argv[0]` as given, NUL-terminated. `CreateProcessW` with a non-null `lpApplicationName` neither searches the path nor appends an extension (Microsoft, "CreateProcessW function").
- *Command line*: `argv[0]` always quoted, then each argument separated by one space and quoted by std's rule (W6): quoted when empty or containing a space or tab; inside, `n` backslashes before a `"` become `2n + 1` followed by `\"`, and `n` trailing backslashes before the closing quote become `2n`. These are the rules the MSVC CRT and Rust's own argument parser undo ("Parsing C++ command-line arguments"). `CreateProcessW` may modify `lpCommandLine`, so the buffer is kept immutable and `sys::create_process` copies it into a fresh mutable buffer for each attempt (W6, W9).
- *Environment block*: `spec.env` sorted with `CompareStringOrdinal(…, TRUE)` ("Changing environment variables": the block is sorted case-insensitively, in Unicode order, without regard to locale), each `KEY=VALUE\0`, then a final `\0`; an empty `spec.env` gives `\0\0`. Nothing is inherited: `CREATE_UNICODE_ENVIRONMENT` with this block.
- *Current directory*: `spec.cwd`, with a verbatim prefix removed under the validation rule above (W6: the current directory does not accept verbatim paths), NUL-terminated. A `cwd` without the prefix is passed as given.

**Sequence.** Each stage lists what exists when it fails. `release_early` (never under the lock) is: `control.close(now + 2 s)` (§2.3) while the drain reads, drop the input write end, `Drain::finish(2 s)`, drop the job; `Cleanup::Confirmed` when the close returned and the drain ended (EOF or read error, thread joined), else `Unresolved { kill: None, close: Some(..), drain_abandoned }`. **What `Cleanup::Confirmed` covers:** host-side release (every handle this spawn opened in the daemon's process is closed, the pseudoconsole's close operation returned, the drain thread ended) and, when a process existed, the backend's proof that it is dead (its handle signalled, or the teardown's `tree_dead: true`). It does not cover conhost's own exit, which the backend observes only as output EOF, nor the `conpty-close` thread's exit after its close returned (§2.3).

1. **Pipes.** `std::io::pipe()` twice: `(in_r, in_w)` and `(out_r, out_w)` (W2). Failure: what exists is dropped; `NeverStarted { Setup }`, `Confirmed`.
2. **Pseudoconsole.**
   1. *Close worker.* `CloseWorker::start("conpty-close")` (§2.3), before the pseudoconsole exists. Failure: drop the pipes; `NeverStarted { Setup }`, `Confirmed`. No pseudoconsole was created, so nothing can be left without a closer.
   2. *Create*, under `SPAWN_LOCK`: `sys::create_pseudo_console(&guard, spec.size, &in_r, &out_w)` = `CreatePseudoConsole(COORD { X: cols, Y: rows }, in_r, out_w, 0, &hpc)`; the guard is dropped when the call returns. On success the `Pcon` is armed on the worker at once (`arm` cannot fail) and goes into a `WindowsControl` (§2.3), so no later path can forget it. Then `in_r` and `out_w` (the backend's copies of conhost's ends) are dropped: conhost holds its own (W3), and conhost is then the output pipe's last writer (W4). Record the `conpty_module` evidence: `GetModuleFileNameW(GetModuleHandleW("kernel32.dll"))`. Failure (HRESULT < 0, mapped to the Win32 code when its facility is `FACILITY_WIN32`, else `other`): `worker.close(now + 2 s)` (unarmed: the worker acknowledges and exits), drop the pipes; `NeverStarted { Setup }`, `Confirmed` when the worker acknowledged within the bound, else `Unresolved { kill: None, close: Some(CloseReport { elapsed: None }), drain_abandoned: false }`.
3. **Drain.** `Drain::start(out_r, output)` (PR2 §2.4; in `fake` and test builds `out_r` may be wrapped by the output-marker reader of §2.6), before any process exists (PR2 §2.1). Failure: `Drain::start` drops `out_r` first, so a waiting `ClosePseudoConsole` gets a broken pipe instead of an undrained one; then `control.close(now + 2 s)`, drop `in_w`; `NeverStarted { Setup }` with `Confirmed` when the close returned, else `Unresolved { kill: None, close: Some(..), drain_abandoned: false }` (no drain thread exists; output EOF is not observable on this path and not claimed).
4. **Job.** `sys::create_job()`: `CreateJobObjectW(NULL, NULL)` (unnamed, not inheritable), then `SetInformationJobObject(JobObjectExtendedLimitInformation)` with `LimitFlags = JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` and nothing else (no `BREAKAWAY_OK`, no `SILENT_BREAKAWAY_OK`; §3 "Breakaway"). Failure of either call (the job handle, if created, is dropped): `release_early`; `NeverStarted { Setup }`.
5. **Create.** Every successful `CreateProcessW` is followed at once by `creation_time(&hProcess)` (§2.1), before any assignment, so every report about this child carries a verifiable identity when the creation-time read succeeds; the start is empty only when that read failed.
   1. *Job-list attempt.* `AttrList::new(2)`, `set_pseudoconsole(&pcon)`, `set_job_list(&[job])`; `STARTUPINFOEXW` with `cb`, `dwFlags = STARTF_USESTDHANDLES`, the three standard handles `INVALID_HANDLE_VALUE` (so the child's standard handles are the pseudoconsole's, never the daemon's, W9), `lpAttributeList`; under `SPAWN_LOCK`, `CreateProcessW(app, <fresh copy of cmdline>, NULL, NULL, FALSE, EXTENDED_STARTUPINFO_PRESENT | CREATE_UNICODE_ENVIRONMENT, env, cwd, &si, &pi)`. Success: the child is a job member before its first instruction (Microsoft, "UpdateProcThreadAttribute function", `PROC_THREAD_ATTRIBUTE_JOB_LIST`). Branch `job_list`.
   2. *Suspended attempt*, once, whenever `set_job_list` or the job-list attempt's `CreateProcessW` failed, whatever the error. Microsoft documents no error code for a rejected job list, and validation has already checked `argv[0]` and `cwd` before anything was created, so most launch-input failures never reach `CreateProcessW`; the rare one that does (a program removed after validation) costs one more failing call. A failure of `AttrList::new` or of `set_pseudoconsole`, shared by both attempts, does not retry. `AttrList::new(1)` with the pseudoconsole only; under `SPAWN_LOCK`, the same call with `| CREATE_SUSPENDED` and a fresh command-line copy; the guard is dropped when the call returns. On success, read the start, then `AssignProcessToJobObject(job, hProcess)`, then `ResumeThread(hThread)` must return 1. Branch `suspended`.
   3. *No process.* `CreateProcessW` returned `FALSE` on every attempt made: no process exists. `release_early`; `NeverStarted`. **Error message:** whenever the suspended attempt ran, the error is `io::Error::new(kind, "job_list: <stage>: <e1>; suspended: <stage>: <e2>")`, both stages and errors kept even when the codes are equal (`<stage>` names the failing call: `set_job_list`, `create_process`, `assign`, `resume`). `kind` comes from the last error: `ERROR_FILE_NOT_FOUND` or `ERROR_PATH_NOT_FOUND` with `metadata(argv[0])` now `NotFound` → `NotFound`; `ERROR_ACCESS_DENIED` → `PermissionDenied`; anything else (`ERROR_DIRECTORY` for a cwd, `ERROR_BAD_EXE_FORMAT` for a non-PE file) → `Setup`.
   4. *Suspended-branch failures.* The child exists, created suspended, and none of the program's instructions has run. Without the lock. **The held process handle decides:** after the termination call, whether it succeeded or failed, `WaitForSingleObject(hProcess, 2 s)`; signalled is a confirmed exit, not signalled is unconfirmed.
      - **Start read or assignment failed.** The job has no member. `TerminateProcess(hProcess, 1)`, then the wait. Confirmed → `release_early`, then `NeverStarted { Setup, error }` with its `Cleanup`. Unconfirmed → `release_early`, then `StartedThenFailed { stage: "identity" | "job_assign", identity: Some(pid, the start read after create, group ""), cleanup: Unresolved { kill: Some(KillReport { method: "windows_process", tree_dead: false, survivors: [identity] }), close, drain_abandoned } }`. The process handle is then dropped: the backend keeps no retry owner, and the identity in the error is what the daemon acts on (conservative: the daemon treats a positional prompt as unconfirmed).
      - **Resume failed** (`u32::MAX`, or 2 or more: the thread is still suspended) after a successful assignment. `TerminateJobObject(job, 1)`: the job owns the cleanup from here. Then the wait. Confirmed → `release_early`, `NeverStarted { Setup, error }`. Unconfirmed → `StartedThenFailed { stage: "resume", identity: Some(group "job:<pid>"), cleanup: Unresolved { kill: Some(KillReport { method: "windows_job", tree_dead: false, survivors: [identity] }), .. } }` after `release_early`, whose job drop terminates the member by kill-on-close (a termination mechanism, not observed here, so the report stays `Unresolved`).
      - **`ResumeThread` returned 0**: the thread was not suspended and may have run. The child is in the job, so it is handled as a stage 6 failure (`StartedThenFailed { stage: "resume" }` through the teardown).
   The thread handle is closed at the end of the stage. Each attribute list is deleted when its attempt ends; the job array and the `Pcon` it points to outlive it by construction (§2.7).
6. **Settle.** The `WindowsChild` (§2.4) is built at once, owning the process handle, the job, and the start read in stage 5. If that read failed on the job-list branch (the child is in the job and may run): `StartedThenFailed { stage: "identity", identity: None }`, released by `SpawnedParts::teardown` (`backend.rs:268-293`): `kill_tree(&[], now + 5 s)` (the job), drop input, `control.close(now + 2 s)`, `Drain::finish(2 s)`.
7. **Hand over** `SpawnedPty::new(SpawnedParts { child, output: drain, input: Box::new(in_w), control: Box::new(control), size: spec.size, evidence })` with `evidence = [("job_branch", "job_list" | "suspended"), ("conpty_module", <path>)]`, plus `("job_list_error", "<stage>: <error>")` on the suspended branch. These are the keys PR2 §2.1 names, plus one additive key; `evidence` stays a crate-internal vector surfaced by `Session::evidence()`.

`spawn` has no deadline of its own: it waits for `SPAWN_LOCK`, and `CreatePseudoConsole` and `CreateProcessW` are synchronous kernel32 calls without a handshake. A failure after stage 6 builds the child is always `StartedThenFailed` released by the teardown, whose order (kill → input → close → drain) differs from `release_early` only in that a tree exists to kill first. The teardown **attempts** the kill before releasing I/O; when the kill cannot prove death by its deadline, input and the pseudoconsole are still released and the result is `Unresolved` with the kill report (`backend.rs:283-291`).

**Crash window (PR 10).** If the daemon dies between a suspended `CreateProcessW` and `AssignProcessToJobObject`, the suspended child is in no Chaldea job, so the daemon's exit does not kill it, and no `launch_started` names it. It never runs (its only thread is suspended), but it holds a pid and its image until something terminates it. The job-list branch has no such window. Recorded under "Related Text" as a PR 10 obligation.

### 2.3 Input, Output, Control

- **Input** is `std::io::PipeWriter` (`in_w`), boxed as the session's `input`. `write` is one `WriteFile` on a synchronous anonymous pipe: it returns only when every byte is in the pipe (Microsoft, "WriteFile function", pipes: a write on a blocking pipe completes when a read makes room), so whole acceptance holds without a loop. A broken pipe (conhost gone) is an error, which the writer turns into `InputBroken` (PR2 §2.3). **Dropping it writes no bytes**: `PipeWriter`'s drop is `CloseHandle`. A write blocked on a full pipe ends when conhost goes away, which `ClosePseudoConsole` causes at close step 4 (PR2 §2.2); the writer thread is reported abandoned if step 3's budget runs out first, exactly as PR2 §2.2 allows. What conhost does when the input pipe reaches EOF is not relied on: on every path that has a child, dropping the input follows an attempted kill (PR2 §2.2 step 2, or the spawn teardown), or a death already proven by an earlier kill; a kill that cannot prove death surfaces as `Cleanup::Unresolved` on spawn teardown and as `CloseOutcome.kill` on `Session::close`. Paths before any process exists have no child to kill. Otherwise the drop follows conhost's death.
- **Output** is `std::io::PipeReader` (`out_r`), owned by the drain from stage 3. `ERROR_BROKEN_PIPE` reads as `Ok(0)` (W2), so the drain reports `OutputEnd::Eof` when the output pipe's last writer closes; any other read error is `OutputEnd::Error`. **Three facts are kept apart:** the pseudoconsole released (`close` returned, `CloseReport::elapsed` is `Some`); output EOF (the last writer of the output pipe closed, which is conhost, normally because the pseudoconsole was released and also when conhost dies on its own, W4); and the process exit observed (`wait_timeout` through the held handle). Child exit does not end the output on Windows, and the session's `Exited` (from `wait_timeout`) is the exit signal, as PR2 §2.2 already treats it. `ReleasePseudoConsole` is not called (§3).
- **Startup output.** conhost writes its own setup sequences (it requested `?9001h` on the spike host, arch §5 "Windows inbox conhost") from before the child exists; the drain feeds them to the VT from the first byte. With flags `0` conhost sends no cursor query that waits for a reply (W5); if a build sends one, the responder's reply waits in the reply lane until the writer thread exists (PR2 §2.2 "Start"), and `spawn` does not depend on it. conhost answers DSR and DA itself and forwards the kitty query (prior-art row 3b); the responder answers what reaches it.

```rust
// windows/control.rs (compiled only on Windows, so no other target has an unused item)
pub(crate) struct CloseWorker { /* sender to the worker, completion receiver, JoinHandle */ }
impl CloseWorker {
    pub(crate) fn start(name: &'static str) -> io::Result<CloseWorker>;  // the thread exists and waits
    pub(crate) fn arm(&mut self, close: Box<dyn FnOnce() + Send>);        // hands over the close; cannot fail
    pub(crate) fn close(self, deadline: Instant) -> Option<Duration>;     // Some: the close operation returned by `deadline`
}

struct Pcon(HPCON);                                   // not a kernel handle; closed only by Pcon::close(self); Drop does nothing
struct WindowsControl { pcon: Option<Arc<Pcon>>, worker: Option<CloseWorker> }   // PtyControl
```

**The close worker.** `start` spawns the thread before the resource it will close exists; the thread waits for a message. `arm` sends it the close closure (the worker is blocked in its receive and nothing else runs on it, so the send cannot fail while the worker lives). `close(deadline)` tells the worker to run the closure and waits for the closure's completion message until `deadline`: `Some(elapsed)` means **the close operation returned** within the deadline; `None` means it did not, and the thread is abandoned with the close recorded as hung. It does not join the thread: a joined thread could still overrun the deadline, because `is_finished` can be true before the thread has stopped and std's Windows `join` waits without a timeout (W12). The thread's own exit is checked only where it matters, in the handle-count harness, through a bounded wait on the thread handle (§7). An unarmed worker told to close acknowledges and exits; if it does not acknowledge in time the result is `None` and the caller reports `Unresolved` (stage 2.2). Dropping a `CloseWorker` without `close` disconnects it: an armed worker then still runs the closure on its own thread, and an unarmed one exits; the caller never blocks. Time is measured against the caller's absolute deadline, not from the moment a thread starts. `close_bounded` in `drain.rs` is removed with its half of `hung_close_is_bounded`; the worker's unit tests in `control.rs` are `hung_close_worker_is_bounded`, `unarmed_worker_exits`, `dropped_armed_worker_runs_the_close`, and `close_and_drop_release_the_control_reference_first`.

- `resize(size)`: `ResizePseudoConsole(hpc, COORD { X: cols, Y: rows })` through the control's `Arc<Pcon>`; an HRESULT failure maps as in stage 2. Unbounded (PR2 §2.1): conhost can wait on the drain. With `pcon` already `None` it returns an error (unreachable through the trait, since `close` consumes the control; no path touches a closed pseudoconsole).
- `close(deadline)`: first `self.pcon.take()` and drop it, leaving the armed closure's clone the only reference, then `self.worker.take()` and `worker.close(deadline)`; the closure does `Arc::try_unwrap(pcon)` and `Pcon::close`. Releasing the control's reference before the dispatch makes `try_unwrap` succeed by construction. The drain keeps reading meanwhile (PR2 §2.2 step 4), so a build whose close waits for the output to drain (W4) returns. `CloseReport { elapsed }` is the worker's result. Because the worker exists before the pseudoconsole, no path holds a pseudoconsole without a thread that can close it.
- `Drop` without `close` (a guard or session dropped on a path that never closed it): the same two steps in the same order, `pcon.take()` dropped first, then the worker's `close(now + TEARDOWN_CLOSE)` (2 s). After `close` both fields are `None` and `Drop` does nothing.
- `CloseOutcome::abandoned` lists `pty-writer`, `pty-drain`, `pty-wait` (W12) and not `conpty-close`; a hung close is visible as `close.elapsed == None` and `released.control == false`, which the tests assert (listing `conpty-close` there would change PR 2's `abandoned` contract for no new information).

### 2.4 Child: Identity, Exit

```rust
struct WindowsChild {
    process: OwnedHandle,                // from CreateProcessW; PROCESS_ALL_ACCESS
    job: OwnedHandle,                    // KILL_ON_JOB_CLOSE: closing the last handle terminates what is left
    identity: ProcessIdentity,           // start_time empty only during a stage 6 failure
    exit: OnceLock<ChildExit>,
    kill: Mutex<KillState>,              // held extras' handles across calls (§2.5); wait_timeout never takes it
}
```

- `identity()` returns the stored value; no panic path.
- `wait_timeout(timeout)`: if `exit` is set, return it. Else `WaitForSingleObject(process, ms)` in chunks: a zero `timeout` is one wait of 0 ms (a poll); otherwise each chunk is `ms = clamp(ceil_ms(remaining), 1, u32::MAX − 1)` (a sub-millisecond remainder rounds up to 1 ms, never to `INFINITE`), and a `WAIT_TIMEOUT` on a chunk continues with the next until `timeout` has passed. `WAIT_OBJECT_0` → `GetExitCodeProcess` → `ChildExit { code: Some(code as i32), signal: None }` (the 32-bit code reinterpreted, so `0xC000013A` is negative), stored once and returned on every later call; `WAIT_TIMEOUT` at the end → `Ok(None)`; `WAIT_FAILED` → the error (`WaitFailed`). It takes no lock. `wait_timeout` rounds a sub-millisecond remainder up because its caller asked to wait that long; the kill engine, bound by a deadline, rounds down and polls instead (§2.5 "Clock rules"). `sys::wait` itself takes whole milliseconds and splits a wait above `u32::MAX − 1` ms into chunks.
- The kill exit code is 1 (`TerminateJobObject(job, 1)`), as in the spike and Codex; a killed leader reports `code: Some(1)`.
- `Drop` closes the process handle and the job handle. The job handle is neither named nor inheritable, so the `WindowsChild` holds its only handle, and closing it terminates any member still running (`KILL_ON_JOB_CLOSE`; CL-28). The child is dropped when its last `Arc<dyn PtyChild>` goes, which can be the session's waiter thread after `close` returns. Kill-on-close is a termination mechanism: nothing observes the members' exit at that point, so it is never a death proof (PR 10 confirms death by identity).

### 2.5 Tree Kill

```rust
impl PtyChild for WindowsChild { fn kill_tree(&self, extra: &[ProcessIdentity], deadline: Instant) -> KillReport; }

pub(crate) trait JobOs {                       // the real one wraps sys; tests script it with a synthetic clock

    fn sleep(&self, d: Duration);

    fn open_process(&self, pid: u32, access: Access) -> io::Result<Held>;  // one OpenProcess
    fn creation_time(&self, h: &Held) -> io::Result<u64>;                // one GetProcessTimes
    fn in_job(&self, h: &Held) -> io::Result<bool>;                      // one IsProcessInJob
    fn signalled(&self, h: &Held, wait: Duration) -> io::Result<bool>;   // one WaitForSingleObject; a zero wait polls

pub(crate) enum PidList { Complete(Vec<u32>), TooSmall }
pub(crate) enum Opened { Held(Held), Gone, Stale, Unverifiable, Cut }   // Cut: the deadline came between its calls
pub(crate) struct KillState { held: HashMap<(u32, u64), Held> }       // verified extras: handle open, so the pid stays reserved
```

`ProcessIdentity` has no `Ord` (W12), so the state uses a hash map.

**The caller's obligation (both OSes).** The caller passes its **full list of recorded descendants on every `kill_tree` call**: the first stop, a retry after `windows_busy`, a retry after `tree_dead: false`, and `close` after an earlier `kill`. A report's survivor list is diagnostic (deduplicated per pid, possibly naming the leader instead of an extra) and is never what the caller resubmits. The backend keeps no unresolved identity across calls; an identity it could not open in a call is a survivor of that call and the caller's to pass again, which it does anyway under this rule. The same obligation is stated on `Session::kill` and `Session::close` (doc comments only; no public type changes): the supervisor retries with its full list through `Session::kill` while the session is available, closes explicitly with its full list, and keeps the launch unresolved when that consuming `close` cannot prove death. An implicit `Drop` of a `Session` closes with `&[]` (`session.rs:920-924`): it is best-effort cleanup and never a death proof, since it cannot supply identities that no earlier call opened. This is recorded as a PR 10 obligation for both backends ("Related Text"); PR 3 retains more across calls (§3), which the uniform obligation makes invisible to the daemon.

**What persists across calls** is only `held`: process handles already opened and verified by creation time on that handle. Keeping them costs one handle each, stops pid reuse, and every later call waits for them, so a `kill(&[a])` that opened `a` followed by `close(&[])` still cannot prove death while `a` lives. A held handle is released at the read that shows it signalled, and on child drop.

**What the job guarantees.** The job lacks `BREAKAWAY_OK`, so a process created by a member is a member whatever inner jobs exist: a member's breakaway request from Chaldea's job fails, and a descendant that breaks away from a permissive inner job stops at Chaldea's job (W11; CL-16 checks the first). A member cannot leave: assigning it to another job nests that job under Chaldea's or fails (W11). The leader is a member from creation (job list) or before it runs (suspended + assign). Nothing outside can join: only stage 5 assigns, and the job handle is unnamed and not inheritable. `JobObjectBasicAccountingInformation.ActiveProcesses` counts the processes of child jobs too (W11). So `ActiveProcesses == 0` read once means no process is associated with the job, and it stays 0.

**Outside the guarantee**, and reached only through `extra`: processes that were never in the job (started on the CLI's behalf by another process, such as a COM or packaged-app activation, a service, or WMI `Win32_Process.Create`; the spike saw an outside-job packaged PowerShell under Codex, arch §5 "Outside-job PowerShell"), and descendants of an `extra` identity that are outside the job. The backend does not walk the process list to find the latter (§3): in the observed case the outside-job PowerShell and its conhost were dead after job termination before any pid fallback (arch §5), and Codex under `--no-daemon` keeps its MCP servers inside the launched tree (arch §5), so the named identities are the remaining reach.

**Extras are trusted input.** A matching creation time identifies the process object behind a pid, not its provenance: passing the exact identity of an unrelated live process kills it (CL-18 does this on purpose with a test-owned process). The daemon passes only identities attributed to this launch (hook emitters' records); attribution is a PR 9 / PR 10 obligation ("Related Text"). **The unrelated-process guarantee is scoped accordingly:** the backend terminates only through the job and through handles of supplied extras whose creation time matched. Separately, `ClosePseudoConsole` sends `CTRL_CLOSE_EVENT` to every process attached to that console (W4), including an outside process that attached itself with `AttachConsole`; that is the console's behaviour at close, not a termination by the backend.

**Extras.** A supplied identity is well-formed if its pid is not 0, not 4 (System), not the daemon's own, and its `start_time` parses as `u64`; a malformed one is a survivor of the call, and that call cannot report `tree_dead: true`. Identical identities collapse; a well-formed identity already in `held` is resolved by that handle. `open_verified(os, id, deadline)` checks the clock before each underlying call: `OpenProcess(PROCESS_TERMINATE | PROCESS_QUERY_LIMITED_INFORMATION | SYNCHRONIZE, FALSE, pid)`, falling back to `PROCESS_QUERY_LIMITED_INFORMATION | SYNCHRONIZE` on `ERROR_ACCESS_DENIED` (then it can be waited for but not killed); `GetProcessTimes` **on that handle**: equal start → `Held` (moved into `held`); another start → `Stale` (the recorded process is gone, since its pid was freed; never signalled); `ERROR_INVALID_PARAMETER` → `Gone`; any other failure → `Unverifiable`; the deadline reached between two of these calls → `Cut`. `Held`, `Gone`, and `Stale` resolve the identity for this call; `Unverifiable` and `Cut` leave it unresolved, a survivor if still unresolved at the end. A `Held` extra is terminated only through its own handle, so the identity check and the kill cannot refer to different processes. The one residual case is two processes with the same pid and the same 100-ns creation stamp after a wall-clock step back, which is not defended (P-2).

**The proof rule.** `tree_dead: true` exactly when, in this call: a read of `ActiveProcesses` returned 0; the leader's handle and every handle in `held` are signalled; every well-formed supplied identity is resolved; and the call was passed no malformed entry. Nothing proven by an earlier call is reused. **Bound:** a member counted out of the job has stopped running, but the job does not report when its handles (file locks among them) are released; Codex observes the job list emptying before members release their handles (W7). The leader and the held extras are waited for until signalled; other members are not (§4, worktree removal).

**Clock rules.** `now()` is read before every OS call, including each list-size retry, each member open, and each call inside `open_verified`; no call starts at or after the deadline. Every sleep is `min(10 ms, deadline − now)`. A handle wait with budget `r` waits `floor(r)` whole milliseconds, and polls (a zero wait) when `r` is under 1 ms, so no wait is rounded up past the deadline. The tolerance is one OS call in flight at the deadline, as in PR 3.

**Steps.**

1. **Lock.** `now ≥ deadline`: no OS call; one `try_lock`. Acquired → `tree_dead: false`, method `"windows_job_incomplete"`, survivors the leader, every handle in `held`, and the supplied identities. Not acquired → `tree_dead: false`, method `"windows_busy"`, survivors the leader and the supplied identities. Else `try_lock` is polled with the sleep above until the deadline; never acquired → the same `windows_busy` report. In both busy cases the caller retries with its original list (the obligation above). A poisoned lock is taken over.
2. **Open.** One `open_verified` per unresolved well-formed identity, checking the clock before each.
3. **Opening check.** `active_processes() == 0`, every handle in `held` and the leader's signalled with a zero wait, every supplied identity resolved, no malformed entry → `tree_dead: true` with no termination call (an already dead tree).
4. **Terminate.** `terminate_job()`; `terminate()` each held handle not yet signalled. A failure is recorded and the steps continue: the proof does not depend on these calls succeeding, only on what step 5 reads.
5. **Prove**, in rounds until the deadline. Each round, in order:
   1. *Extras pass* (independent of the job count): one `open_verified` per unresolved identity, and `terminate()` once for each newly held or still unsignalled held handle.
   2. *Job:* `active_processes()`. Nonzero → `terminate_job()` again (a member that created a child as the termination began). Zero → wait on the leader and each held handle for at most `min(100 ms, deadline − now)` each under the clock rules; all signalled, every supplied identity resolved, no malformed entry → `tree_dead: true`.
   3. *Pace:* a round that resolved no identity and saw no handle signal sleeps. A query error is not proof and counts as no progress.
   4. *Member snapshot* (survivor report only, at most once per call): in the first round whose count is nonzero, after its actions, `list_members` (capacity 64, doubling on `TooSmall` up to 4 096), then `member_identity` for each listed pid (listed only if `IsProcessInJob` confirms membership on that handle, since the pid may name a new process; `group` `job:<leader pid>`; empty `start_time` when it cannot be read). The snapshot is never refreshed; a later round whose count reads 0 discards it, since its members are then known to be gone.
6. **At the deadline**, `tree_dead: false`. Survivors: the leader unless seen signalled; the member snapshot, if not discarded; every unsignalled held handle's identity; every unresolved supplied identity; this call's malformed entries. Deduplicated: identical identities collapse, then one entry per pid in the order leader, held extra, snapshot member, unresolved identity (the smallest `start_time` value), malformed entry (first passed). Method `"windows_job"` when the last `ActiveProcesses` read was 0 (no member survives, the list is complete); `"windows_job_incomplete"` when that read failed or was nonzero, since members may have changed after the snapshot or it was cut short. The member list never enters the proof.

`method` is `"windows_job"`, `"windows_job_incomplete"`, or `"windows_busy"`; all three are values of the existing `String` field, so no type changes, and PR 10 treats every `tree_dead: false` alike. There is no graceful phase: Windows has no signal for a console process tree that the daemon can send without attaching to the pseudoconsole, and closing the pseudoconsole first would kill console clients before the job proof and hide survivors (spike §4.6). `kill_tree` has no panic path.

**Daemon inside a job** (PR 8). Nesting is conditional (W11): a parent job that sets UI limits, or with which no valid hierarchy forms, refuses it. Then the job-list attempt fails, the suspended attempt's assignment fails, the suspended child is terminated (stage 5.4), and the spawn is `NeverStarted` (or `StartedThenFailed` with `Unresolved` if its exit is not confirmed), never an uncontained running child (CL-27). When nesting succeeds, the session's job is a child of the parent job and nothing here needs breakaway.

### 2.6 Test Routes and Fault Injection

Faults live in `windows::hooks`, compiled under `cfg(any(test, feature = "fake"))`, so no default-feature build contains them (PR2 D6). Unit tests set them on a `WindowsPty`; integration tests use `fake::windows_inject_next(fault)`, which applies to the next native spawn **on the calling thread** (a thread-local), so parallel tests cannot see each other's faults. Unit tests also have PR 3's stage hooks (PR3 `src/unix/tests.rs`): `Validated`, `LockAcquired { stage: 2 | 5 }` (inside the lock, before `CreatePseudoConsole` and before each `CreateProcessW`), and `Spawned { pid }` before stage 6. A per-thread **call trace** records, in order: each `CreatePseudoConsole` and `CreateProcessW` call with its creation flags, each attribute-list init and delete, `assign`, `resume`, the termination calls with their results, and the release calls of §2.2 and `SpawnedParts::teardown` (including a point right after the teardown's kill and one right before its close); each entry records `spawn_lock_held_here()` (§2.1).

```rust
pub enum WindowsFault {                    // fake feature, Windows
    FirstPipe, SecondPipe,                 // fail that pipe; SecondPipe: the first pipe exists
    CloseWorker,                           // fail CloseWorker::start: no pseudoconsole is created

    CreateProcess,                         // both attempts fail without calling CreateProcessW: 5.1 ERROR_NOT_SUPPORTED, 5.2 ERROR_NOT_ENOUGH_MEMORY
```

- **Real failures.** The `…TerminateDenied` faults call the real `TerminateProcess` or `TerminateJobObject` on a duplicate of the backend's handle made by `DuplicateHandle` without the terminate right, which fails `ERROR_ACCESS_DENIED`; the wait on the held handle then times out for real because the child stays suspended. `JobListAttr` makes the fallback run through the real suspended path. No fault makes a successful kill look unconfirmed. The faults that imply `RejectJobList(None)` force the 5.1 → 5.2 fallback themselves, since `windows_inject_next` takes one variant.
- **`windows_watch`** opens **one** handle with `PROCESS_QUERY_LIMITED_INFORMATION | SYNCHRONIZE`, reads the creation time on it, fails unless it equals `id.start_time`, and keeps that same handle for every later `signalled` call, so a watch can never observe a different process.
- **Gates.** A `Gate` is two `std::sync::mpsc` channels: the backend signals `reached` at the gate and waits on `open` for at most 10 s; the test waits for `reached`, checks what it needs, and opens. If `open` times out or its sender is dropped (a test assertion failed and unwound), the backend records `gate_abandoned` in the fault report and continues with the injected path, so a failed test can never strand a spawn. Tests that exercise a gated path (CL-5, CL-7) assert that the fault report has no `gate_abandoned`, so a timeout or disconnect never counts as the synchronized path. No test waits by sleeping.
- **Teardown hook.** `windows_on_teardown_kill` is thread-local and is armed on the **spawn thread before `spawn` is called**, since the teardown runs on that thread. The closure holds an `Arc` to the fixture coordinator's shared state: the coordinating thread puts the role watches there before opening the gate, and the closure reads each with a zero wait and writes the results back. The teardown point records `teardown_hook_ran` in the call trace, so a test can require that entry before the trace's `close` entry. Both teardown points in `backend.rs` compile under `cfg(all(windows, any(test, feature = "fake")))`, because testkit's integration tests link pty-runtime with `fake` and without `cfg(test)`.
- **Output marker and drain hold.** In test and `fake` builds, `out_r` is wrapped before `Drain::start` (which takes any reader, W12) by a reader in `windows::hooks` that searches what it reads for the armed marker, carrying the previous read's last `marker.len() − 1` bytes; `Drain` itself is unchanged. `AfterSpawn` waits, bounded by 10 s, until the wrapper has seen `marker` with the child still running; the wrapper then **holds**: its next read blocks until the teardown's close step begins (the trace point before close) or 10 s pass. While held, the fixture's later writes stay pending in the pipe and in conhost. Missing the marker is reported as "milestone not reached", never as the injected failure. A byte count would not do: conhost's startup bytes already satisfy any count (§2.3).
- **Close threads.** In test and `fake` builds each `CloseWorker` registers its `JoinHandle` when its close returns; `windows_close_threads_exited` waits on those threads' handles (`AsHandle`, W12) with `WaitForSingleObject` bounded by `timeout`, joins those that are signalled, and returns whether all were. Production code never joins the worker.
- `windows_in_job` reads a registry of live jobs keyed by leader pid (weak references, removed when the child drops), present only with `fake`.

### 2.7 The `unsafe` Carve-Out

**Endings.**

| Ending | What happens |
|---|---|
| Validation failure | `NeverStarted`, nothing created. |
| Stage 1 or 2.1 failure | Pipes (and nothing else) dropped; `NeverStarted { Setup }`, `Confirmed`. No pseudoconsole exists. |
| Stage 2.2 failure | Unarmed worker closed (it acknowledges and exits), pipes dropped; `NeverStarted { Setup }`, `Unresolved` if the worker did not acknowledge in time. |
| Stage 3 failure | Output read end dropped first, then the close through the worker, then the input; `NeverStarted { Setup }`, `Confirmed` only when the close returned, else `Unresolved`. |
| Stage 4, 5.1–5.3 failure | No process exists. `release_early`; `NeverStarted` with its kind and `Cleanup`. |
| 5.4 failure (assign, resume) | Termination of the suspended child (through the job once assigned), its exit awaited through its handle for 2 s: confirmed → `NeverStarted`; unconfirmed → `StartedThenFailed` with `Unresolved` and the identity. `release_early` in both cases. |
| Stage 6 failure, or later | `StartedThenFailed`; `SpawnedParts::teardown`: kill attempted (job), then input, close (worker), drain; `Unresolved` when the kill could not prove death. |
| Child exit | `wait_timeout` reports it on every call; descendants stay in the job; output continues; while conhost is healthy, no EOF before close. |
| `kill` | §2.5 within the deadline; I/O stays up. |
| `close` | PR2 §2.2: kill; input released (a blocked write ends when step 4 makes conhost go away); `ClosePseudoConsole` on the worker while the drain reads; drain to EOF; join. |
| `Session` drop | As close; the child's drop closes the job (kill-on-close for anything left) and the process handle. |
| conhost dies on its own | Output EOF, possibly before close; writes fail (`InputBroken`); the CLI, a console client, is terminated by the console's loss, which `wait_timeout` observes. |
| Reader `ERROR_BROKEN_PIPE` | `OutputEnd::Eof`. Any other read error: `OutputEnd::Error`. |
| Write error | Unit `Incomplete`, `InputBroken` (PR2 §2.3). |
| `ClosePseudoConsole` hang | The worker's `close` returns `None` at the deadline; `conpty-close` abandoned; the drain finishes at its bound or is abandoned. |
| Daemon crash between suspended create and assign | The suspended child survives outside any Chaldea job, unrecorded (PR 10, §2.2). |
| Panic | No panic path in this backend's code; a poisoned `kill` mutex is taken over. |

**Waits.** Every wait has a deadline except: acquiring `SPAWN_LOCK`; `CreatePseudoConsole` and `CreateProcessW` (synchronous, no handshake); the drain's `ReadFile` and the writer's `WriteFile` (both end when conhost closes its ends, which close step 4 causes); `ResizePseudoConsole` (unbounded by PR2 §2.1). Bounded: `wait_timeout` (zero is a poll; sub-millisecond rounds up; chunks continue); `kill_tree` (sleeps of `min(10 ms, deadline − now)`, handle waits floored to whole milliseconds and polled under 1 ms, no OS call started past the deadline; one in-flight call can overrun); `close` (the worker's close operation, against the caller's deadline; the thread is not joined); the suspended child's exit wait (2 s, without the lock); `release_early` and the teardown (2 s close, 2 s drain, 5 s kill); `AfterSpawn`'s milestone wait and every gate's `open` wait (10 s each, tests only); the Windows `double-forked` fixture's stdin wait (10 s).

**Timing.** No test synchronizes by sleeping. A test waits for a FakeCli hello or event (sent only once its mechanism is in place: the breakaway result, the parent's exit, an output line), `SessionEvent::Exited`, a stage hook, a gate, a pong, a handle's signal, or a `report-process` file after `Exited`, each bounded by 10 s; kill deadlines are 5 s with 500 ms of slack on real processes. Survival is proven by `ping` after `kill_tree` returned; death by a watch handle signalled, never by a stream's closing alone (a stream can also close by fixture timeout, a peer failure, or a later pseudoconsole close). Every event a test asserts is read before the fixture is killed, since Windows resets a killed process's socket and discards unread lines (PR3 §2.8 "Report channel"). Fault gates open on a milestone, so a fault never fires before the state it tests.

**Handle counts.** `pre_process_faults_leave_no_handle` and `after_process_faults_leave_no_handle` re-execute the `pty_windows` test binary with an environment variable naming the case (`--exact <test name>` selects the same test; the variable switches it into helper mode). The helper runs nothing else, so no other test thread opens handles; its FakeCli fixtures open no report stream (`report-process` or `sleeper` without `--report`), so it holds no sockets. Per fault, each cycle first asserts the fault's call trace (exactly the resources its stage acquired, each released; for a process fault, the leader's `fake::identify` is `None` afterwards), then waits for the cycle's close threads with `windows_close_threads_exited(10 s)` (a `false` fails the test), then samples `process_handle_count()`. One warm-up cycle gives the baseline; five measured cycles follow, and every sample, the first included, must equal the baseline; `None` fails the test. What the count can see is the daemon's own handle table (process, thread, job, pipe, and event handles); it cannot see an attribute-list heap block (the trace covers its delete), a process that holds no handle of the daemon (the exit checks cover the CLI), or conhost's own handles, which are outside the claim. The helper prints its result and exits; the outer test asserts exit 0.

**Leaks.** Every FakeCli runs with `--max-life-secs 60`; `Cleanup` kills by verified identity on any exit; a dropped `Session` closes the job, which kills its members.

## 8. Decisions

**D1. An own `windows-sys` backend with flags `0`, bound statically to `kernel32.dll`.** No search-path DLL can supply ConPTY (W1); the loaded module is recorded per launch and the binary's imports are checked.

**D2. The child is in a kill-on-close job before its first instruction, or it does not run.** Job list first; `CREATE_SUSPENDED` + assign + `ResumeThread == 1` second, once, on any failure of the job-list attribute or attempt, with both attempts' errors kept. A failure on the suspended branch terminates the child (through the job once assigned), and the held handle decides: `NeverStarted` when it signals, else `StartedThenFailed` with `Unresolved` and an identity read right after creation, with no retry owner. The branch, and the job-list error on the fallback, are evidence of every launch.

**D3. `CreatePseudoConsole` and each `CreateProcessW` call run under the process-wide spawn lock, proven by a guard type only that lock produces, and the backend creates nothing inheritable.** `CreatePseudoConsole` holds inheritable duplicates of conhost's pipe ends during the call (W3); everything else is non-inheritable from creation and the CLI is created with `bInheritHandles = FALSE`. Failure-path waits and releases run without the lock.

**D4. Death is proven from the job's own count and from held handles.** `ActiveProcesses == 0` in the call, the leader and held extras signalled, every supplied identity resolved, and no malformed entry; the job is terminated again while members remain; the pid list serves only the survivor report, collected within the deadline. The guarantee covers the job and verified `extra` identities; processes never in the job and outside-job descendants of an extra are outside it. Kill-on-close terminates; it never proves.

**D5. No breakaway.** The job sets only `KILL_ON_JOB_CLOSE`; a CLI's breakaway request fails, and a breakaway from an inner job stops at this one (W11). Reopen with evidence that a supported CLI needs breakaway, at the cost of a stated escape path.

**D6. Extras are per call: the caller passes its full list on every call, and only verified held handles persist.** Extras are trusted, launch-attributed input, opened by pid, verified by creation time on the same handle, and killed and waited for only through it; held handles keep their pids reserved and keep later calls from proving death while they live. An identity not resolved in a call is that call's survivor and is not kept. No terminate by pid alone; no Toolhelp; no busy handoff.

**D7. Output ends at close while conhost is healthy, and the pseudoconsole always has a closer.** conhost's pipe ends are closed in the host right after `CreatePseudoConsole`, `ReleasePseudoConsole` is not used, and the close worker is started before the pseudoconsole exists and runs `ClosePseudoConsole` against the caller's deadline while the drain reads; `Some` means the close returned, not that the thread was joined. If conhost dies first, EOF comes earlier.

**D8. Synchronous std pipes; `PipeWriter` is the input and `PipeReader` the drain's source.** Whole writes, `ERROR_BROKEN_PIPE` as EOF, nothing written on drop, no `unsafe`.

**D9. `unsafe` lives in `windows::sys`, the second and last allowance of the crate.**

**D10. Faults are injected through `cfg(test)` hooks and a `fake`-feature thread-local, and make the failing call fail for real where the path under test depends on it; leaks are judged by handle counts stable across cycles in a quiescent helper, by traces, and by handles that signal.** No fault path ships in a default build.

**D11. FakeCli uses `winapi-util` for console mode and size on Windows**, keeping testkit free of `unsafe` and the lock unchanged; new Windows facts arrive in opt-in modes, flags, and events, so PR 3's types and tests are unchanged.

**D12. `ProcessIdentity::group` on Windows, persisted as `launch_started.pgid_or_job`, is `job:<leader pid>` for job members and `""` for a process outside the job, including a suspended child whose assignment failed.** It is opaque display and diagnostic text: `launch_id` is the durable correlation, and no reader parses it as a reopenable job, a restart proof, or membership evidence. Rejected: an empty value (loses the containment fact in `launch_started` and survivor lists) and a named job (would let another process open the job, contradicting D3 and §4's restart reasoning). Once events are stored, readers accept the old values forever (append-only store, mvp §2.1).

No open questions remain.
