# Design: Hook Ingest (MVP PR 9)

Status: implemented in `crates/daemon/src/hook` and `crates/cli/src/hook_emit`. Scope is the PR 9 row of `docs/mvp-design.md` §4 (cited as "mvp §N"): `POST /hook`, binding, `raw_unknown`, `chaldea hook-emit`, and the B-8 cases (arch §5 open item **Windows hook receiver**). The contract implemented is mvp §2.1 (hook idempotency keys, `raw_unknown`), §2.5 (the `/hook` route, its rejections, deadline, and log rules), §2.9 (early hooks, binding, buffering), the PR 9 obligations of mvp §4, and the claims CL-10, CL-16, CL-17, CL-23 of mvp §6.2. mvp §4's PR 9 / 10 obligation (`extra` attribution) is handed to PR 10 entirely (§4, D10). It builds on the store of `docs/design/event-store.md` (cited as "store §N"), the HTTP surface of `docs/design/http-surface.md` (cited as "http §N"), and implements the `buffer*` and `bind` actions that `specs/thread_input.qnt` assumes (`docs/design/formal-specs.md`, cited as "formal §N").

**What PR 9 decides and what it leaves.** PR 9 owns everything between the `/hook` guard and the store: the request headers, the hook body budget, intake order, intake facts, and the binding order, the process-ancestry walk used for Codex binding eligibility, delivery deduplication, binding, session selection, buffering and promotion, `raw_unknown` reasons, and the emitter (`chaldea hook-emit`). It does not decide what a bound hook *means* (which events a `UserPromptSubmit`, `Stop`, or `PermissionRequest` produces, readiness evidence, ack attribution): that is a seam (`HookAdapter`, §2.6) filled by PR 10 (supervisor facts) and PR 13 / 14 (payload decoding). It records no process for `kill_tree`'s `extra`, and it does not launch CLIs, inject hooks, mint hook tokens, run timers, or recover at restart (PR 10, 13, 14); it names the functions those PRs call and the obligations they carry (§2.9, §4).

**Trust boundary.** Processes of the user's OS account are trusted already: they can read the owner token file and get owner access (mvp §2.5). Other OS accounts are outside the threat model (as in PR 8's design). Within that model:

- The **hook token is the authentication boundary for its launch.** Every process of the launch's tree inherits `CHALDEA_HOOK_TOKEN` and can post any hook for that launch, with any headers; it can never read or write another launch or thread (the token names one launch, §2.8).
- **Nested CLIs are separated per agent, for unintentional emissions only.** A nested CLI that inherits the environment and runs the unmodified `chaldea hook-emit` (spike B-11, prior-art row 6c) is kept from binding or feeding the launch: for Codex by the ancestry walk, when the nested CLI's own link, under a recognised CLI name (the agent name or the launched binary's name), lies between the emitter and the launch in the walk's kept prefix (§2.5); for Claude by the session id. Outside that, the separation fails in stated ways (§2.5 "Where Codex separation fails"): a nested CLI whose own link is absent or unrecognised can bind the launch to its session first, and a legitimate `SessionStart` whose walk ends below the launch leaves it unbound. A nested Claude that resumes the launch's own session id (`claude --resume <id>`) is indistinguishable from the launch's CLI and its hooks are taken as the launch's (§2.5 "Binding rule per agent"; D3). Neither check is a defence against a process that deliberately forges `X-Chaldea-*` headers or names another process's pid; such a process already holds the token.
- The ancestry walk is a **heuristic over current parents and pids** (§2.5). It decides one hook's Codex eligibility and nothing else: no kill, no `extra`, no other launch.

**Commitments from PR 6 and PR 7 this design keeps.**

1. One store job per delivery: deduplication on `(launch_id, emit_id)`, the routing decision, the events, binding, and promotion run in one `BEGIN IMMEDIATE` transaction (store §2.3 "Hook deliveries"). The store keeps buffered data opaque; PR 9 owns its format (§2.9).
2. The reply is sent only after the job's ticket resolved `Ok`, so a buffered hook is durable before 200 (store §2.9, D5).
3. `/hook` is a `Mount::write` route (http §2.2 route table, `crates/daemon/src/http/routes.rs:264-270`): Host, `Origin` absent, `hook` token, framing, and size are decided by PR 7's guard before the handler, and the deadline runs from the connection's first head byte (http §2.2 "One deadline origin"). PR 9 adds no check before the guard and changes none of its order.
4. Store outcomes map through PR 7's `run_write` / `write_failure` mapping (`crates/daemon/src/http/ctx.rs:145-229`, `error.rs:223-244`); PR 9 adds no status code.
5. `core` is unchanged: no public type, payload, kind, or reason is added. No hook body or token reaches a log (mvp §2.5 "Secrets"; http §2.10).

## 1. Goal and Dependencies

**Goal.** A `hook` module in `chaldea-daemon` that accepts a CLI hook on `POST /hook`, decides its routing (appended to the thread, buffered while its launch is unbound, or kept as `raw_unknown`) in one store job, binds a launch only through mvp §2.9's rule and never ahead of an earlier hook of the same launch, promotes buffered hooks in receipt order at binding, and replies only after the decision is durable; and `chaldea hook-emit`, which posts one hook payload with one `emit_id`, retries within its budget, and always exits 0 within 3 s with nothing on stdout. Every B-8 case is a table-driven test per layer on `macos-latest` and `windows-latest`.

**`crates/cli` dispatch.** `crates/cli` (shared with PR 8) builds the `chaldea` binary from a library whose `dispatch` runs `hook-emit` first, before any runtime or configuration initialization (mvp §3 "Single binary"), and a `main.rs` that only calls `dispatch` (§2.13).

## 2. Types and Functions

Names may change in review; shapes may not.

### 2.1 The Rules

1. **One job decides.** Deduplication, routing, binding, buffering, promotion, and buffer bounds are decided inside the delivery's store job, from what the database holds at that moment, with every target (thread, launch) derived from the token as re-verified in that job (§2.10). Everything before the job (header checks, body, ancestry walk, pid wait, binding order) gathers inputs and writes nothing.
2. **Memory holds only intake order.** `IntakeOrder` (§2.4) keeps, per launch, the next receipt ordinal (seeded from the stored maximum) and the set of ordinals taken but not yet submitted to the writer. Losing it at restart loses nothing: the stored maximum seeds it again, and no request outlives the process.
3. **Binding never overtakes an earlier hook.** A `SessionStart` that could bind waits until every lower receipt ordinal of its launch has been submitted to the writer or released (§2.4).
4. **Hook meaning is the adapter's.** PR 9 interprets a payload only as far as binding and session selection need: `hook_event_name`, `session_id`, and for `SessionStart` `transcript_path` (§2.5). Every other event of a selected session goes through `HookAdapter::interpret` (§2.6).
5. **Only the current, live, bound launch and its session change state.** A hook reaches `interpret` only when its launch is the thread's current launch, has a recorded pid and no exit, is bound, and the hook is of the bound session (rows 3–8 of §2.7). A buffered hook appends no event, feeds no reducer, and changes no projection (formal §3 hole d).
6. **Every wait has a deadline** (§5 "Waits"), and every ending of a request is listed (§5 "Endings").

### 2.2 Request Shape

The emitter's request (and the only shape the handler accepts past the guard):

```
POST /hook HTTP/1.1
Host: 127.0.0.1:<port>                 (or localhost:<port>, as in CHALDEA_HOOK_URL)
Connection: close
Authorization: Bearer chd_<43>          (CHALDEA_HOOK_TOKEN)
Content-Type: application/json
Content-Length: <n>                     (0 ≤ n ≤ 4 MiB)
X-Chaldea-Emit-Id: <uuid>               (public, mvp §2.1; required)
X-Chaldea-Attempt: <1|2|3>              (internal; the emitter's attempt number)
X-Chaldea-Emitter-Pid: <decimal pid>    (internal; the walk's starting pid)
X-Chaldea-Thread-Id: <uuid>             (internal; CHALDEA_THREAD_ID, when it is a hyphenated UUID)
X-Chaldea-Agent: <agent>                (internal; the emitter's argument when it is non-empty visible ASCII, recorded only)
X-Chaldea-Emitter-Version: <version>    (internal; recorded only)
X-Chaldea-Body-Truncated: 1             (internal; present only when stdin exceeded 4 MiB)
```

No `Origin` (403 otherwise, guard step 3). Header parsing (`request.rs`) runs after the guard and before the body:

- `X-Chaldea-Emit-Id` must occur once and parse as a hyphenated UUID, else 400 `bad_request`.
- Each other header of the list above may occur at most once; a second occurrence is 400 `bad_request`.
- Values outside their form are treated as absent: a pid that is not a decimal `u32` in `1..` (the chain is then empty), an attempt outside `1..=3` (then `None`, treated as a retry, §2.6), an empty agent or version (recorded as `unknown`). The agent and version are otherwise kept as sent, within the guard's 8 KiB head; they decide nothing.
- `X-Chaldea-*` headers not in the list are ignored, repeated or not (a newer emitter against an older daemon).

The internal headers are a protocol between two copies of the same binary (§8 D6). Their values are trusted only as far as the trust boundary allows: they steer which chain is walked and are never authority over another launch.

**Body cap.** 4 MiB (mvp §2.5): over it the guard answers 413 before the body. The emitter never sends more: a longer stdin is sent as its first 4 MiB with `X-Chaldea-Body-Truncated: 1` and is kept as `raw_unknown` `unparseable` with a truncation marker, never interpreted (§2.7 row 1; §8 D5).

**Body budget.** Before reading the body the handler takes `ceil(Content-Length / 1 KiB)` permits from one `Semaphore` of `body_budget / 1 KiB` permits (32 MiB), with `try_acquire_many_owned`; none free → 503 `busy`, nothing read. The permit moves with the body bytes into the delivery job's closure and is released when the writer drops the closure (after the job ran or expired), when a refused submission drops it on the submitting side, or when the request ends before its observer registers. The budget counts the raw request bodies held between their read and the end of their job, so a client that disconnects after submission still holds its permit until the writer is done with the body. Before the job only the discriminating fields are decoded (§2.3 step 3), so a waiting request holds its raw bytes and no parsed tree. The budget does not count the buffered bodies a binding or expiry job reads back (at most 8 MiB, one job at a time on the single writer), the parsed JSON of the running job's own body, or SQLite's internal copies.

**Reply.** Every recorded delivery answers `200` with an empty body (`Content-Length: 0`), the guard's `Cache-Control: no-store`, and PR 7's `Connection: close`; the stored first reply is `{ http_status: 200, body: "" }`. The disposition is observable in the thread stream and in `hook_deliveries`, not in the reply (§8 D7). Every other status is a rejection or an unknown outcome (§2.11).

| 5 | **Intake**: `IntakeOrder::intake(launch, stored_max, probe, now)` → an `IntakeTicket` with the ordinal, `seams.intake.facts(launch)`, and the intake instant on the server's clock (the pid wait's origin), in one critical section (§2.4) | non-blocking | — |
| 6 | **Ancestry walk** of the emitter pid in `spawn_blocking` (§2.5): the server's clock is checked against the deadline before the walk is submitted to the blocking pool (a passed deadline submits nothing), and the walk is awaited until the deadline | `max_chain` links; the deadline | the deadline passed, or not finished by it: 408 |
| 7 | **Pid wait**, only when the pre-read found no recorded pid and no exit (below) | `min(intake + pid_wait, deadline)` | the request deadline: 408; the 1 s side: passed to the job |
| 8 | **Binding order**, only for an untruncated body decoded as `SessionStart` whose launch was unbound at the pre-read: wait until `IntakeOrder` holds no lower ordinal of the launch (§2.4) | the deadline | 408, nothing written |
| 9 | **Delivery job** through `ctx.write_then(job, release)` (`not_after = deadline`): the job closure owns the body, the permit, the decoded fields, the chain, the facts, and `pid_wait_expired` (§2.7); `release` owns the `IntakeTicket` | the deadline + 100 ms reply grace | §2.11 rows J |
| 10 | Reply with the delivery's first reply | — | — |

**`WriteCtx::write_then(job, release)`** is `WriteCtx::write` with one addition: the observer drops `release` as soon as `Store::submit` returns, success or failure; the registry refusing the observer, or aborting it before its first poll (shutdown), drops it too. So the ticket is released exactly when its job is in the writer's queue (or will never be). Ownership passes from the request to the observer at registration: a client that disconnects after the observer is registered, even before it is first polled, no longer holds the ticket; the observer submits the job and releases it then.

**Pid wait (step 7).** Let `pid_deadline = min(intake + pid_wait, deadline)`. Subscribe to the store's commit notifications first (`WriteCtx::commits()`), then re-read the launch and thread rows, so a `launch_started` that committed between the pre-read and the subscription is seen. Each notification naming the thread's stream, and each `Lagged`, re-reads. Every re-read is `WriteCtx::read_by(pid_deadline, …)` (a read with `pid_deadline` in place of the request deadline, K3), whose cutoff is strict: a result is classified by the one clock sample taken when the wait returns it, and one taken at or after `pid_deadline` is 408 whatever it is (a failed join, or the reader pool's exhaustion, included), so a re-read still waiting for a reader at `pid_deadline`, or finishing at or after it, counts as not having seen a start, and one taken before it counts even when the task resumes later. `pid_wait` (`hook/mod.rs`) decides the order between re-reads; it keeps two properties: no re-read triggered by a notification is submitted after the clock sample taken on that wake-up is at or after `pid_deadline`, and its timer wins over a notification ready in the same poll. The wait ends, without a decision, when a re-read before `pid_deadline` shows a recorded pid, an exit, or a launch that is no longer the thread's current one, or when the notification channel closes (store shutdown). Reaching `pid_deadline` otherwise: if it is the 1 s side, `pid_wait_expired = true` goes into the job, which records `raw_unknown` `unbound` (row 6) even if `launch_started` commits between the wait's end and the job (past the bound the hook is `unbound`, mvp §2.9 "Early hooks", decided once); if it is the request deadline, the reply is 408 with nothing written.

Steps 1–8 write nothing. A request that ends before step 9 registers its observer (client disconnect, deadline, rejection) drops its ticket and permit, which releases its ordinal for the binding order (§2.4); its ordinal is a gap (store §2.3 allows gaps). After step 9 registers the observer, the job is submitted and runs to its end on PR 7's registered observer (http §2.3), whatever the client does.

### 2.4 Intake: Ordinal, Facts, and Binding Order

```rust
pub(crate) struct IntakeOrder { launches: std::sync::Mutex<HashMap<LaunchId, LaunchIntake>> }
struct LaunchIntake { next: u64, pending: BTreeSet<u64>, released: Arc<tokio::sync::Notify> }
pub(crate) struct IntakeTicket { launch: LaunchId, ordinal: u64, order: Arc<IntakeOrder> }   // Drop: remove from pending, notify_waiters
impl IntakeOrder {
    /// The next ordinal (an absent entry starts at stored_max + 1), the probe's facts, and the intake instant
    /// from `now` (the server's clock, sampled under the lock: the pid wait's origin), in one critical section.
    pub(crate) fn intake(self: &Arc<Self>, l: LaunchId, stored_max: u64, probe: &dyn IntakeProbe,
        now: impl FnOnce() -> Instant) -> (IntakeTicket, Option<IntakeFacts>, Instant);
    /// Resolves once no ordinal lower than `t`'s is pending for its launch.
    pub(crate) async fn earlier_released(&self, t: &IntakeTicket);
}
pub trait IntakeProbe: Send + Sync + 'static {
    /// The facts PR 10 needs at a hook's intake (the PTY writer's position, dispatched writes), or None
    /// (no session yet). Non-blocking: it runs under the intake mutex.
    fn facts(&self, launch: LaunchId) -> Option<IntakeFacts>;
}
#[derive(Clone, Serialize, Deserialize)] pub struct IntakeFacts(pub serde_json::Value);   // opaque to PR 9
```

**Intake** is the instant step 5 runs: the request is complete, authenticated, and its launch known. The ordinal, the facts, and the intake instant are taken in one critical section, so receipt order, the order of intake facts, and the pid wait's start agree: time a request spends before intake never shortens its pid wait.

**Ordinals across restarts.** An absent entry starts at `max(receipt_ordinal) + 1` of the launch's stored deliveries (`ReadTx::max_receipt_ordinal`, read in the pre-read), so a hook token that is still valid after a restart (a launch that had exited before it, whose token PR 10's restart revocation does not reach) never reuses an ordinal (`UNIQUE (launch_id, receipt_ordinal)`, store §2.4). Two concurrent first requests both read the same maximum; the first creates the entry and the second takes the next value from it. Within a run, every ordinal of a launch comes from its entry, which is never removed.

**Binding order** (rule 3). `pending` holds every ordinal whose ticket is alive. A ticket dies when the request ends before its observer registers (disconnect, deadline, rejection), or when `Store::submit` for its job returns (`write_then`, §2.3). A `SessionStart` of a launch that was unbound at the pre-read awaits `earlier_released` before step 9. `earlier_released` loops: it creates the `Notified` future of `released` and pins it (in `tokio 1.54.1` a `Notified` observes `notify_waiters` from its creation; `enable()` is called as well, so the guarantee does not rest on that detail); only then locks the mutex and checks `pending` for a lower ordinal; none → return; else unlock and await the future. A ticket dropped between the check and the await wakes it, so no release is missed. Creating the future after the check is the bug this order prevents. Because a returned `Store::submit` puts the job ahead of every later submission in the writer's FIFO queue (K12), every lower-ordinal job has then either been queued ahead of the binding job or will never run. So:

- a hook received before the binding `SessionStart` is buffered (or decided otherwise) before binding, and promoted in receipt order with it: `SessionBound → PromptSubmitted → Stop`, never `SessionBound → Stop → PromptSubmitted` (K10);
- of two eligible `SessionStart`s of different sessions, the one received first binds; the later one finds the launch bound and is `foreign_session` (§2.7 row 7);
- a lower request stuck in its walk or pid wait delays the binding by at most its own deadline; a lower request that ends early releases its ordinal at once; a lower job already queued releases its ordinal at submission, so a writer stalled on another job delays the binding job only inside the queue, where the binding job's own `not_after` bounds it. A `SessionStart` whose own deadline passes while waiting answers 408 with nothing written, and the emitter retries (§2.13).
- A lower job that is queued but then expires or rolls back records nothing; its retry is a new delivery with a higher ordinal, which does not hold the binding back. It is decided after the binding when the binding job was queued first (bound: row 8, marked as a retry, §2.6), or buffered and promoted with the binding when it is queued first; both orders follow the writer's queue.

The wait never cycles: a `SessionStart` waits only for lower ordinals, and only `SessionStart`s wait.

**What intake order means for bound launches.** Deliveries appended directly while bound appear in the stream in commit order; their intake facts, not their stream order, are what ack attribution uses (mvp §2.3 "Ack"). A first attempt that recorded nothing leaves its retry as the delivery, with the retry's ordinal and facts, marked as a retry (§2.6).

Default probe (`HookSeams::mvp()`): returns `None`. PR 10 supplies the real one.

### 2.5 Process Lookup, the Ancestry Walk, and Binding Rules

**Process lookup** (`pty_runtime::process`, public; PR3 D7's public lookup):

```rust
pub struct ProcessEntry { pub identity: ProcessIdentity, pub ppid: u32, pub name: String }
pub enum Lookup { Live(ProcessEntry), Gone, Unreadable }
pub fn lookup(pid: u32) -> Lookup;
pub struct Ancestry { pub links: Vec<ProcessEntry>, pub end: AncestryEnd }   // links[0] is `pid` itself
pub enum AncestryEnd { Root, Limit, Gone(u32), Unreadable(u32), ParentNewer(u32) }
pub fn ancestry(pid: u32, max: usize) -> Ancestry;
```

- `identity` uses the backend's identity format (K7), produced by the same functions as `launch_started`'s identity, so `(pid, start_time)` compares equal with it. `identity.group` is display only (macOS pgid; empty on Windows); comparisons use `(pid, start_time)` only, never `ProcessIdentity`'s derived equality.
- `name`: the image name, ASCII-lowercased, a trailing `.exe` removed. macOS: `pbi_name` (at most 31 characters), else `pbi_comm` (at most 15), from the same `proc_pidinfo` call; Windows: `szExeFile` of the Toolhelp entry. Names are compared only with names from the same function on the same host, so truncation applies equally to both sides.
- `Lookup`, macOS: `proc_pidinfo`; a zombie (`unix::table::Lookup::Zombie`) is `Gone`; a refused read is `Unreadable`. Windows: `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION | SYNCHRONIZE)`: `ERROR_INVALID_PARAMETER` (no such pid) is `Gone`, any other failure (access denied) is `Unreadable`; then the existing `windows::sys::wait(h, 0)`: `Ok(true)` (signalled: exited, even while a handle keeps its object) is `Gone`, `Ok(false)` is live, `Err` (`WAIT_FAILED` or any other return) is `Unreadable`; the creation time is read from the same handle.

**The walk.** `ancestry` reads `links[0] = lookup(pid)` (not live: an empty chain ending `Gone(pid)` / `Unreadable(pid)`; `max = 0`: an empty chain ending `Limit`), then repeatedly follows the last link's `ppid`, checked in this order: `0` or the link's own pid ends with `Root`; `max` links read ends with `Limit` (no lookup past it); a parent lookup of `Gone` or `Unreadable` ends with `Gone(ppid)` / `Unreadable(ppid)`; a live parent whose `start_time` is later than its child's ends with `ParentNewer(ppid)` (a parent pid that a later process took, K13; equal stamps pass, and a stamp that does not parse as a decimal integer fails closed as newer); otherwise the parent is pushed. The walk keeps every link read before its end. On Windows, one Toolhelp snapshot supplies every `ppid` and `szExeFile`, and the handle of each link is opened, checked, and closed in turn; a pid absent from the snapshot is `Gone` (its process exited before the snapshot; a process holding the pid now was created after it), and a failed snapshot makes every lookup `Unreadable`. The system time is read just before the snapshot; a handle whose creation time is later belongs to a process created after the snapshot, which took the pid after the row's process exited, so the row and the handle are two processes and the lookup is `Unreadable` (the walk fails closed). Both stamps are system time, so a clock step can refuse a live process or let such a reuse through, as for the start-time check below, and a reuse within the clock's resolution of the snapshot is not seen. Ancestors above the daemon (system and session processes) routinely refuse `OpenProcess`, so a Windows walk usually ends with `Unreadable` above the launch, its prefix intact. `lookup(pid)` on Windows takes its own snapshot. The decision logic is one platform-independent walker over a `Table` trait, unit-tested on every OS with synthetic tables, and the Windows table's decisions run over an OS seam (`WinOs`: open, wait, creation time) that a scripted one replaces in unit tests on every OS; `unsafe` stays in `unix::sys` and `windows::sys` (`docs/design/pty-unix.md` §2.7).

**What the walk is.** A heuristic over current parents and pids, read once (K13): a debugger attached to a process, a reparenting, or a reused parent pid whose new process is older than the child can make a link name a process that did not create the child. A system clock stepped back cuts both ways: between a creator's exit and the reuse of its pid it can let a later process pass the start-time check, and between the launch's start and its child's start it makes the real parent look newer (`ParentNewer`), ending the walk below the launch. Its only use is Codex eligibility (below), under the trust boundary; a wrong result misclassifies hooks of the launch (selected or `foreign_session`, including which session binds, below) and nothing else. It never feeds `extra` or a kill (D10).

**Eligibility** (`hook/ancestry.rs`, pure; decided in the job against the launch row). Let `L` be the launch's recorded `(pid, start_time)` from `launch_started`, and `emitter_name` the normalized image name of the emitter binary (`chaldea`, `HookConfig::emitter_name`). A chain is *eligible* for `L` when:

1. `links[0].name` equals `emitter_name` (the request's pid names a process running the emitter binary);
2. some link `k ≥ 1` of the kept links has `(pid, start_time)` equal to `L`;
3. the CLI names are `{ agent name ("claude" / "codex"), links[k].name }`; and
4. the nearest link `j ≥ 1` whose name is in the CLI names is `k`.

It fails closed: a walk that ended (`ParentNewer`, `Gone`, `Unreadable`, `Limit`) before reaching `L` is not eligible; a walk that ended above `L` is judged on its kept prefix, which contains `L`. A nested CLI inheriting the environment puts its own process (same image) between the emitter and `L`, so rule 4 fails (B-11; K9). An empty chain (no pid header, or link 0 not readable) is never eligible. The chain is walked at intake while the emitter is still waiting for its reply, so its links are current.

**Binding rule per agent** (`HookAdapter::rule`, §2.6; mvp §2.7 "Session binding", §2.9):

| Agent | `SessionStart` of an unbound launch binds when | A later hook of the bound launch is selected when | Expected session |
|---|---|---|---|
| Claude | `session_id` equals the expected session | `session_id` equals the bound session | `HookAdapter::expected_session` (§2.6) |
| Codex | the chain is eligible | `session_id` equals the bound session **and** the chain is eligible | — (the first eligible `SessionStart`, in receipt order, names it) |

**Where Codex separation fails.** Separation by the walk holds when the nested CLI's own link, under a recognised CLI name (the agent name or `links[k].name`), lies between the emitter and `L` in the kept prefix; rule 4 then makes that link, not `L`, the nearest CLI link. Two failure modes remain:

- *The nested CLI's own link is missing or unrecognised.* A nested copy under another image name (a renamed or versioned binary), or one whose link is absent from the kept prefix (its parent pid read as another process, K13), can leave `L` as the nearest recognised CLI link; its `SessionStart` is then eligible when the kept prefix reaches `L` and no other recognised CLI link lies between the emitter and `L` (rules 2 and 4). If it is received first, it binds the launch to the nested session, and every hook of the launch's real session is then `foreign_session` (row 7). Recovery is a fresh launch, not `resume` (which would pass the bound, wrong session); PR 13 / 14's session-switch decision (D2) covers it if they rebind.
- *The legitimate walk ends below `L`.* A `SessionStart` whose walk ends before `L` (`Limit`, `Unreadable`, `ParentNewer`, a clock step back included) is `foreign_session` (row 11), stored and answered 200, so the emitter does not retry; the launch stays unbound until another eligible `SessionStart`. PR 10's `session_start_timeout` attention reports the unbound launch, and recovery is a fresh launch.

A `raw_unknown` `foreign_session` whose raw body is a `SessionStart` is an observation of contention, not of a failure: an ordinary nested CLI that is correctly rejected leaves the same event. PR 9 promises no attention from it (§4 PR 14).

Both rows also require `X-Chaldea-Thread-Id` equal to the token's thread. Claude binds by its predetermined `--session-id` (mvp §2.9; spike §4.3) and keeps that check; its chain is not used (§8 D3). For Claude, a nested CLI that starts its own session sends another session id and is `foreign_session`; a nested CLI that resumes the launch's session id with the unmodified emitter sends the bound id and is selected as the launch's own (tested as such, PR9-CL-7). PR 13 decides whether Claude also requires the chain (D3).

### 2.6 The Adapter Seam

```rust

    fn rule(&self, agent: Agent) -> BindingRule;                                      // SessionId | Ancestry
    /// Claude's predetermined session id for this launch, from stored facts only.
    fn expected_session(&self, tx: &ReadTx<'_>, launch: &LaunchRow) -> Result<Option<String>, StoreError>;
    /// Events for one selected hook of the current, live, bound launch, decided inside the delivery or binding job.
    fn interpret(&self, tx: &ReadTx<'_>, hook: &AcceptedHook<'_>) -> Result<Interpretation, StoreError>;
}
pub enum Interpretation { Events(Vec<HookEvent>), Raw(RawUnknownReason) }       // Events non-empty
pub struct HookEvent { pub event: TypedEvent, pub name: &'static str, pub annex: Option<EventAnnex>, pub blobs: Vec<BlobInput> }
pub struct AcceptedHook<'a> {
    pub thread: ThreadId, pub launch: &'a LaunchRow, pub emit_id: Uuid, pub receipt_ordinal: u64,
    pub event_name: &'a str, pub session_id: &'a str, pub json: &'a serde_json::Value, pub body: &'a [u8],
    pub intake: Option<&'a IntakeFacts>,
    pub attempt: Option<u8>,            // X-Chaldea-Attempt; None when absent or invalid
    pub intake_reliable: bool,          // attempt == Some(1): the facts were taken when the CLI's first request arrived
    pub binding_ordinal: u64,           // the receipt ordinal of the SessionStart that bound the launch
    pub promoted: bool,                 // true: applied from the buffer in the binding job
}
pub struct HookSeams { pub adapter: Arc<dyn HookAdapter>, pub intake: Arc<dyn IntakeProbe>, pub procs: Arc<dyn ProcessProbe> }
pub trait ProcessProbe: Send + Sync + 'static { fn chain(&self, emitter_pid: u32, max: usize) -> Ancestry; }  // blocking
```

- `interpret` is called only under rule 5 of §2.1. `interpret` and `expected_session` run on the writer thread inside the job: data only, non-blocking, no network, PTY, supervisor, or channel handle (http commitment 5). They read through the job's `ReadTx`, which sees the job's earlier appends: in the binding job, `session_bound` and its status events are already applied when `interpret` runs, and a promoted hook sees the events of the hooks promoted before it. Effects on the supervisor travel through the store's commit notifications. `json` is the body expanded into a `serde_json::Value` inside the job (§2.7 step 4); a body the light decoder accepted can still fail to expand (a lone surrogate escape such as `\uD800` in a skipped string), and such a hook is row 1, never passed to `interpret`.
- **Retries** (`attempt`, `intake_reliable`). A delivery recorded by a retry carries the retry's intake facts, which were taken after the CLI fired the hook and can include writes that came later (e.g. an input dispatched in between). `intake_reliable: false` tells PR 10 to treat the hook conservatively: it acks no input and is no readiness evidence (mvp §2.3: ambiguity leaves the gate closed or the input `unconfirmed`). A first attempt that committed is replayed by the dedup and never interpreted twice. **Limit:** `intake_reliable: true` and the intake facts say nothing about which submission a hook belongs to. The receiver cannot bound how old a hook is at intake: the CLI can fire a hook before its emitter is scheduled, the emitter's work budget starts at its own `main`, a first attempt's write can complete late (§2.13 "Scheduling limits"), and the daemon takes intake after the body and the pre-read. A first attempt is recorded with `intake_reliable: true` and the facts of its intake, which can include a later dispatch; with Claude's `UserPromptSubmit`, whose payload is the prompt text, a hook for an earlier submission of identical text can then look like the ack of that dispatch. PR 10 carries the resulting obligation (§4).
- **`binding_ordinal`** lets PR 10 tell a `Stop` received before the binding `SessionStart` from one received after it (formal §3, `trace_buffered_stop_after_session_start`). It is the `receipt_ordinal` of the delivery whose primary event is the launch's `session_bound`, the same for promoted hooks and for every later direct delivery of the launch.
- PR 9 builds the envelope for each `HookEvent`: stream `thread:<thread>`, `thread_id`, `launch_id`, `command_id: null`, source `{ kind: hook, agent: launch.agent, cli_version: launch.cli_version, transcript: null }`, `occurred_at: None`. Keys: the first event of a delivery `hook:<emit_id>` (mvp §2.1); every further one `derived:hook:<emit_id>:<name>` (mvp §2.1 "Derived event"). **Reserved names:** `bind_status:<i>` and `binding_raw`, used by the binding job (§2.7); a `HookEvent.name` starting with `bind` is refused by PR 9 before any append (the job rolls back, 500), and so is a name repeated within one delivery (`KeyConflict`). Both are adapter bugs, caught by the adapter's own tests.
- `Interpretation::Raw(r)` stores the hook as `raw_unknown` with reason `r`.
- **`MvpHooks`** (the default in `HookSeams::mvp()` until PR 10 / 13 / 14 replace it): `rule` as in §2.5; `expected_session` = the thread's bound `session_id` when the thread has one (a resume passes `--resume <it>`), else the launch id in lowercase hyphenated form (a fresh launch passes `--session-id <launch_id>`); `interpret` = `Raw(UnknownEvent)` for every hook (no decoder exists before PR 13 / 14). The obligations this puts on PR 10 / 13 are in §4.

### 2.7 The Delivery Job

`route.rs` builds one closure capturing only data: the parsed headers, the body bytes and their permit, the decoded fields, the chain, the intake facts, `pid_wait_expired`, `Arc<dyn HookAdapter>`, and `HookConfig`. It runs inside `ctx.write_then`, which first re-verifies the token in the job's transaction (§2.8). Every target below (the thread, the launch, `L`) is the re-verified token's, never a value from the pre-read.

1. **Dedup.** `tx.read().hook_delivery(launch, emit_id)`: present → return its first reply; nothing else runs.
2. **`emit_id` reuse.** A delivery of another launch of the thread holds `emit_id` (`tx.read().hook_emit_in_thread(thread, emit_id)`, buffered deliveries included, which have no event yet), or `tx.read().event_by_key(thread stream, hook:<emit_id>)` is present → refuse with 400 `bad_request`, nothing stored. Either can only be another launch's, since this launch's delivery would have matched step 1; checking the buffered rows keeps their later promotion from meeting the key taken by another launch. The key contract stays `hook:<emit_id>` per stream (mvp §2.1). Retries of one emitter use one token and so one launch, where step 1 answers first; only a forged or broken request, or a v4 UUID collision, meets this.
3. **Expire** (only while the launch is unbound). `buffer::expire(tx, launch, cfg)` (§2.9).
4. **Expand and decide.** For a body `payload::decode` returned as `Hook`, expand it into a `serde_json::Value` (`D.json`); a failure is row 1. Then decide the routing by the table below, first matching row. The binding hook's expansion is therefore settled before `session_bound` is appended, and an unexpandable hook is never buffered.
5. **Record**: `tx.hook_delivery_record(NewHookDelivery { launch, emit_id, receipt_ordinal, first_reply: 200 "", routing })`.
6. **Bind** (row 9 only), after step 5 in the same transaction: re-read the launch and thread (now bound); call `interpret` for this `SessionStart` with `promoted: false` and append its events with `tx.append` (`Raw(r)` → a `raw_unknown` of this body with reason `r`, key `derived:hook:<emit_id>:binding_raw`, so the binding hook's payload is kept as a public event); then `tx.read().buffered_deliveries(launch)` in receipt order, each decided by the promotion table and passed to `hook_delivery_promote` in that order. Any error in step 6 rolls back the whole job, binding included.
7. Return the first reply.

`D` is the decoded payload; `L` the launch row (and its recorded identity); `T` the thread row.

| # | Condition | Routing |
|---|---|---|
| 1 | `X-Chaldea-Body-Truncated` present, or `D` is not JSON (invalid JSON or invalid UTF-8), or its expansion failed (step 4) | `raw_unknown` `unparseable` (truncated: with `EventAnnex::Hook { truncated: true }`, §8 D5) |
| 2 | `D` is JSON but not an object with a non-empty string `hook_event_name` and a non-empty string `session_id`; or a `SessionStart` whose `transcript_path` is present and neither a string nor `null` | `raw_unknown` `schema_mismatch` |
| 3 | `L` is not `T.current_launch_id` | `raw_unknown` `unbound` |
| 4 | `X-Chaldea-Thread-Id` absent or not the token's thread | `raw_unknown` `foreign_session` |
| 5 | `L` has exited (`exit_reason` set), bound or not | `raw_unknown` `unbound` |
| 6 | `L` has no recorded pid, or `pid_wait_expired` | `raw_unknown` `unbound` |
| 7 | `L` bound to session `S`: `D.session_id ≠ S` (a conflicting `SessionStart` included, §8 D2), or the rule is `Ancestry` and the chain is not eligible | `raw_unknown` `foreign_session` |
| 8 | `L` bound: otherwise | `interpret` → `appended` (its events) or `raw_unknown` (its reason) |
| 9 | `L` unbound, `SessionStart`, the rule's condition (§2.5) holds, and `reduce(T.state, SessionBound)` accepts | **bind**: `appended` with `session_bound { launch_id, session_id, transcript_path }` and one `status_changed` per `StatusChanged` the reducer returned (keys `derived:hook:<emit_id>:bind_status:<i>`); then step 6 |
| 10 | `L` unbound, `SessionStart`, the rule's condition holds, `reduce` refuses | `raw_unknown` `unbound` |
| 11 | `L` unbound, `SessionStart`, otherwise | `raw_unknown` `foreign_session` |
| 12 | `L` unbound, any other event, selected for the launch (Claude: `session_id` equals the expected session; Codex: the chain is eligible) | `buffered` if the bounds hold after adding it (§2.9), else **overflow**: this delivery and every buffered delivery of `L` become `raw_unknown` `unbound` in receipt order (the buffered ones received before it, then this one, then those received after it) |
| 13 | `L` unbound, any other event, otherwise | `raw_unknown` `foreign_session` |

**Promotion table** (step 6, each buffered delivery `B` read back with its meta, §2.9; the launch is current, live, and just bound to `S`):

| Condition | Promotion |
|---|---|
| `B.body` does not expand into a `Value`, or `B.meta` does not parse (only a bug or a direct store write can cause either, since step 4 refuses to buffer them) | `RawUnknown` `unparseable` (body) / `schema_mismatch` (meta), this delivery alone; the binding and the other promotions go on |
| `B.session_id ≠ S`, or its thread header is not the token's thread, or (rule `Ancestry`) its stored chain is not eligible for `L` — the ancestry evaluated at receipt, checked again against `L` here (mvp §2.9) | `RawUnknown` `foreign_session` |
| otherwise | `interpret` with `promoted: true`, `binding_ordinal` = this binding's ordinal, and `B`'s stored intake facts and attempt → `Appended(events)` or `RawUnknown(reason)` |

**`raw_unknown` of a hook**: stream `thread:<thread>` (the token names the thread, so a hook is never "unbound to a thread" in mvp §2.1's stream rule), `launch_id` = the token's launch, key `hook:<emit_id>` (or the reserved `binding_raw` name above), payload `{ source: hook, reason, agent: launch.agent, cli_version: launch.cli_version, content_type: "application/json" when row 1 did not apply else "application/octet-stream", raw: prepare_content(body) }`. The raw bytes are the request body exactly (`Content` inline UTF-8, base64 for invalid UTF-8, a blob above 64 KiB; store §2.5).

**Why the rows are in this order.** Rows 1–2 keep anything PR 9 cannot read as a hook, before any session logic. Rows 3, 5, 6 enforce rule 5 of §2.1: a superseded launch, an exited launch, and a launch with no pid (or whose wait ran out) change no state. Rows 4, 7, 11–13 are session selection: a hook of another session never reaches `interpret` (the Quint model takes in only hooks of the selected session, formal §1). Row 9 is the only place a launch binds.

**Hooks after exit, and late acks.** Every hook whose job runs after `launch_exited` committed is kept verbatim as `raw_unknown` `unbound` (row 5), even if it is of the bound session and was fired before the exit. A `UserPromptSubmit` delayed past the exit therefore acks nothing: the exit already moved the launch's `sending` / `sent` inputs to `unconfirmed` (mvp §2.3), and a human settles them with `chaldea input resolve`. While the launch is alive, every selected hook reaches `interpret`, and a late `UserPromptSubmit` is judged by mvp §2.3's attribution rules whatever made the input `unconfirmed` (the window expired, the write outcome was unknown); a late attributable ack moves it to `acked` (`thread_input.qnt` ack actions). A launch that exits before binding has its buffer resolved by `resolve_unbindable` in the exit job (§2.9), and a `SessionStart` arriving afterwards is row 5; a launch that binds before exiting has its buffer promoted once, in the binding job, and the promotion trigger (store §2.4: `buffered → terminal` once) keeps a later `resolve_unbindable` from touching it.

### 2.8 Token Check

`verify_hash_in` (http §2.4) gains, for kind `hook`: the token has both `thread_id` and `launch_id`, the launch exists, and its thread is the token's thread; otherwise `Invalid` (401). The launch need not be current, running, or bound: late hooks are kept (rows 3, 5, 6), and revocation (PR 10 at restart, §2.11 close) ends a token. The guard's step-4 lookup, the pre-read, and the job each run it, and the job's result is the one every target is derived from, so a revocation committed after the pre-read refuses the job with 401 and nothing changes (row J4).

### 2.9 Buffer

A launch's buffer is its deliveries with routing `buffered`; nothing else holds it.

```rust
pub struct HookConfig {
    pub emitter_name: String,        // "chaldea": links[0] must run the emitter binary
    pub pid_wait: Duration,          // 1 s: early hooks wait this long, inside the deadline, for launch_started
    pub max_chain: usize,            // 16 links walked from the emitter
    pub buffer_max_count: usize,     // 32 buffered deliveries per launch
    pub buffer_max_bytes: u64,       // 8 MiB of buffered bodies per launch
    pub buffer_ttl: Duration,        // 30 s from the earliest received_at of the buffered deliveries
    pub body_budget: u64,            // 32 MiB of hook bodies held from read to job end (§2.2)
}
pub fn expire(tx: &mut WriteTx<'_>, launch: LaunchId, cfg: &HookConfig) -> Result<usize, StoreError>;
pub fn resolve_unbindable(tx: &mut WriteTx<'_>, launch: LaunchId) -> Result<usize, StoreError>;
impl ReadTx<'_> {
    pub fn buffered_summary(&self, l: LaunchId) -> Result<BufferedSummary, StoreError>;   // count, body bytes, MIN(received_at); no bodies read
    pub fn max_receipt_ordinal(&self, l: LaunchId) -> Result<u64, StoreError>;           // 0 when none
    pub fn binding_receipt_ordinal(&self, t: ThreadId, l: LaunchId) -> Result<Option<u64>, StoreError>;  // the latest binding delivery's ordinal
    pub fn hook_emit_in_thread(&self, t: ThreadId, emit: Uuid) -> Result<bool, StoreError>;  // a delivery of any launch of `t` took `emit`
}
```

- **Meta** (`BufferedHook.meta`, JSON, version 1): `{ "v": 1, "thread_header", "agent_header", "emitter_version", "attempt", "chain": [{ "pid", "start_time", "name" }], "chain_end", "intake": <IntakeFacts> }`, `intake` present exactly when the probe returned facts (any JSON value, `null` included) and absent for `None`; `BufferedHook.body` is the request body. A meta that does not parse, or a body that does not expand, at promotion is promoted alone as raw (promotion table); it never rolls back the binding.
- **Bounds**, checked in the job that would add a delivery, from `buffered_summary`: the count after adding ≤ 32 and the summed body bytes after adding ≤ 8 MiB; otherwise overflow (row 12).
- **Time.** A delivery's `received_at` is its record job's `recorded_at`: the store clock read after the writer took the write lock (K4). `expire` reads `buffered_summary` (no bodies) and, when the running job's `recorded_at` minus `MIN(received_at)` exceeds `buffer_ttl`, promotes every buffered delivery of the launch to `raw_unknown` `unbound` in receipt order. The earliest stamp, not the first in receipt order, is the oldest, since jobs record in commit order. Both stamps are the store clock's fixed format `YYYY-MM-DDTHH:MM:SS.mmmZ` (`core::ids::Timestamp`), parsed by `buffer.rs` itself into milliseconds since the epoch (the daemon has no date crate); a negative age (the clock stepped back) or an unparsable stamp does not expire. `expire` runs at the start of every delivery job of an unbound launch (step 3; a bound launch has no buffer, so it is skipped) and in PR 10's timer tick. **While PR 9 ships without PR 10, an idle buffer expires only when the next hook of its launch arrives**; launches exist only through PR 10's supervisor, so no production launch is affected before then.
- **Launch that can no longer bind.** `resolve_unbindable` promotes every buffered delivery of the launch to `raw_unknown` `unbound`. PR 10 calls it in the job that appends `launch_exited`, and at restart for each of `buffered_launches()` before serving (mvp §2.9; formal `restart`). Row 5 covers a hook arriving after that.
- After an overflow or expiry the buffer is empty and later unbound hooks buffer again; if the launch then binds, only those are promoted. The earlier ones stay `raw_unknown`, visible, never applied out of order.

### 2.12 Store Additions

**Migration v2** (`MIGRATIONS[1]` in `store/schema.rs`) adds one trigger and nothing else:

```sql
CREATE TRIGGER events_session_bound_once BEFORE INSERT ON events WHEN NEW.kind = 'session_bound' BEGIN
  SELECT RAISE(ROLLBACK, 'events_session_bound_once: a binding without a launch, a second binding, or a binding of another launch')
  WHERE NEW.launch_id IS NULL
     OR EXISTS (SELECT 1 FROM events WHERE stream_id = NEW.stream_id AND kind = 'session_bound' AND launch_id IS NEW.launch_id)
     OR NEW.launch_id IS NOT (SELECT launch_id FROM events WHERE stream_id = NEW.stream_id AND kind = 'launch_reserved'
                              ORDER BY seq DESC LIMIT 1);
END;
```

- **Why the trigger.** One binding per launch, only for the stream's current launch, is an invariant SQLite can express, so it is a trigger (store §2.1 rule 1: "SQLite is the proof, Rust is the second line"); row 7 is the Rust check that returns the typed outcome first. It reads `events` only, so it holds while projections are dropped, and its `NEW.launch_id IS NULL` clause keeps a `NULL` operand from passing (store S10). If PR 13 / 14 adopt rebinding (§8 D2), a later migration drops it. The migration's schema fingerprint is added to `schema.rs`.
- **`EventAnnex::Hook { truncated: bool }`**, accepted only on a `raw_unknown` whose source kind is `hook` (row 1); the annex column needs no DDL change. Internal, like every annex; it is not in the public `EventEnvelope`.
- **Reads**: `buffered_summary` and `max_receipt_ordinal` (§2.9), and `binding_receipt_ordinal`, the `receipt_ordinal` of the delivery whose routed event is the launch's latest `session_bound` by stream sequence (`None`, passed as 0, when that event came from no hook delivery), searched within the token thread's stream through `events_kind` and then looked up by the launch's delivery key, so the lookup inside a direct hook's job reads no other thread's events (the `binding_ordinal` a direct delivery after the binding passes to `interpret`, §2.6), and `hook_emit_in_thread` (§2.7 step 2), over `hook_deliveries`' and `events`' existing columns and keys.

### 2.13 The Emitter: `chaldea hook-emit <agent>`

**Dispatch.** `crates/cli` is a library and a binary: `main.rs` is one call, `chaldea_cli::dispatch(args, Stall::Off)`. `dispatch` compares `argv[1]` with `hook-emit` before any runtime, logging, or configuration initialization and calls `hook_emit::main(argv, stall)`, which starts the watchdog before anything else and never returns (mvp §3 "Single binary"). The command form is fixed: `<absolute path to chaldea> hook-emit <agent>`, nothing else, because Codex hashes the command string into its hook trust (arch §5; §8 D1).

**Environment** (mvp §2.5 "Token kinds"): `CHALDEA_HOOK_URL` (exactly `http://127.0.0.1:<port>/hook` or `http://localhost:<port>/hook`, port 1–65535 with no leading zero; the spike's `parse_local_url` rules, K8), `CHALDEA_HOOK_TOKEN` (`chd_` + 43 base64url characters), `CHALDEA_THREAD_ID` (sent as `X-Chaldea-Thread-Id` when it is a hyphenated UUID, 8-4-4-4-12 hex digits, so no value can change the request's framing or push its head past the guard's limit; otherwise omitted, which the daemon routes as row 4's absent header). The agent argument is sent as `X-Chaldea-Agent` when it is a non-empty value of visible ASCII, otherwise omitted. A missing or malformed URL or token: exit 0 at once without reading stdin. No other variable is read, in any build, and no log file is written (§8 D8).

**Test stall.** `Stall` (`#[doc(hidden)]`) has two more values, used once stdin is read: `AfterStdin` blocks the main thread on a channel that is never sent, and `PanicAfterStdin` panics on it. Only the test-only binary `tests/hook_emit_stall.rs` (`harness = false`) passes them. That binary re-executes itself as `hook-emit codex` with the emitter's environment and the case's role (`CHALDEA_TEST_HOOK_EMIT_STALL`, read by that binary's own `main`, never by the emitter; a role without a stall passes `Stall::Off`) set only on that child, and calls the same `dispatch`. Both branches are compiled into the library; the guarantee is that the shipped binary's `main` always passes `Stall::Off`, and no CLI argument or environment variable changes it (§7.4).

**Budget.** Let `T0` be the start of `hook_emit::main`. Fixed instants: the watchdog at `W = T0 + 3000 ms`; the work end `E = T0 + 2900 ms`; the stdin end `I = T0 + 1500 ms`. Attempt `k` starts at `s_k` and has the absolute deadline `A_1 = min(E, s_1 + 1800 ms)`, `A_k = min(E, s_k + 1000 ms)` for `k = 2, 3`.

**Run**, with the checks in this order:

1. Install a panic hook that ends the process with code 0 without printing; start the watchdog thread, which ends it with code 0 at its first clock reading at or after `W` (a sleep that wakes early sleeps again). Every exit of the emitter, these two and the normal ones, is `pty_runtime::host::exit_now(0)`: Unix `_exit`, Windows `TerminateProcess(GetCurrentProcess(), 0)`. Neither runs exit handlers, stdio flushes, or DLL detach, so nothing the process holds can delay its end. If `TerminateProcess` refuses (no case is known for the current process), `exit_now` falls back to `std::process::exit`, the normal exit with its detach path.
2. Read stdin on a thread to its EOF, keeping at most 4 MiB + 1 bytes (past them the rest is read and discarded), and wait until `I`. The reader stamps the instant its read completed (EOF or an error) and hands the stamp over with the result; the result is classified by that stamp, not by when the main thread receives it. Completed before `I` → the body, even when received after `I`; more than 4 MiB → its first 4 MiB and `X-Chaldea-Body-Truncated: 1`. Completed at or after `I`, nothing by `I` (stdin still open, whatever it has sent, more than 4 MiB included), or a read error → exit 0 with no request. A payload whose EOF comes after `T0 + 1.5 s` is not sent; the CLIs write the payload and close stdin at once, so this cut leaves at least 1.4 s for the attempts.
3. `emit_id = Uuid::new_v4()` once.
4. For `k = 1, 2, 3`: the backoff before attempt `k` is 0, 50 ms, 100 ms. Before sleeping, if `now + backoff + 300 ms > E`, stop. Sleep the backoff; then set `s_k = now` (real time after the sleep) and check again: if `s_k + 300 ms > E`, stop. Run the attempt, sending `X-Chaldea-Attempt: k`: `TcpStream::connect_timeout(127.0.0.1:<port>, min(500 ms, A_k − now))`; write the head and body; read until the first CRLF (at most 1 KiB). Before every socket call the remaining time `A_k − now` is computed; if it is zero, the attempt ends as a timeout without calling `set_read_timeout` / `set_write_timeout` (which reject `Duration::ZERO`). The status line, through its first CRLF, must match `HTTP/1.` + one digit + `SP` + three digits followed by `SP` or that CRLF; anything else is a transport error. Bytes read at or after `A_k` end the attempt as a timeout; an EOF or a read error ends it as a transport error whenever it comes. Each of these is retried alike (step 5), so a late EOF or error has the disposition of a late read.
5. **Retry on**: a connect error or timeout; a write or read error, a timeout, a reset, or EOF before a complete status line (the request may or may not have been recorded; the same `emit_id` makes a retry safe); status 408 or any 503 (a `retry_after` is not honoured: the fixed backoff fits the budget). **Stop on** any other status.
6. `exit_now(0)`.

**Scheduling limits.** An attempt's decisions use its absolute deadline `A_k`, checked before every socket call and after every read. The bound handed to the OS for one call is relative: `connect_timeout`, `set_write_timeout`, and `set_read_timeout` get `A_k − now`. A thread descheduled between computing that bound and entering the call (`connect`, one `write`, or one `read`) can run that one call past `A_k` by the length of the pause, and the OS timer's granularity and wake latency add their own overshoot; the next check then ends the attempt. The outcome changes when that overshoot uses up the slack left before the next budget check, which near the `E − 350 ms` boundary for a further attempt a pause of any length can do, in one of two ways: a later attempt no longer fits before `E` and the hook is lost where a prompt retry would have delivered it; or the stale first write completes after `A_k` and reaches the daemon instead of the retry. A lost hook is the best-effort delivery stated below. Whichever attempt commits is the one delivery of its `emit_id` (PR9-CL-1), with that attempt's intake facts (PR9-CL-30); a stale first attempt's facts are those of its late intake with `intake_reliable: true`, which is the limit of §2.6 "Retries": neither tells which submission the hook belongs to. The CLI still sees exit 0 within the watchdog's bound. The stdin cut has the same limit: a reader that reaches EOF before `I` but is descheduled after it and before publishing its result is classified as still open at `I`, and the hook is not sent. The client stays on blocking std sockets; nonblocking I/O with readiness waits would remove the pause only from the socket calls, at the cost of an event loop in a one-shot emitter.

**When a second attempt runs.** Attempt 2 runs when attempt 1 ends by `E − 350 ms = T0 + 2.55 s` (50 ms backoff and a 300 ms minimum attempt). A quick failure (refused connect, 408, 503, a reset) leaves room for it and usually for a third. A first attempt that gets no reply nominally ends at `A_1` (later under the scheduling limits above), which is by `T0 + 2.55 s` only when attempt 1 started by `T0 + 0.75 s` (the usual case: stdin closes at once); a first attempt that started later and gets no reply is the only one.

Nothing is written to stdout or stderr on any path (Claude injects hook stdout into context, and exit 2 would block the prompt; spike §4.3). mvp CL-23 holds by construction, with two OS conditions: exit code 0 is the only one used, panics included, and the watchdog ends every path at `W`, provided the scheduler runs the watchdog thread at `W` and the OS completes the process's self-termination. Neither `_exit` nor `TerminateProcess` on the current process returns. On Windows the process can stay observable (not yet signalled) until its pending I/O, a blocked stdin read or socket call, has completed or been cancelled. Neither has a deadline of its own.

**Best-effort delivery.** A hook can be lost, and PR 9 has no durable redelivery of a lost hook. A hook fired while the daemon is down or restarting can be lost (connect errors, or 401s from tokens revoked at the restart). A slow daemon can also leave the emitter without a delivery: every delivery job runs on the one writer with its commit's `fsync`, and a body of up to 4 MiB is read, decoded, and held through its job, so concurrent hooks and large bodies delay one another, and the emitter can end on a status it retries but has no time left to retry (§2.11), on an EOF or reset while the daemon still reads its request, or at its own attempt deadline before any status. Once the request has registered its write observer (§2.3), a client disconnect no longer cancels it, and an accepted job can still commit after the emitter has gone; §2.11 governs the job's outcomes (expiry, rollback, an unknown outcome; `hook::tests::submitted_hook_can_expire_after_disconnect`). The emitter still exits 0 within its watchdog's bound. A missing hook is missing evidence, whose consequences are those §2.11 states for the delivery and mvp §2.3 ("Gate", "Residual constraint") states for the thread.

**Windows.** The same console-subsystem `chaldea.exe` (prior-art row 9; spike C-5 `go`: no window for hook launches); it inherits the CLI's console and creates none. A connect to a closed loopback port can take about 2 s to be refused on Windows (A2); the 500 ms connect bound keeps that inside the attempt. `exit_now` from the watchdog (`TerminateProcess` on the current process) ends a main thread blocked in `connect`, `send`, or `recv`, once the OS has cancelled that I/O. No `cfg` in the emitter.

### 2.14 FakeCli Additions

- `echo --emitter <path> [--agent <claude|codex>] [--session-id <id>] [--nested]`: at start, runs the emitter once (`<path> hook-emit <agent>`, agent default `codex`) with `{ "hook_event_name": "SessionStart", "session_id": <id or a random UUID>, "transcript_path": null }` on stdin, and per input line (split at CR or LF, bracketed-paste markers removed, empty lines skipped) a `UserPromptSubmit` with the same `session_id` and the line as `prompt`. `--nested` starts a nested FakeCli (`echo --nested-child`, the same binary, inheriting the environment and the `--report` and `--max-life-secs` arguments) that emits a `SessionStart` with another session id before and after the parent's (spike `src/fake_cli.rs:244-269`, B-11). The order is a handshake of exact lines, each counted only with its LF or CRLF and only when its reader stamped it, after decoding, before the deadline (a line stamped at or after the deadline is late; one stamped in time but published after it, its reader paused, is late when the receiver has already given up, and in time when the receiver is itself late and still finds it queued): the child emits and writes `sent` to its stdout; the parent, having read it, emits its own and writes `go` to the child's stdin; the child, having read it, emits again and exits 0. A side that gets EOF (an unterminated line included), another line, or nothing within 20 s reports `handshake_failed` (`side`: `parent` or `child`; `reason`: `eof`, `unexpected`, or `timeout`), emits no further hook, and exits 1. So does a side whose emitter cannot be started (reported as an `emitted` event with `spawn_failed`), before it writes its line. A failing parent ends the child at once rather than at its bound. The parent awaits the child at most 60 s from its launch.
- `hooks --emitter <path> [--agent <claude|codex>] --script <json>`: runs a list of steps in order: `{ "emit": <payload> }` (one emitter process with the payload on stdin; waits for its exit), `{ "concurrent": [<payload>, …] }` (one emitter each, all started, then all awaited), `{ "nested": [<step>, …] }` (a nested FakeCli `hooks` with those steps, inheriting the environment and the `--report` and `--max-life-secs` arguments; waits for it at most 60 s from its launch), `{ "wait_file": "<path>" }` (waits until the file exists, at most 10 s, so a test can hold the next step). Every child's deadline is measured from its own launch and enforced in one place (`fake_cli/watch.rs`): one loop over the children of a step kills each at its own deadline (an emitter 10 s after its launch), reaps it, and awaits its counted output pipes until 1 s after that deadline, independently of the order in which results are reported. It reports each emitter's exit code (null when it did not exit before its deadline), elapsed time, and stdout and stderr lengths (each null when that pipe's EOF did not come by the deadline plus 1 s, a descendant holding it; each count carries the instant of its EOF) on the report stream (`emitted`), and each nested run's and `wait_file` step's outcome; a script that is not a JSON array exits 2 after a `script_error` event. A payload given as a JSON string is sent as its raw text (a body that is not JSON). FakeCli's random session ids come from the standard library's hash keys (it has no random source of its own).

FakeCli stays free of workspace dependencies other than `core` (mvp §3); it starts the emitter with `std::process::Command`.

**Fixture limits.** FakeCli is a test fixture, and these are its stated limits rather than enforced bounds:

- Report I/O (the connect and each line's write) has no timeout. The report peer is the test's own listener, which always reads; a peer that stops reading is a fixture bug and shows as the test's own timeout. Each line is one `write_all` call (which may issue several writes) under one lock, shared by events and `pong` answers, so lines never interleave; a process killed mid-write can still leave an unterminated last frame, which the test's reader discards. The reader drains (bounded) before a test's final counts and when the test ends, so a complete frame that is not JSON fails the test wherever it comes; a reader that ends other than at its stream's end or a reset (its read timeout on an open connection, a read error, a failed socket setup) fails it the same way, and the fixture's drop stops its accept loop, waiting at most 30 s, before it raises that failure (a failure raised earlier by a final count leaves the listener to that drop).
- An output-counting thread can stay blocked while a descendant holds its pipe open; `settle` stops waiting for it at the cutoff and does not join it. A read error ends the count as EOF would.
- Deadline enforcement begins once a step's whole launch batch has been spawned: `settle` starts after the last spawn returns, so a slow later spawn delays the kill of an earlier child by that spawn's time, with no bound of its own.

**Endings of a hook request** (each row of §2.11 is one): a hyper parse rejection or slow-head EOF; a guard rejection; a header rejection; the body budget; the body deadline, size, or early end; a pre-read failure or replay; the walk, pid wait, or binding order cut by the deadline; the job's outcome (recorded, replayed, refused, expired, busy, rolled back, panicked, commit unknown, writer gone, failed, no reply by the grace); a client disconnect before the observer registers (nothing written; the ticket and permit released) or after it (the observer carries the job on, holding the permit, and its outcome is one of §2.11's J rows); daemon shutdown (registration refused → 503 `shutting_down`; an admitted job is answered by the writer, http §5).

**Waits.** Head: hyper's `header_read_timeout`. Body, pre-read, walk, binding order, job admission: the request deadline (5 s from the first head byte). Pid wait and its re-reads: `min(intake + 1 s, deadline)`. Job reply: deadline + 100 ms. The intake mutex: a map operation and a non-blocking probe. The emitter: the fixed instants of §2.13.

**Windows and macOS.** The daemon side has no `cfg`: OS differences are in `pty_runtime::process` (Toolhelp and handles vs `proc_pidinfo`) and in K2's reset behaviour, which B-8 records per OS.

### 7.1 B-8 (`crates/daemon/tests/hook_b8.rs`)

The test server is started with the product values set explicitly (`short_deadline = 5 s`, `header_read_timeout = 5 s`, `max_body_bytes = 4 MiB`, `max_header_bytes = 8 KiB`), not the harness defaults. Each table row: a name, the raw request (head, then body sent, withheld, trickled, partly sent then stopped, or none), the expected observation, a per-case deadline, and the no-side-effect check. The client is the raw client of `tests/support/http.rs`; its observation is `{ status: Option<(code, ErrorBody code or none)>, status_line: Option<code>, closes: Option<bool>, end: Eof | Reset | Error | Open | Timeout, send_error: Option<io::ErrorKind> }` (`status`: the whole reply, framed by its `Content-Length`; `status_line`: a complete status line, kept when a reset cut the rest; `closes`: once the head was read, whether it says `Connection: close`; `Reset`: `ConnectionReset` or `ConnectionAborted`, `Error`: any other read error; `Open`: a whole reply came and the connection stayed open 1 s after it, a kept-alive connection). A reply without `Content-Length`, or one ended by EOF after some of it and before its framing completed, fails the case, since only a reset may cut a reply. These fields tell a reset while still sending apart from one after the status. A case that sends no body byte, or withholds its body until it reads the response, requires the whole reply with its exact status and `ErrorBody` code. A case with body bytes in flight when the server decides (the guard and handler tables send each request's own body after its head) accepts the decided status, EOF, or a reset (K2): a reset can cut the reply anywhere, so a complete status line the client read must carry the decided status, and a whole reply its `ErrorBody` code. Only the `observed_*` cases print their observation per OS (`B8-OBSERVED`). The guard, handler, and ordering tables and the `observed_*` cases check PR 7's close contract: a reply head the client read says `Connection: close`, and the connection ends in EOF or a reset (`ConnectionReset` or `ConnectionAborted`), never `Open` or another read error; the parser and deadline cases do not check it. A failed write completes only once the observation has started its bounded wait for the sender (at most 1 s), so a sender still sending when the server closed reports its error after the end was seen, and only a waiting observation gets it. **No side effect** (`support::hook::Snapshot`): the count of `hook_deliveries` rows of the launch, `head_seq` of the host and thread streams, and every `proj_*` row are equal before and after the case. Every table ends with its positive control: the same server and launch accept a valid hook (200, one delivery), so a broken setup cannot pass the negative cases.

## 8. Decisions

**D1. `chaldea hook-emit <agent>` is the only emitter command form, from the first release.** Codex hashes the command string into hook trust (arch §5), so any later change of the arguments costs every user a `Hooks need review`; everything else passes through the environment. Irreversible in practice; it follows mvp §2.7's "fixed command strings".

**D2. A launch binds once in PR 9; session switches are PR 13 / 14's decision.** A `SessionStart` with another session for a bound launch is `raw_unknown` `foreign_session`, and the binding stays. Nothing user-visible depends on it yet: until PR 13 / 14 plug in decoders, every bound hook other than the binding itself is `raw_unknown` anyway. Once adapters exist, the effect is that after a session switch in an attached CLI (Claude `/clear` or in-session `/resume`; Codex `/new` or `/clear`, A1) the thread stops following the CLI: the new session's hooks are `foreign_session`, its prompts and readiness are not applied, the gate does not reopen, the tailer stays on the old transcript, and `chaldea resume` passes the old session. PR 13 and PR 14 must settle this before they merge, from PR 12's fixtures of switch payloads (`source`, new id): either follow the new session (a repeatable `session_bound` per launch as a new turn start for PR 10's gate and a new transcript generation for the tailer, with `events_session_bound_once` dropped by migration) or keep one binding and document the limit. Reversible: stored events do not change meaning either way.

**D3. Claude binds and selects by session id; its chain is not required.** mvp §2.9 and the spike verified the session-id rule for Claude; requiring ancestry for Claude was never run on a real Claude host (the spike's Claude binding used the session id only, K9). The cost is that a nested Claude resuming the launch's session id is taken as the launch's own (§2.5). PR 13 checks the chain on real hosts; switching Claude to rule `Ancestry` is one row of `HookAdapter::rule`.

**D4. The buffer bounds are 32 deliveries, 8 MiB, and 30 s per launch.** Codex's early hooks are the first turn's few concurrent hooks; 30 s exceeds the 5 s request deadline plus the 1 s pid wait many times, and 8 MiB holds two maximal bodies. Internal; tunable without migration.

**D5. Stdin over 4 MiB is sent truncated and kept as `raw_unknown` `unparseable` with an annex marker.** The spike dropped it (B-9), which is a silent loss (arch §1); the truncated prefix keeps the evidence that the hook fired. This is the one exception to P-14's "verbatim": such an event's `raw` is the first 4 MiB, and its annex `Hook { truncated: true }` records that, internally and rebuildably. Exposing the marker to clients would be a public payload change; it can be added later as an optional field. The 4 MiB cap (mvp §2.5) is unchanged.

**D6. The `X-Chaldea-*` headers other than `X-Chaldea-Emit-Id` are internal.** Both ends are the same binary; a running launch keeps the emitter path it was given, and a daemon restart revokes open launches' tokens, so a version mix lasts at most until the restart. The daemon ignores unknown `X-Chaldea-*` headers and treats an absent or invalid value as described in §2.2.

**D7. A recorded delivery answers 200 with an empty body.** No new public body (mvp §2.5 lists the public bodies); the emitter reads only the status; dispositions are in the stream and in `hook_deliveries`. A disposition body can be added later; it is additive.

**D8. No emitter log file.** A log path would be a new public environment variable (mvp §2), and the emitter is silent by contract; the doctor (PR 21) observes deliveries on the daemon side. A `CHALDEA_HOOK_LOG` can be added later; it is additive. The watchdog test's stall is a `dispatch` argument that only a test binary passes, not a variable.

**D9. B-8 does not drain rejected bodies.** After a rejection decided before the body, the server reads what has arrived once and closes (K2), so a client with body bytes in flight, at any body size, may see a reset instead of the status; the only client retries and needs no status (§2.13), and nothing is created either way (PR9-CL-20).

**D10. Hook ancestry is a binding heuristic, never kill evidence; `extra` is PR 10's.** A parent link read from the OS names the current parent (macOS, changed by reparenting and debugger attach) or the creator's pid without its generation (Windows), so no hook-time walk can prove that a process descends from a launch without a clock comparison or a kernel generation number the documented APIs do not give (K13). A wrong `extra` entry makes `kill_tree` kill an unrelated process; a wrong eligibility result misclassifies one hook under the trust boundary. So PR 9 uses the walk only for Codex eligibility, failing closed, and records nothing for `extra`; PR 10 attributes `extra` from containment it can prove (§4). Reversible: if a later PR finds kernel generation data on both OSes, a proven walk can add an attribution source without changing PR 9's tables.
