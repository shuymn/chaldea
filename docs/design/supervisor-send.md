# Design: Supervisor, Send and Ack Side (MVP PR 10b)

Status: implemented (#48) in `crates/daemon/src/supervisor/send` and `crates/core/src/input/key.rs`. Scope is the send and ack half of the PR 10 row of `docs/mvp-design.md` §4 (cited as "mvp §N"), called **PR 10b**: the `send`, `ready`, `key`, `input_resolve`, and `input_cancel` commands; the readiness gate and its evidence; the writer integration (`encode` at write time, the `WriteUnit`, the hook fence, the outcome mapping, `human_write`); ack attribution with `prompt_matches`; the real `IntakeProbe`; input-side attention and approval cards; and the send path's guards in `specs/thread_input.qnt`. It builds on the 10a1 design, `docs/design/supervisor.md` (cited as "sup §N"), through its §2.11 interfaces and the changes listed in §2.9 here.

**What 10b decides and leaves.** 10b owns the daemon's `supervisor::send` module, a `core` key encoder, the hook adapter wrapper that turns decoded hooks into state, and the small changes to earlier seams that §2.9 lists (one writer guard in pty-runtime, the hook route's commit callback, the input projection). It leaves to PR 13 and PR 14 the hook configuration of real CLIs and the decoders that read their payloads (until then no real CLI binds, sup SD14), the readiness and resume columns of `GET /api/adapters`, session switches, and the evidence that resolves an approval card (mvp §2.10; the `tool_use_id` correlation rule is deferred); to PR 11 attach and resizing (F5); to PR 18–19 the UI; to PR 10a2 crash recovery.

**Commitments from earlier PRs this design keeps.**

1. Thread and input state move only through explicit events: hooks, the writer's completion records, and the supervisor's own commands (invariant 1). Nothing reads PTY text; the VT is read only for its mode word and a diagnostic snapshot (mvp §2.2).
2. No input is resent automatically: nothing leads from `sending`, `sent`, or `unconfirmed` back to `queued` or `sending` (`step`, `crates/core/src/input.rs:178-211`).
3. `reduce`, `step`, `gate`, and `blocks_gate` keep their rules; `GateView` and every public payload keep their fields. New public names are listed in §1 and flagged in §3.
4. `HookAdapter::interpret` stays data-only on the store writer (hook-ingest §2.6): it reads through its `ReadTx` and its `AcceptedHook`, never supervisor memory. Supervisor memory learns of a delivery only after its job committed (§2.9 P2). The one supervisor value a delivery job reads is the launch's turn watermark: the hook route loads it on the writer before `interpret` into `AcceptedHook.turn_watermark`, and only the writer raises it, after the job's `COMMIT` (§2.4 "Turn boundaries in receipt order").
5. Every wait has a deadline through `deadline::settle_before`, `LiveLaunch::with_session`'s deadline, or `supervisor::record`'s policy (§2.8). Every instant handed to pty-runtime (`Guard.not_after`, `Session::snapshot`'s deadline) is converted with `clock.real(…)`, as sup §2.3 does.

## 1. Goal and Dependencies

**Goal.** A prompt given to `chaldea send` is written to the CLI's PTY exactly once, as one encoded unit, only while the gate holds and no hook was taken in since the gate was read, or is shown `rejected` or `cancelled` with zero bytes; every written input ends `acked` only on a `UserPromptSubmit` that matches its text and can be attributed to its completed write, otherwise `unconfirmed` and never resent; no keystroke reaches a dialog it was not meant for; and every human write, card, and timer reaches the store as an explicit event.

## 2. Design

### 2.1 Rules

1. **The store decides; memory holds what the store cannot give in time.** Whether an input opens, is acked, or times out is decided in one store job that re-reads the projection. `SendLaunch` (memory, per launch) holds the hook fence, the latest intake's ordinal, the ack facts of the in-flight input (`Dispatch`), the running input unit (`running`), the count of unsettled human units, each card's observed human position (`cards`), the turn log, and timer start instants. It lives until the launch's exit job committed and its writer fired every completion (§2.3 "After exit"); a restart exits every launch (sup §2.5).
2. **One synchronous boundary orders hooks against writes.** Every hook intake advances `L`'s fence word before its job can commit, and the writer compares that word under its queue lock as the last check before a unit's first write permission (§2.3 "The hook fence"). A unit whose state was read before a hook was taken in is refused with zero bytes. A card key is also bound to the human writer position at the observation that showed its card (§2.6).
3. **Positions, not wall time, order writes against hooks.** Every attribution and staleness test compares writer positions (`last_started` per `OriginClass`, `Published.reference`), as pty-runtime §2.3 "Ack attribution" states. Durations are measured on the supervisor's monotonic clock (`SupervisorConfig.clock`) from the instant of the event that starts them.
4. **Zero bytes or unknown, never guessed.** `NotStarted` and every refused submission are zero bytes (`RecheckFailed`); `Incomplete` and a stalled unit are unknown (`WriteOutcomeUnknown`), pty-runtime D5. Showing an input `unconfirmed` does not end its unit: a running unit blocks the next send until it completes or is sealed.
5. **Ambiguity fails closed.** A hook whose turn, write, or intake facts cannot be attributed acks nothing and is no evidence; the gate stays closed until evidence that can be attributed or `chaldea ready` (mvp §2.3 "Residual constraint" (c)).
6. **One owner per record.** The driver applies every write completion of a launch (inputs and human units alike); commands await its report, never the writer's callback.

### 2.2 Commands

Registered in `Built::commands` beside 10a1's four (E1). Each `prepare` parses `args` (400 `bad_args`) and builds an intent from data. Each intent checks the target against the token's grant first, through `deny_for` on the target thread (403 for a thread the token can read, 404 otherwise, `http/auth.rs:330-339`).

| Command | Who (`auth.rs:126-175`) | Args | Intent | Effect | Success |
|---|---|---|---|---|---|
| `send` | owner; agent self+ | `SendArgs { thread_id, text, origin? }` (`origin` default `cli`) | `thread_closed`; current launch `starting` or `running`, else `no_live_launch`; `input_created { launch_id: current, initial_state: queued, encoding: caps.pty_encoding, origin, created_by }` with `created_by` from the authenticated principal (`Human` for the owner, `Thread(me)` for an agent) and `text` through `prepare_content`; `check(agent, pty_encoding, Send, text)` → `Err(r)`: `queued → rejected(r)` in the same job. `Completed` (the input and its completed receipt in one transaction, mvp §2.4) | none | `SendResult { input_id, state, reject_reason }` (`state` `queued` or `rejected`; `reject_reason` null unless rejected) |
| `ready` | owner | `ReadyArgs { thread_id, expected_launch_id? }` | `thread_closed`; `launch_changed`; current launch `running`, else `no_live_launch`; unbound → `not_bound` (A12). `Pending(L)` | §2.4 "Owner assertion"; a running input unit of `L` → `unit_running` | `ReadyResult { launch_id }` |
| `key` | owner | `KeyArgs { thread_id, launch_id, keys: [KeyToken], approval_id? }`; `keys` empty or over `MAX_KEYS` → 400 `bad_args`; with `approval_id`, a token before the last that is not in `caps.card_nav_keys` → 400 `bad_args`, so a card key request carries at most one deciding key, as its last token | `thread_closed`; `launch_changed`; `running`, else `no_live_launch`; with `approval_id`: the card open and of `L`, else `card_closed`. `Pending(L, card)` | §2.6 | `KeyResult { outcome, bytes_written }` |

A rejected input is created and rejected in one job so that its reason is public (`input_state_changed.reason`), as input-encoders §4's PR 10 row asks. `origin` is the client's claim and decides nothing. A second request with the same `command_id` replays the stored result, or answers 409 `in_progress` while the first runs (http-surface §2.8).

`thread_closed`, `launch_changed`, `prompt_too_large`, and `prompt_rejected` are 10a1's (sup §2.2), as is `launch_busy` (504), which `ready` also answers when it could not sample the launch's session in time (http-surface §2.8).

**Claude's first prompt.** `spawn --prompt` and `resume --prompt` for Claude (400 `bad_args` in 10a1) become a queued input made at reservation (§2.9 D3). `spawn`'s `prepare` runs the size check and `check(Claude, BracketedPaste, Send, text)` (400 `prompt_too_large`, `prompt_rejected`); `resume` runs both in its intent, right after the target-scope check reads the thread's agent, and a refusal rolls the receipt back with the job (sup §2.2). The reservation job runs `prepare_content` and appends `input_created { launch_id: L, initial_state: queued, encoding: bracketed_paste }` with the prepared text and its blob after `launch_reserved`; the input's queued instant is taken as for `send` (§2.7). The input is written when the gate first opens, and `SpawnResult.input_id` (`ResumeResult.input_id`) names it.

### 2.3 The Send Path

`Driver` is one supervisor task started in `SupervisorComponents::attach`. It dispatches wake-ups to one worker task per live launch, so a launch whose job is being retried never delays another's: `Store::subscribe` notifications naming a thread stream wake that thread's current launch; every tick that `SendTick` forwards (with the live list, §2.7) and every `RecvError::Lagged` wake all live launches; completions wake their launch. A worker handles its launch `L` only while `L` is its thread's current launch and `Supervisor::live(thread, L)` returns an entry, one pass at a time.

**The hook fence.** `SendLaunch.fence` is one `AtomicU64` word: the count of `L`'s hook intakes in the high 44 bits and the count of those not yet finished in the low 20 bits. `SupervisorProbe::facts` stores the intake's ordinal into `SendLaunch.latest_intake`, then adds `(1 << 20) + 1` to the word with a checked compare-and-swap (non-blocking, under PR 9's intake mutex, before the hook's job exists); an add that would overflow either field sets the word to the closed value `u64::MAX` instead, and every compare-and-swap on the word, a guard's release included, leaves `u64::MAX` unchanged, so every send and key of `L` stays refused until the launch exits. Each intake gets one `IntakeGuard` (§2.9 P2) that releases it exactly once: after a reply that decides the job (committed, rolled back, or refused), it first applies the job's marks (`TurnLog`, `cards`), then subtracts 1 with `Release` ordering; on every path that ends before the job was submitted (registration or submission refused, deadline passed, client gone) it subtracts 1 with no marks; when the job was submitted and its outcome stays unknown (`CommitUnknown`, `WriterGone`, or the observer aborted at shutdown before the reply), it does not subtract, so `L` stays closed until it exits. A reader loads the word with `Acquire`; when it shows zero unfinished intakes, every hook taken in so far has committed or failed, so a store read after the load sees them. pty-runtime's writer compares the word with `Guard.fence.expect` under its queue lock as the last check before a unit's first write permission, beside `not_after` (§2.9 W1). The fence orders intake against that logical permission: a hook taken in before it refuses the unit `FenceMoved` with zero bytes; a hook taken in after it does not, and since the writer calls the backend after releasing the queue lock, that hook's job may commit before the bytes reach the CLI.

Per pass, for the oldest `queued` input `Q` of `L`:

1. **Open job** (`open_job`, through `supervisor::record` with a typed value, §2.9 D1), when `SendLaunch.running` is empty and `human_unsettled` is 0. It loads `fence`; unfinished intakes or the closed value → `None` (the hook's finish wakes `L` again). It reads `L`, `Q`, and the thread, and samples the session through `with_session(clock.real(now + 250 ms), |s| (s.modes(), s.observer().last_started_each()))` taken by the worker just before the job (`Busy` or `Gone` → skip the pass). It builds the `GateView` from the projection with `needs_bracketed_paste` = `pty_encoding == BracketedPaste` and `bracketed_paste_on` from the sampled modes, and `gate(view)`. It also refuses as `WriteAfterEvidence` (SB3) when the sampled `last_started` over `write_basis.counted` is above `write_basis.position` (a counted write after the evidence with no event of its own, such as a VT reply). After its last read it checks `SendLaunch.running` empty and `human_unsettled` 0 again under the `SendLaunch` mutex, the one a human unit's registration takes (§2.6): a human unit registered before that check keeps `Q` `queued`; one registered after it is ordered after the open, and its writer refuses `Q`'s unit if the human unit starts first. Open → `input_state_changed(queued → sending, GateOpened, sent_after_seq = head)`, clearing `input_gate_timeout`; the projection records `attempt_seq` and `last_write_before` (§2.9 E1). The job returns `Some(Opened { write_basis, epoch, fence_word, competing, needs_paste, text })` with `competing` = `last_human_write_seq > last_turn_start_seq` (§2.5), or `None` whatever closed it (the worker skips the pass alike): `Q` stays `queued`.
2. **Submit** (after `Opened` returned). `Q`'s text, through `ReadTx::blob` when it is `Content::Blob`, goes to `encode(agent, host_os, text, Send)` (C2); an `Err` cannot happen after `check` accepted the text at `send` (PR5-CL-1) and is treated as a refused submission. The unit is `WriteUnit { origin: Input { input_id }, parts: [Bytes(text), Pause(submit.delay), Bytes(submit.bytes)] }` (input-encoders §2.3). The `Guard`: `not_after` = `clock.real(now + DISPATCH_WAIT)` (10 s); `basis = Basis { seq: write_basis.position, counted }`; `bracketed_paste = Some(epoch)` iff `needs_bracketed_paste`; `fence = Fence { word: L.fence, expect: fence_word }`; no recheck. Inside `with_session(clock.real(now + 1 s), …)` the worker reads `before` = `last_started[input]`, installs `Dispatch { input_id, before, written: false, competing }` (the ack facts, kept until the input leaves flight or the next dispatch), creates the shared `written` flag, and sets `SendLaunch.running = RunningUnit { ticket: None, submitted_at: now }`, all before calling `submit`, so a completion that runs before `submit` returns still finds them and a hook taken in once the unit may write sees `running` (§2.4); the returned ticket is then stored in `running.ticket`. A `SubmitError` clears `running`; otherwise only the record (step 4) or the seal clears it. The unit's `Completion` sets `Dispatch.written` (an atomic) under `L`'s `SendLaunch` mutex when the outcome is `Written` (§2.5: the intake probe holds the same mutex across its read and the fence advance), then sends the record to the driver; that mutex is its only wait. `Busy`, `Gone`, or a `SubmitError` → the completion job with `RecheckFailed` (nothing was submitted, so zero bytes are certain).
3. **Writer checks** (pty-runtime §2.3). Before the first permission the writer refuses on a counted write since the basis (`WriteSinceBasis`, `BasisUnknown`), a changed 2004 epoch, exit, close, `not_after`, and a moved fence. Together with the open job's gate these are the model's `recheckView` (A33): every gate input other than the writer's own state (`bound`, process, turn, cards, evidence, in-flight inputs) changes only through a hook (fenced), a human write (a counted write after the basis), a stop (seal), or `ready` (opens only).
4. **Completion job** (F3), run by `L`'s worker for every record. Only for an input still `sending` of a launch with no `launch_exited` (a completion after the exit job is ignored, pty-runtime §2.3): `Written` → `WriteCompleted` (`sent`); `NotStarted(_)` → `RecheckFailed` (`cancelled`; the projection restores `last_write_seq`, SB1); `Incomplete` → `WriteOutcomeUnknown` (`unconfirmed`, raising `input_unconfirmed`). An input a hook already moved on (§2.5 step 3) or the stall already showed `unconfirmed` is left as it is. The record ends the running unit (`SendLaunch.running` cleared) whatever the job does; `Dispatch` stays, so a matching hook after `sent` or `unconfirmed` is still attributed (§2.5). A job that is not recorded keeps its record for the next pass.
5. **Dispatch wait and stall.** While `running` is set, each pass reads `ticket.started_at()` (§2.9 W2), the writer's instant of the unit's first permission, recorded on the ticket at the permission and read without the queue lock. With no `started_at` and no record `DISPATCH_WAIT` + 1 s after `submitted_at` (the unit waits behind a blocked unit, so the writer never reaches its `not_after`), the worker calls `ticket.try_cancel()` (§2.9 W3), which never waits for the queue lock: `Some(true)` → its completion is `NotStarted(Cancelled)` and step 4 cancels the input; `Some(false)` → it is permitted or settled, and a later pass sees which; `None` (the lock is held, as by a writer at its dispatch boundary) → the next pass tries again. With `started_at` set and no record once `clock.real(now)` is `WRITE_STALL` (30 s) past it, a job applies `WriteOutcomeUnknown` (`unconfirmed` with `input_unconfirmed`, SB15); the input is shown on the first pass after that bound, so a worker delayed by its own launch's job shows it later, never earlier. The unit keeps running: the next open, `ready`, and every hook or settle evidence wait for its record or the seal, whatever the owner does with the input meanwhile.

**After exit.** `SendExitStep` (10b's `ExitStep`, sup §2.11 "Exit job order") applies each `ExitFacts.sealed` record whose origin is `Input { input_id }` to that input if it is still `sending` (`RecheckFailed`; a sealed unit wrote zero bytes) and settles sealed human records as §2.6 does, expires the launch's open cards (`approval_resolved { outcome: expired }`, §2.9 D4), and records each record of `SendLaunch.exit_set` as the worker does (§2.6 "Human units": a `human_write` for `Written` or `Incomplete`, nothing for `NotStarted`): the human records the worker held unrecorded, copied under the `SendLaunch` mutex at the exit job's first attempt and the same immutable set on every retried attempt (the idempotency key makes a record the worker commits meanwhile an existing event). Its `after_commit` removes those records from the worker; until then the worker keeps them. The worker of the exited launch keeps running until the session's writer has fired every completion (the session closed or dropped), recording any human completion outside `exit_set`; then `L`'s `SendLaunch` is dropped. A unit refused `ChildExited` before the exit job commits is cancelled by its completion job; one whose completion comes after is ignored and the 10a1 sweep has made the input `unconfirmed` (A23). At restart the exit steps run with `restart: true` (sup §2.5), so cards of every open launch expire there too.

### 2.4 Gate Evidence

A `readiness_observed` carries `EventAnnex::Readiness(WriteBasis { launch_id, position, counted })` (event-store §2.6), `position` = `last_started(counted)` sampled at the evidence's own intake and `counted` = the adapter's policy, `ClassSet::ALL` for every row (pty-runtime D3; S15). Every job that appends one also appends the `status_changed` that `reduce(&thread.state, &StateInput::ReadinessObserved)` returns (the projection sets the turn only from `status_changed`, `project.rs:224-242`). Per kind (A9, X3):

| Evidence | Where it is decided | Its intake (the basis) |
|---|---|---|
| `session_start` | the binding job, in `SupervisorHooks::interpret` for the binding `SessionStart` | the `SessionStart`'s `IntakeFactsV1.last_started` |
| `stop_settled` | `L`'s worker's settle job | `Supervisor::observe` sampled when the worker builds the job (an `Unobservable` launch is skipped that pass) |
| `post_decision` | `interpret`, when a decoder reports one | the hook's intake facts |
| `owner_asserted` | `ready`'s effect | `with_session(clock.real(now + 1 s), \|s\| s.last_started(counted))` |

Evidence is recorded only when `evidence_allowed(row, kind)` holds (the model's `kindAllowed`: `session_start` only for Claude and not `OwnerOnly`; `stop_settled` only under `StopSettle`; `post_decision` only under `PostDecision`; `owner_asserted` always), and, for a hook, its `intake_reliable` is true, its facts decode (D3), and they show no running input unit (`running` false; a unit that may still write makes any idle evidence stale, SB15). `Capabilities::readiness_mode` is `StopSettle` for all four rows (mvp §8 D8); PR 13 and PR 14 may change a row and expose the column.

**Settle completion** (A36, SB14). A settle completion counts only for the `Stop` it was started for, of the current turn, while no later hook of the launch was taken in. Hooks carry no turn id the daemon can rely on, and intake order does not bound a hook's age (hook-ingest §2.6 "Retries"), so the daemon settles only on an end it can attribute, and otherwise waits:

1. `interpret` returns a `TurnMark` with the events: `Start` for a `PromptSubmitted`; `End { settle }` for a `Stop` or an `Interrupt`, `settle` true only for a `Stop` with `intake_reliable` and facts present that show no running input unit, or a running unit whose `inflight.written` is true and whose input the job reads `acked` with an `ack_seq`, that is acked by a hook (its own turn's `UserPromptSubmit` was attributed, and the unit ran to `Written` before this intake, so it ended before the `Stop`; step 3 waits for its record). Any other `Written` unit may have a turn still running: one whose input is not yet acked, or acked only by the owner's `input resolve --delivered`, which sets no `ack_seq`; a `Stop` taken in while a unit may still write never becomes a candidate, even after the unit ends; `Card { approval_id, human_at }` for a `CardOpened` (`human_at` = the facts' `last_started[human]`; none when facts are missing, when `intake_reliable` is false (a retried delivery may be older than human writes already counted), or when the facts show `human_running` (a human unit submitted and not yet recorded, permitted or not, may still write after the card appeared)); `Resolved { approval_id }` for a `CardEvidence` that resolves an open card; `Other` for every other hook. A stale boundary (below the launch's turn watermark, "Turn boundaries in receipt order" below) keeps its mark: the log is keyed by receipt ordinal. After the job commits, `IntakeProbe::finished` puts each mark into `L`'s `TurnLog` under its receipt ordinal with the commit's instant (the clock read right after the job's SQLite `COMMIT` through a `CommitStamp`, carried to `finished`), and each `Card` into `SendLaunch.cards` (§2.9 P2), once. Whether a card is open is the store's, never the order the observers finish in: only a `Resolved` mark drops its own card's entry, so a boundary whose job commits before a card's, or whose observer finishes late, never drops the basis of a card the store holds open. An entry also leaves when a card key finds its card closed, or with the `SendLaunch` (§2.6 "Card memory").
2. On each pass with zero unfinished intakes in the fence word, the worker takes the log's highest entry `S`. `S` is a settle candidate when its ordinal equals `latest_intake` (so a later intake whose job never committed still ends it), it is `End { settle: true }`, there is a `Start` `T` below it (the current turn's start), and the boundary entry (`Start` or `End`) just below `T` is an `End`, or `T` is `L`'s first boundary. Otherwise nothing settles: an earlier turn may still have a `Stop` in flight, or the turn started unseen.
3. A candidate at least `SETTLE` after its commit instant gets one job: it loads `fence` and requires the word the worker saw (no hook taken in since), requires `SendLaunch.running` empty and no human unit unrecorded (`human_unsettled` 0; otherwise the job writes nothing, the candidate stays, and the pass after the record decides it again, so the readiness follows the unit's `human_write`), re-reads `L` (current, bound, `running`), the thread (turn `unknown`, no open card of `L`), and that no readiness evidence of `L` is newer than `S`'s delivery, and appends `readiness_observed { stop_settled }` and its `status_changed`.

Examples: `P1`'s `Stop` taken in after `P2`'s `UserPromptSubmit` (late, or after a `ready` the owner ran before it arrived) leaves `P2`'s start right after `P1`'s, so neither that `Stop` nor `P2`'s own settles, and the owner runs `ready` once; `P3`, whose start follows `P2`'s `Stop`, settles again by itself (SB14, L-9). The inference from the hook sequence has an accepted gap: a late `Stop` after a lost `UserPromptSubmit`, or a turn's second `Stop`, taken in after the next turn's start (L-11). Every `Stop` that is not stale still sets the turn `unknown` and supersedes the launch's open cards, whatever its turn: both close the gate and refuse card keys, which is the safe side (§2.5). The log keeps entries from the boundary below the current turn's start.

**Turn boundaries in receipt order** (PR10b-CL-23). Hook jobs of one bound launch commit in any order: only a binding `SessionStart` waits for lower ordinals (hook-ingest §2.4). A turn boundary is a delivery whose mark is `Start` or `End`, whether its interpretation is `Events` or `Raw`. `SendLaunch.turn_watermark` (an `AtomicU64`, created with the `SendLaunch` before any hook of the launch) is the highest receipt ordinal among `L`'s committed turn boundaries. The hook route loads it once per job on the writer and hands it to each delivery the job interprets as `AcceptedHook.turn_watermark`, raised within the job by every boundary interpreted before it, promoted ones included (promotion runs in receipt order). After a successful `COMMIT` the writer raises the atomic by `fetch_max` (`WriteTx::after_commit`), before its reply and before the next job; a rollback drops the raise. Card and readiness hooks neither raise it nor are checked against it. The `SendLaunch` lives from the reservation job until the launch left the live map, which happens after its exit job answered, committed or not; a job that finds none reads the watermark as `u64::MAX`, so every boundary of a launch the store still holds live after an unrecorded exit counts as stale.

- **TO-1.** When a turn boundary of `L` commits with a receipt ordinal below the watermark, it appends its `user_message` and its ack steps (attribution, `ack_seq`, and `user_message.input_id` as §2.5 decides), but changes no turn state, supersedes no card, and leaves `L`'s turn-start basis (`last_turn_start_seq`) where it was. Its `user_message` carries the store-internal annex `Prompt { superseded: true }` (event-store §2.6), which the projection reads to skip the basis.
- **TO-2.** Among `L`'s turn boundaries, the resulting turn state and open cards are those of their receipt order, whatever their commit order. The history is not: a boundary overtaken by a later one records no `status_changed` of its own (a `Stop` that commits before its start leaves no `running` transition).
- **TO-2b.** A stale start keeps the previous basis. This is conservative, not receipt-order equivalent: when the stale start is a turn a human typed through attach, the settle's evidence is of the same turn (`EvidenceOfSameTurn`), so the gate waits for `ready`, and after `ready` the next send's `competing` (§2.5) comes from that basis, so a matching hook can leave it `unconfirmed`. Without the annex, a delayed start's commit position would pass for a later turn.
- **TO-3.** A boundary whose job rolls back or is never submitted leaves the watermark unchanged.

A binding job's own `SessionStart` folds before the deliveries it promotes, by hook-ingest's binding design; promoted boundaries follow TO-2 among themselves and against boundaries already committed. Card and readiness hooks keep the commit-order fold (L-13). A `Stop` that commits before its turn's start therefore leaves the turn `unknown`, and it settles when it is a candidate (step 2) and step 3's conditions hold, as when the start commits first; without the watermark the late start would set it `running`, so the turn would neither settle nor open the gate. Memory is enough because a launch never outlives its daemon process (the next start records it `daemon_restart`); committing boundaries in receipt order instead would make every boundary wait on its predecessors' jobs, as only the binding does.

**Owner assertion** (C3). `chaldea ready` asserts that the CLI's composer is in its normal edit mode and empty, with no search, popup, or dialog open, which no signal shows (input-encoders §2.6). The effect answers `unit_running` while `SendLaunch.running` is set (a unit that may still write would put its bytes after the assertion's basis, SB15); otherwise it samples the basis, then one `supervisor::record` job re-checks that no input unit runs, that the thread is not closed, and that the launch is current, bound, and `running`, and appends `readiness_observed { owner_asserted, by: human }` with its `status_changed`; a re-check that fails answers its code (`unit_running`, `thread_closed`, `launch_changed`, `no_live_launch`, `not_bound`). It writes no PTY byte. A send made when the assertion does not hold follows the ordinary match and attribution rules and is never resent. A write between the command and the sample lies inside the basis (L-3).

### 2.5 Hooks: Decoders, Intake Facts, Ack Attribution

**Decoder seam** (SB10). `SupervisorHooks` (new) implements `HookAdapter` and replaces `MvpHooks` in `SupervisorComponents::build` (its `rule` and `expected_session` are `MvpHooks`'s). Its `interpret` asks a per-agent `HookDecoder` for a `HookFact` and the adapter's own events:

```rust
// crates/daemon/src/supervisor/send/hooks.rs (new)
pub(crate) trait HookDecoder: Send + Sync + 'static {
    /// Data only, as `interpret`. `extra` are the adapter's own events (assistant text, tool activity).
    fn decode(&self, tx: &ReadTx<'_>, hook: &AcceptedHook<'_>) -> Result<(HookFact, Vec<HookEvent>), StoreError>;
}
pub(crate) enum HookFact {
    SessionStart, PromptSubmitted { prompt: String }, Stop, Interrupt, PostDecision,
    CardOpened { tool_name: String, tool_input: serde_json::Value, turn_ref: Option<String>, correlation: Option<ApprovalCorrelation> },
    CardEvidence { tool_use_id: String },       // a PostToolUse; the card whose correlation names it
    Other,
}
```

`NoDecoder` returns `Other` with no events for every hook. Real CLIs send no hook until PR 13 and PR 14 configure them (sup SD14), and with `NoDecoder` a hook that does arrive stays `raw_unknown` `unknown_event`, as with `MvpHooks` today. Tests install `FakeDecoder`. Per fact, in the delivery or binding job (`L` is current, live, and bound, hook-ingest §2.1 rule 5):

| Fact | Events appended (besides `extra`) | Mark |
|---|---|---|
| `SessionStart` | in the binding job only: `readiness_observed { session_start }` and its `status_changed` when §2.4's conditions hold; a later same-session `SessionStart` is PR 13's session-switch decision and appends nothing here | `Other` |
| `PromptSubmitted` | `user_message { prompt, input_id }` with the attribution below (`prompt` through `prepare_content`); unless stale (§2.4 "Turn boundaries in receipt order"), the `status_changed` of `PromptSubmitted` when the turn changes and open cards of `L` → `approval_resolved { superseded }`; stale, the `user_message` carries the `Prompt { superseded: true }` annex | `Start` |
| `Stop` | unless stale, the `status_changed` of `TurnStopped` when the turn changes and open cards superseded | `End` |
| `Interrupt` (Codex) | unless stale, the `status_changed` of `Interrupted` when the turn changes and open cards superseded | `End { settle: false }` |
| `CardOpened` | `approval_requested { approval_id = the delivery's emit_id, launch_id: L, … }`, `status_changed` (`ApprovalOpened`) | `Card` |
| `CardEvidence` | the open card of `L` whose correlation has that `tool_use_id` → `approval_resolved { ran }`, then `status_changed` (`ApprovalsAllResolved`) only if no other card of `L` stays open (A34; cards close at every turn boundary, so `L`'s open cards are the current turn's) | `Resolved { approval_id }` when it resolves an open card, else `Other` |
| `PostDecision` | `readiness_observed { post_decision }` and its `status_changed` when allowed | `Other` |
| `Other` | `extra` | `Other` |

Each `approval_resolved` of one delivery is named `card:<approval_id>`, so one `Stop` can close several cards (§2.9 P3). When the events and `extra` are both empty (a `Stop` on an `unknown` turn with no card, a stale `Stop` or `Interrupt`, a `CardEvidence` with no open card, a refused `PostDecision`, a `SessionStart` that is no evidence) `interpret` returns `Interpretation::Raw(UnknownEvent)` with the mark, never an empty `Events` (`route.rs:124-126` refuses one, which would roll back a binding).

**Intake facts** (D1). `SupervisorProbe` (new, built in `build` over `Supervisor::observe` and `SendMap`) is the `IntakeProbe`. It waits on nothing but its read of `SendMap`, which may wait on a short `SendMap` write section (one `SendLaunch` construction and insert, or one remove; no await, I/O, or other lock inside it); this wait has no deadline of its own: the writers are `send_launch` in the reservation job and the worker's exit. It never waits on a launch, a writer, or the store. On each call it tries `L`'s `SendLaunch` mutex, reads `Dispatch.written` under it, advances `L`'s fence (§2.3) while still holding it, and only then observes the launch, so every fact is settled against the intake at one point: `running`, `human_running`, and `inflight` are those of the fence advance. A `Written` completion sets `written` under the same mutex, so it is either before the intake (a fact of it) or after it, never in between; one released while the probe holds the mutex publishes after it, and its hook acks nothing (the input goes on to `sent`). It encodes:

```json
{"v":1,"reference":<u64>,"last_started":[<input>,<human>,<reply>],"running":<bool>,"human_running":<bool>,"inflight":{"input_id":"…","position":<u64|null>,"written":<bool>,"competing":<bool>}|null}
```

`LaunchObservation::Started { reference, last_started }` → `reference` and `last_started` as given; `Reserved` → zeros (no child exists, so no write precedes the hook); `Unobservable`, or `L`'s `SendLaunch` mutex contended (`try_lock`) → `None`. `inflight` is `L`'s `Dispatch`, kept until its input leaves flight or the next dispatch, with `position` = `last_started[input]` when that is above `Dispatch.before` (the unit's own seq; one input unit runs at a time), else null. `running` = whether `SendLaunch.running` is set, independent of `inflight` (a dismissed input whose unit still runs has no `Dispatch` but `running` true). `human_running` = whether `SendLaunch.human_unsettled` is above 0. `None`, another `v`, or a shape that does not parse are "facts missing": such a hook acks nothing and is no evidence, never "no write happened".

**Attribution** of a `PromptSubmitted` with prompt `P` (A10, X4, A16–A18, B2, C4), decided in the job:

1. `M` = the in-flight inputs of `L` (`sending`, `sent`, `unconfirmed`) whose text (through `ReadTx::blob` when a blob) has `prompt_matches(agent, encoding, text, P)`. `|M| = 0` → `user_message` without `input_id`. `|M| ≥ 2` → without `input_id`, no input changes (A18).
2. `M = {X}`, attributable only when all hold: `intake_reliable`; facts present; for a positional `X` (`encoding: positional`): `last_started[input] ≤ reference` and `last_started[human] ≤ reference` (SB5); otherwise `inflight.input_id = X`, `position = s` present, `written` true (the whole unit, submit included, was written and its completion ran before the intake), each other counted class's `last_started < s` (no counted write after it), and `competing` false; and no input of `L` that left flight without a hook ack (`acked` with no `ack_seq`, `dismissed`) has `prompt_matches` for `P` (an earlier unattributed dispatch, C4).
3. Attributable → `user_message { input_id: X }`; `X` `sending` → `WriteCompleted` then `AckAttributed` in this job (the facts show the write completed; the completion job later finds `X` settled); `sent` or `unconfirmed` → `AckAttributed` (`unconfirmed → acked` is A7's late ack). Not attributable → no `input_id`; `X` `sent` → `AckNotAttributable` (`unconfirmed`); `sending` or `unconfirmed` → unchanged (the window, §2.7, ends a `sent` input that no attributable hook acks).

An input whose `user_message` names it is always `acked`, and a hook taken in before its input's unit completed acks nothing (SB4, L-6). `competing` is the open job's record of a gate-closing human write (`attach`, `key`) after the launch's last turn start: its submission, if any, is unknown history, so the input stays `unconfirmed` (mvp §2.3 "Ack"; formal-specs §3's case: a human submits `P`, its hook is delayed, the owner asserts readiness, a dispatch of `P` is not submitted). The open job runs only with no unsettled human unit (§2.6), so the projection it reads holds every human write the writer started. A `key` write after `X`'s dispatch is a counted `Human` write after `s` (A17); a human write during `X`'s unit is queued behind it and is such a write too, so a hook whose intake follows it acks nothing (A8).

### 2.6 Keys, Human Writes, Cards

**Key encoding** (`core::input::key`, new): `KeyToken` is one of `enter` (`\r`), `escape` (`\x1b`), `tab` (`\t`), `backspace` (`\x7f`), `ctrl_c` (`\x03`), `up`/`down`/`right`/`left` (`ESC [ A`… or, under DECCKM, `ESC O A`…), or `{ "char": c }` for one printable ASCII scalar; `encode_keys(tokens, app_cursor)` concatenates them into one `Bytes` part, 1 to `MAX_KEYS` (32) tokens. `Capabilities::card_nav_keys` lists the tokens that move a dialog's selection without answering it: `up`, `down`, `left`, `right` for all four rows (PR 13 and PR 14 may change a row). Keys are VT input on both OSes; ConPTY's input parser turns them into key events, as it does for `win_keys` text (input-encoders §2.5 rule 2's source).

**Card memory.** `SendLaunch.cards` holds one small entry per card (its `approval_id` and `human_at`). A card resolved by its evidence drops its entry at that hook's `finished`; a card a turn boundary supersedes, or one whose resolving hook finishes before the hook that opened it (the opening hook's `finished` then inserts the entry late), keeps its entry until a card key finds it closed or the launch's send side is removed at the worker's exit, so the map holds at most one entry per card seen during one launch. A stale entry grants nothing: the key's read refuses a card the store holds closed (`card_closed`).

**Human units.** Every `Key`, `CardKey`, and `Attach` unit (PR 11 submits attach units the same way) is submitted inside `with_session` with `human_unsettled` incremented just before `submit` (decremented at once if `submit` fails), and a `Completion` that sends its record to the driver and nothing else. `L`'s worker is the one owner of these records: in `record.seq` order it appends one `human_write { launch_id, origin: record.origin.human_write(), approval_id }`, keyed `derived:human_write:<launch_id>:<record.seq>` so a retried job finds the existing event, for `Written` or `Incomplete` (bytes may have reached the CLI, any `bytes_written`) and nothing for `NotStarted`, then decrements `human_unsettled`. A job that is not recorded is tried again on the next pass, and the launch's later human records wait behind it; the exit job records the ones it copied into `exit_set` (§2.3 "After exit"). The projection then advances `last_write_seq`, and for `attach`/`key` `last_human_write_seq` (event-store §2.6). So after a raw key only evidence of a later turn or `ready` reopens the gate (`gate`'s `EvidenceOfSameTurn`, A11, A20), however late a same-turn evidence is committed; after a card key, which answers a dialog rather than the composer, the turn's next evidence reopens it (A19, mvp §2.3). While `human_unsettled` is above 0 no input opens (§2.3 step 1).

**`key`'s effect** (owner only, mvp §8 "Also decided"). A key reads its own state:

1. `live(thread, L)` → `None` → `no_live_launch`. Load `L`'s fence word; unfinished intakes or the closed value → `key_not_written` (a hook is being taken in and may close the card).
2. Read `L` and, for a card key, the card, on a blocking task with `settle_before` until now + 1 s (not in time → `key_not_written`). `L` not `running` → `no_live_launch`; the card not open → `card_closed`. A card key also needs `SendLaunch.cards[approval_id]` with a `human_at` (none: the card's observation had no reliable facts or showed `human_running` → `key_not_written` until a new `approval_requested`).
3. `with_session(clock.real(now + 1 s), …)`: read `modes()`, encode with its `app_cursor`, and submit `WriteUnit { origin: Key | CardKey { approval_id }, parts: [Bytes] }` with `Guard { not_after: clock.real(now + 2 s), fence: Fence { word: L.fence, expect: <the word of step 1> }, basis, recheck }`, where a card key's `basis` is `Basis { seq: human_at, counted: {Human} }`, the human writer position at the observation that showed the card: any key or attach unit that started after that observation, an earlier card key for the same card included, may have answered or changed the dialog before any hook, so it refuses every later card key for that card (`WriteSinceBasis`, zero bytes) until new card evidence (a new `approval_requested`) arrives; one card key request carries navigation tokens and at most one deciding token, last (§2.2); the recheck refuses when `ctx.modes.app_cursor` differs from the encoded one (`modes_changed`), and the writer's boundary refuses a later mode change. For a raw key the fence is also set: no key is written over a state a hook changed after the effect read it. `Busy` or a `SubmitError` → `key_not_written`; `Gone` → `no_live_launch`.
4. Await the worker's report for this unit with `settle_before` until `not_after` + 1 s: `human_write` committed → `KeyResult { outcome: written | incomplete, bytes_written }`; `NotStarted` → `key_not_written`. No report by then: `WriteTicket::try_cancel()`, which never waits for the queue lock: `Some(true)` → `key_not_written` (it never dispatches); `Some(false)`, or `None` because the writer holds the queue lock (it may be permitting the unit) → `{ outcome: pending, bytes_written: null }`. The worker records the unit whatever the effect returned.

A key is not gated (it is how the owner clears a startup prompt, mvp P-12). Only `card_closed` and `no_live_launch` say the target is gone; every other refusal is `key_not_written`, after which a retry may succeed.

### 2.7 Timers

`SendTick` is registered as a `TickStep`; its `tick(now, live)` returns no job and forwards `now` and the live launches to the driver through a `watch` channel (never blocks). Each worker runs its launch's timers on the monotonic clock from the instant of the event that starts them, and decides each in a job that re-validates from the store:

| Timer | Start | Job |
|---|---|---|
| Gate timeout (`GATE_TIMEOUT` 60 s, A15) | the input's queued instant: the worker's first read of the input as `queued` (the clock read right after that read, before the pass's jobs), on the pass the commit's stream notification wakes (`send` keeps one transaction, mvp §2.4, so it hands over no instant); this is later than the commit by that pass's latency, so the cause comes at least 60 s after the input was queued | raise `input_gate_timeout(input_id)` once (stays `queued`, zero bytes). Before the job the worker tries one VT snapshot, `LiveLaunch::snapshot_before(now + 250 ms)` (§2.9 D2); a snapshot it gets is appended as `vt_snapshot_taken` (`grid` through `prepare_content`) in the same job; `Busy`, `Gone`, or `VtUnavailable` raise the cause without one |
| Ack window (`ACK_WINDOW` 30 s) | the completion job's commit (the clock read right after its SQLite `COMMIT`, a `CommitStamp`), or `CommittedStart.at` for the positional input; for a positional input it runs only while neither startup cause is active (mvp §2.3), which its job reads again | `AckWindowExpired` (`unconfirmed`) |
| Settle (`SETTLE` 2 s) | §2.4 | §2.4 |
| Dispatch wait, write stall (`WRITE_STALL` 30 s) | `submitted_at`; the writer's `started_at` of the unit | §2.3 step 5 |

A timer is decided on the first pass after its bound (passes run at least every tick, 1 s); a job that cannot be recorded is tried again on the next pass of its own launch.

### 2.9 Changes to Earlier Interfaces

**Changes to 10a1 interfaces** (sup §2.11). 10a1 part 2 implements its merged design as written; D1–D3 are made by the 10b implementation PR, and D4 is 10b's own:

| Id | Change | Reason |
|---|---|---|
| D1 | `supervisor::record` takes a job with a value, `Job<R = ()> = Arc<dyn Fn(&mut WriteTx<'_>) -> Result<R, JobError> + Send + Sync>`, and returns `R` from the attempt whose commit the writer confirmed (`write_with` already returns it, `ctx.rs:190-196`) | the open job and `ready` hand their committed result (attempt seq, basis, fence word, refusal) to the caller; a value set inside an attempt that later rolled back would let a submit follow an uncommitted `sending` |
| D2 | `LiveLaunch::snapshot_before(&self, sup, deadline) -> Option<Snapshot>` (sup §2.11): starts a blocking task, which, once running and before `deadline`, takes the op lock with one `try_lock`, takes `Session::screen` (pty-runtime §2.2), releases the lock, and copies the screen with `Screen::snapshot(clock.real(deadline))`; the caller awaits the join with `settle_before` until `deadline`. `None` for a held lock, no session, a failed VT or its lock not taken in time, or no answer in time (the gate timeout only needs whether a snapshot was taken) | the copy waits for the VT lock in a sleep loop and walks the grid (`session.rs:37-49`), which `with_session`'s inline `f` may not do; the op lock is held only while the screen is taken, and a task waiting for the blocking pool holds no lock, so a snapshot never carries the op lock into its wait or its copy. ## 3. Decisions

Numbered SB (send-side decision). "Public" marks owner-visible contracts.

**SB1. Hole b, a zero-byte attempt (A31).** Before, `sending` advanced `last_write_seq`, so after `RecheckFailed` the gate stayed `WriteAfterEvidence` until new evidence or `chaldea ready`. Example: on an idle CLI, `a` opens, a hook is taken in before its permission (`FenceMoved`) or `with_session` is `Busy`; `a` is `cancelled` with zero bytes, and `b` would never be sent, since an idle CLI sends no `Stop`.

| Option | Gain | Loss | Reversibility | Cost |
|---|---|---|---|---|
| A. Keep, with an immediate notice on the next queued input | no store change | a new public attention cause (core, reducer, model); the owner must act on every transient refusal | additive | medium |
| **B. A zero-byte attempt leaves `last_write_seq` as it was** | `b` opens at once when the gate still holds; stale evidence stays closed through SB3's open-time basis check | two projection columns, an apply rule, schema v3 and a projection rebuild | rebuild | medium, internal |

**Adopted: B** (mvp §4 PR 10 (b)'s second option: tell attempts from started writes, leave out only attempts known to have written zero bytes; intervening writes, stale evidence, and unknown outcomes still close). Internal; owner-visible effect: a transient refusal no longer blocks later sends. Changes it: a refusal cause that should keep later sends waiting.

**SB2. `readiness_evidence: none` withholds Claude's `SessionStart` (A37).** Adopted, as the model assumes (`kindAllowed`): `OwnerOnly` exists to stop automatic sends where the adapter's evidence is not trusted, and mvp §2.3 says "only `chaldea ready`". Alternative: `SessionStart` counts in every mode (mvp §2.7 lists it first) — a mode named "none" would still send at startup. No row uses `OwnerOnly` in the MVP; PR 13 may. Internal now; public with the PR 13/14 column.

**SB3. The gate's evidence basis (A9, X3).** Adopted: the basis is sampled at the evidence's own intake (§2.4's table), and the open job refuses a stale basis (position moved past it) as `WriteAfterEvidence`, so the input stays `queued` instead of being cancelled at dispatch. Alternatives: the settle basis at the `Stop`'s intake (a reply to a query the CLI sends after its turn would cancel every send; the model takes the basis at the completion, `ready(ev, stop)`); no staleness check at open (each send after an evidence-less reply is cancelled). Internal.

**SB4. Ack of an input still `sending` (A10, X4, A16, A17, B2, C4).** A hook can be taken in before the completion job commits. Adopted: the intake facts carry `Dispatch.written`, which the unit's completion sets only for `Written`, and an attributable hook acks a `sending` input only when it is set, applying `WriteCompleted` and `AckAttributed` in the hook's job.

| Option | Gain | Loss | Reversibility | Cost |
|---|---|---|---|---|
| **A. `written` in the intake facts** | `interpret` stays data-only; no candidate kept between jobs; `user_message.input_id` names only an `acked` input; a hook before the Return was written, or with an `Incomplete` write, acks nothing | a hook taken in after the last byte was accepted but before the completion ran acks nothing, so that input ends `unconfirmed` (L-6) | model change (§7) | small |
| B. The model's candidate: keep a match while `sending`, apply it after `Written`, drop it after `Incomplete`, ambiguous on a second match | as the model | the candidate must outlive the hook's job: a new annex or memory written from `interpret`, which hook-ingest §2.6 forbids | — | medium |
| C. Mark the candidate with `user_message.input_id` and apply it in the completion job | no new state | an `Incomplete` write or an exit leaves a `user_message` naming an input that ends `unconfirmed`; a second match overwrites the first | — | small |

A keeps the model's results for every ordering in which the completion precedes the intake, and fails closed (`unconfirmed`, never a wrong `acked`) for the others. **Public** in effect (which sends end `acked`); changes it: PR 13's captures narrowing `prompt_matches`, or a measured share of hooks inside L-6's window.

**SB5. The positional anchor and what counts against it (A35).** Adopted: the anchor is `Published.reference` (sup §2.3 step 5); `Human` and `Input` writes above it make the ack non-attributable; `Reply` writes do not. Examples: Codex answers its startup queries after publication (replies above the anchor) → still attributable; the owner attaches and types before the `UserPromptSubmit` → not attributable; a reply before publication is below the anchor either way. Reason: the prompt is in argv, not on the PTY, so a reply cannot join or displace it, contains no CR or LF (pty-runtime §2.5's reply table), and cannot be text a matching prompt contains (`check` rule 1 refuses ESC). Rejected: counting replies (`trace_finding_positional_vt_reply`: every Codex launch whose queries are answered after publication would leave its first prompt `unconfirmed`, closing the gate until the owner resolves it). Sends keep `ClassSet::ALL` (mvp §2.3). Public in effect.

**SB6. `ready`'s meaning and shape (C3). Public.** Adopted: §2.4 "Owner assertion", accepted only for the current, bound, `running` launch of an open thread, with optional `expected_launch_id` (the CLI pins it from `GET /api/threads/{thread_id}` as `resume` does, sup SD16), the basis sampled in the effect. Alternatives: no pin (an assertion about one CLI lands on its replacement after a resume); sampling in `prepare` (it has no launch id without a store read). Changes it: a client that needs to assert for a starting launch.

**SB7. Hooks against first write permission: the fence (A33, mvp §2.10). Public in effect.** Adopted: one fence word per launch, advanced at every hook intake and compared by the writer under its queue lock at the last check before a unit's first permission, for sends and keys alike (§2.3). A send or key whose state was read before a hook was taken in is refused with zero bytes: a send is `cancelled` (visible, never resent; SB1 lets the next input open), a key answers `key_not_written`. Example: a card key's Enter passes every check, a `Stop` is taken in and will close the card; the writer sees the moved word and writes nothing, where before the Enter could land on the composer. Alternatives: a mirror of the store read by a recheck closure (a hook committed but not yet mirrored admits a prompt and Return onto a just-opened approval dialog, or a key onto a closed one); two atomics compared by the daemon before submission (a hook taken in between that comparison and the permission is not seen); a store read on the writer thread (blocks every PTY write on the reader pool). The fence orders a hook's intake against the unit's logical permission, not against byte delivery (§2.3). For a card key, a change the owner's own earlier key or attach input made before any hook is caught by binding the card key to the human writer position at the card's observation (§2.6); after any human unit, the card needs new card evidence. Rejected: a basis read per key request (a second request made after the first key was written reads the first key's position and passes). The cost is that a hook taken in between an open job and its permission cancels that send (the window's length is not measured); the owner sees the `cancelled` input, with zero bytes written, and sends again. This replaces the send recheck and its mirror. Changes it: owner reports of sends cancelled by unrelated hooks.

**SB8. Wire types and codes of §2.2. Public.** Adopted as listed; every result field always present (`payload.rs:3-4`). `send` returns `rejected` with its reason instead of a 400 so the PWA shows the input (PR 19) and an agent sees why; `origin` is a client claim, informational only. One `input_state` code for both input commands. Changes it: a client that must tell the two refusals apart (split the code, additive).

**SB9. `key`'s token set and result. Public.** Adopted: §2.6's tokens and `KeyOutcome` `written | incomplete | pending`; `written` and `incomplete` are answered only once the `human_write` committed, and `pending` says only that no recorded outcome was known at the reply (the worker records it later): the effect's `try_cancel()` returned `Some(false)` (dispatched or already settled) or `None` (the writer held the queue lock and may be permitting the unit; the effect never waits for it). Alternatives: `started` for that case (claims a dispatch the writer does not promise); the effect recording `human_write` itself (two recorders, and a `Late` completion consumed by the effect is lost to the other); raw bytes (a client could send ESC sequences the keypad does not need, and arrows would ignore DECCKM); a full key-name table now (unused before PR 19's keypad). Additive later.

**SB10. The decoder seam (PR 13/14 boundary).** Adopted: `SupervisorHooks` owns state effects and turn marks; `HookDecoder` only reads payloads; memory learns of a delivery through `IntakeProbe::finished` after its commit (§2.9 P2). Alternative: each adapter writes state events itself (attribution and gate rules duplicated per CLI). Internal.

**SB11. F5 to PR 11.** No 10b path resizes; attach is the first caller of `Session::resize`, and pty-runtime §2.2 leaves resizing during a unit to it.

**SB12. Timers on the monotonic clock, from the event's own instant.** Adopted for gate timeout, ack window, settle, dispatch wait, and write stall: each starts at the instant of its event (the worker's first read of a queued input, the completion's commit, the mark's commit, the submission, the writer's `started_at`), kept in `SendLaunch`; per-launch workers keep one launch's retries from delaying another's deadline; tests drive `Supervisor::tick(now)`. Alternative: store stamps (`recorded_at`) as `buffer::expire` — a forward step of the wall clock would settle a `Stop` early and open the gate, and the input rows carry no stamps (`rows.rs:73-86`). Internal; a timer fires on the first pass after its bound, never before it.

**SB13. Claude's `--prompt` (§2.2).** Adopted: a queued input at reservation, for `spawn` and `resume`. Alternative: keep 400 (Claude launches need a second command). Public: `spawn` and `resume` accept a Claude prompt. Changes it: none foreseen.

**SB14. Which turn a `Stop` ends (A36). Public in effect.** Hooks carry no turn id the daemon can rely on, so a late `Stop` of turn `P1` taken in after `P2`'s `UserPromptSubmit` looks like `P2`'s end. Adopted: settle only on a `Stop` whose turn start follows an end the daemon saw (§2.4), and otherwise wait for `ready` or another eligible evidence. Example: the owner runs `ready` before `P1`'s `Stop` arrives, sends `P2`, and `P1`'s `Stop` comes during `P2`; before (counting starts and ends), the count balanced and the next send could be written into the running `P2`; now `P2`'s end does not open the gate, the owner runs `ready` once (the gate timeout shows the waiting input after 60 s), and later turns settle by themselves. Alternatives: the latest delivery only (the late `Stop` qualifies); counting starts and ends (a `ready` or a lost `Stop` resets or skews the count); a decoder-supplied turn id (none of the four rows is known to carry one; PR 13/14 may add it and narrow L-9). The purpose holds: apart from L-11, a send is written only when the gate's evidence is the current turn's, a wait is visible to the owner, and nothing is resent. Rejected for L-11's case: settling only on an end attributable to the current turn by an id in the payload — no row's `Stop` is known to carry one, so every turn would need `ready`, against mvp D8's choice of `Stop` and settle by default; PR 13/14 narrow L-11 if a payload carries a turn id.

**SB15. A running unit blocks the next send until it ends (F3, pty-runtime §2.3 "Started units").** Adopted: `WRITE_STALL` runs from the first permission (the writer's `started_at`) and only shows the input `unconfirmed` with attention; the next input opens, and `ready` or any idle evidence is accepted, only after the unit's record or the seal, even if the owner resolves the stalled input first (`ready` answers `unit_running` meanwhile). A unit that never reaches the writer is cancelled after `DISPATCH_WAIT` + 1 s. Reason: a permitted unit's remaining bytes may still reach the CLI at the same writer position, so a second input dispatched meanwhile, or a basis taken meanwhile, could not be told apart from them. Example: `a`'s first write is held after its permission, the owner dismisses `a` and runs `ready` on the still-empty composer; the held write then delivers `a` as a new turn, and a `b` sent on that `ready` would land in it; now `ready` is refused until `a`'s record, after which `a`'s own hooks or a new `ready` decide. Alternatives: start the stall at submission (turns a certain zero-byte refusal into "unknown"); let resolution reopen the gate (the next prompt may interleave with the first's bytes). Public: `unit_running`; a send behind a blocked unit waits (gate timeout after 60 s) until the CLI reads its input or the owner stops the thread.

## 6. Tests

Unit tests drive `FakePty` (`hold_writes`, `wait_entered`, `fail_writes_after`, `FakeScript.startup_output`, `ProbePoint::RecheckEntered`, `PauseEntered`, `Dispatching`), the store, `Supervisor::tick(now)` with injected instants (converted with `clock.real` where they reach pty-runtime), and `FakeDecoder`, which maps FakeCli payloads (`hook_event_name`, `prompt`, `tool_use_id`, `tool_name`) to `HookFact`s. Integration tests run the daemon with FakeCli and the native runtime as `crates/cli/tests/hook_e2e.rs` does, with `FakeDecoder` installed through `SupervisorConfig`.

**FakeCli `stall` mode** (new): prints a fixed screen and sleeps until `--max-life-secs`, sending no hook.

**FakeCli `submit` mode** (new): sends a `SessionStart` at start (so the launch binds), then reads its stdin and rebuilds the text from the row's documented encoding (input-encoders §2.4–§2.5): with DECSET 2004 on, a bracketed paste kept whole, line breaks included; for the Codex Windows row, keyed input whose newline sequence is a line break. A CR outside a paste submits: it sends one `UserPromptSubmit` whose `prompt` is the rebuilt text in the row's expected form, then a `Stop`. P-1's FakeCli check uses it on every row, so the prompt the hook reports is the one the PTY delivered.

**Host speed.** Timers run on instants passed to `Supervisor::tick(now)`; writer races are held with `wait_entered`, `park`, and pause points; intake facts are taken while the test holds the writer at a probe point; hook commits are held at hook-ingest's test points (`after_intake`); a unit's `Completion` can be held by a test hook in `SendLaunch`; no test sleeps in place of an event. Native tests read the published port (`client::discover`).

**Windows CI.** Every `supervisor::send::`, `key::`, `store_open::`, and `supervisor_e2e::` test runs on `windows-latest` (`scripts/windows-tests.ps1 -Lane Cargo`); the Codex Windows row is exercised on both runners through `HostOs::Windows`.

**Mutation check.** Each mutation of §5.2 is applied by hand before merging and the named test seen failing.

**Completion commands**: sup §6's.
