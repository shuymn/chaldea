# Design: Daemon Lifecycle (MVP PR 8)

Status: implemented in `crates/daemon/src/lifecycle` and `crates/cli/src`. Scope is the PR 8 row of `docs/mvp-design.md` §4 (cited as "mvp §N"): `chaldea daemon run`, `daemon start` (detached: a launchd job on a macOS GUI host, `setsid` without a GUI domain, `DETACHED_PROCESS` on Windows), `daemon stop`, the parent kill-on-close job check on Windows, and the obligations handed to PR 8 by mvp §4 "PR 8", `docs/design/event-store.md` (cited as "store §N") §2.4, §4, §5, `docs/design/http-surface.md` (cited as "http §N") §2.2, §2.4, §2.10, §2.11, §4, and `docs/design/formal-specs.md` §7.4 "PR 8". It also adds `chaldea open` (mvp §2.5 "Secrets", http §8 D12), the first client of the files this PR defines.

**What PR 8 decides and what it leaves.** PR 8 owns the process: its CLI entry, the state directory and the files in it, the single-instance lock, discovery, the port, the owner token file, startup order, the one shutdown decision and its budget, detaching and the readiness handshake, the Windows parent job check, the process-wide signal state, logging, and the panic hook. It does not decide hook ingest (PR 9), launches, the supervisor, or the restart scan of launches and inputs (PR 10), attach (PR 11), the PWA (PR 18), or the doctor (PR 21); for each it provides the seam of §2.14 and §4. No public type of `crates/core` changes, and no public contract of mvp changes; the public names this PR adds are §8 D14.

**Commitments from PR 6 and PR 7 this design keeps.**

1. `Store::shutdown` blocks its thread; the daemon calls it off the executor's worker threads, once, inside the one shutdown budget, after `ServeHandle::shutdown` (store §4 row 8; http §4 row 8).
2. The single-instance lock is released in-process only when the store's report says both `readers_returned` and `writer_exited` (an abandoned reader still holds a SQLite connection and its snapshot); otherwise the process exits holding it, and the OS releases it (store §5 "Normal shutdown").
3. The DB files are touched in-process only when both `readers_returned` and `writer_exited` hold; PR 8 touches them in no case after shutdown (no delete, copy, or checkpoint of its own).
4. `receipts_mark_unknown_after_crash` runs before the HTTP server serves (mvp §2.4 "Restart"; formal-specs §7.4 "PR 8").
5. Every `LifecycleSink::store_fatal` (`CommitUnknown`, `WriterGone`, `Failed`, `ReceiptUncompleted`, `LaunchUnrecorded`) stops the daemon (http §2.2), each variant covered by PR8-CL-7's per-variant test. The exit reason reflects the fatals reported before the coordinator's final read of `gate.worst()` (§2.8); one reported after that read may be missing from it (`docs/design/supervisor.md` L-8).
6. Every diagnostic the process writes goes through `trace::redact_secrets`, and the panic hook omits the panic payload (http §2.10).

## 1. Goal and Dependencies

**Goal.** A `chaldea` binary whose `daemon run` holds one state directory exclusively, reconciles the store before anything can reach it, serves PR 7's HTTP surface on `127.0.0.1:<port>`, publishes where it listens and an owner token for the user's CLI, and ends on every trigger through one shutdown with one budget, releasing the lock only after the store's writer and readers have finished; `daemon start` runs it detached from the launching terminal (macOS GUI host: outside the terminal app's launchd job and session; macOS without a GUI domain: in its own session; Windows: outside its console and every job) and reports readiness or the reason it failed within a deadline; `daemon stop` stops it, during startup too, through an OS mechanism. Every claim of §6 has a test on `macos-latest` and `windows-latest`, or names why it is single-OS or a real-host check.

## 2. Types and Functions

Names may change in review; shapes may not.

### 2.1 Threat Model and Rules

**Threat model.** The MVP assumes a host used by **one OS account**. Processes of that account are trusted: they can already read `owner.token`, signal the daemon, and attach a debugger to it. Other OS accounts on the same host are outside the model. Consequences, stated as known limits (§6.2) with the reopen condition "Chaldea runs on a host shared with other OS accounts":

- The CLI does not authenticate the server: Host validation protects requests that arrive at Chaldea, but a process of another account that holds the saved port while Chaldea is stopped, or after the CLI's liveness check, can receive the CLI's Bearer token, and can serve a page at the PWA's origin that reads the origin's IndexedDB owner token on reload. A server-authentication handshake for the CLI and a revised browser credential are the additions that close this; both are reversible additions. **PR 18 must not treat the stable origin (§2.6) as an authenticated server**; its design states its browser-credential assumption against this section.
- The pair code may appear in the browser launcher's process arguments while `chaldea open` runs (§2.13). Only the account's own processes see them in the model, and those can already read `owner.token`, so the model accepts it for the same reason it accepts the token file.

Measures that need no protocol are taken anyway: the state directory and its secret files are private to the account and verified so (§2.4), and files are adopted only on evidence and never through links (§2.4).

**Rules.**

1. **The OS decides exclusivity and liveness.** One daemon per state directory is an OS file lock (L1), released by the OS at process exit whatever happened; a published record is used only while the lock is held and its process is alive. Stopping is an OS signal (Unix) or an event in the account's global namespace (Windows), never a request the HTTP stack must still be able to serve.
2. **One coordinator decides the shutdown.** Every trigger (signal, stop request, fatal store outcome, panic, a failed startup step) calls `ShutdownGate::request`; the first call fixes the cause and the cutoff together, and nothing moves the cutoff afterwards (§2.8). A Windows console end is not a shutdown but a crash exit (§2.8). One task, the coordinator, runs the shutdown; it never interrupts the startup task, which stops at its next step boundary (§2.7).
3. **Order is code, not discipline.** Startup is one task whose steps run in a fixed order; the listener does not exist before reconciliation committed (§2.7). Shutdown is one function: startup join, HTTP, participants, store, lock (§2.8).
4. **Nothing is adopted, removed, or overwritten without proof** (§2.4): the state directory is ours only when we created it, adopted it empty, or it carries our marker, and it must be private; inside it, names are opened without following links; a file is replaced only by an atomic rename of a temporary this run created; the discovery record is removed only when it still names this instance. The lock file is never removed, truncated, or written.
5. **Lifecycle resources outlive every unwind.** `InstanceLock`'s `Drop` never releases the lock (the handle is leaked; only the OS releases it at exit); the startup task owns what it creates and hands it to the coordinator only by returning it; the runtime is never dropped while work may remain (`shutdown_background`); every panic on the startup, coordinator, or main path is caught (§2.9). The only in-process release is `InstanceLock::release`, called once by the coordinator when §2.8 step 6's conditions hold.
6. **Every wait has a deadline** (§5 "Waits"), and every ending ends the process: `dispatch`'s last act is `std::process::exit`. One call has no bound of ours: `ShellExecuteExW` in `chaldea open` returns when the shell has handed the URL over; `open` is a foreground command the user can interrupt, and the daemon never makes this call.

### 2.2 Process Layout, CLI, and `pty-runtime::host`

**Binary.** `crates/cli` is a library and the binary `chaldea` (hook-ingest §1): `main.rs` is one call, `chaldea_cli::dispatch(argv, Stall::Off)`, and `dispatch` is the single entry. It runs, in this order, before any thread exists:

1. `argv[1] == "hook-emit"` → the emitter (hook-ingest §2.13, mvp §3 "Single binary"), before process setup, the runtime, or any configuration; it never returns and exits 0. `dispatch(&[OsString], Stall) -> !` takes the emitter's test seam (`Stall`, hook-ingest §2.13) as its second parameter; `main` passes `Stall::Off`. That the branch comes before `prepare_process` is observed on macOS by `hook_emit::hook_emit_runs_before_process_setup`: while its first attempt waits for a reply, the emitter has two threads (main and watchdog, read with `ps -M`), and `prepare_process` would add the log thread; its other effects (the `SIGCHLD` disposition, the signal mask, the panic hook, which the emitter replaces) have no outside probe (CL-17).
2. macOS: when `argv[1..4]` is exactly `["daemon", "run", "--from-launchd"]` (the shape the starter writes into the job's `ProgramArguments`, §2.10) and the whole `argv` passes `daemon run`'s usage checks (it parses, and `--detached-child` comes with a `--ready` that is `stdout` or an absolute path), `host::leave_launchd_job()`, whose fork needs a single-threaded process. An invocation that fails them never forks: the job's process itself reaches step 4 or `daemon run` and exits 2 (binary test `daemon_macos::invalid_launchd_invocation_exits_2`).
3. `lifecycle::prepare_process` (§2.3).
4. `Cli::try_parse_from(argv)`; a `clap::Error` is rendered with `render()`, passed through `log::diag` (§2.13), printed to stderr (or to stdout when `use_stderr()` is false, as for `--help`), and the process exits with `exit_code()` (2 for usage errors, 0 for `--help`; binary test `daemon_run::help_goes_to_stdout`). clap never prints on its own.

```
chaldea [--state-dir <path>] daemon run   [--port <n>]
chaldea [--state-dir <path>] daemon start [--port <n>]
chaldea [--state-dir <path>] daemon stop
chaldea [--state-dir <path>] open [--print-url]
```

`--state-dir` falls back to `CHALDEA_STATE_DIR`, then to the default (§2.4), and is made absolute against the caller's working directory (`std::path::absolute`) before any use, so the starter and the detached child name the same directory. `daemon run` takes hidden flags only `daemon start` passes: `--from-launchd` (macOS, first after `run`), `--detached-child`, `--ready <channel>`. Exit codes are `ExitCode` (§2.8).

### 2.3 Process Setup and Per-Run State

**Once per process** (`lifecycle::prepare_process`, called by `dispatch` after the `hook-emit` branch and before argument parsing (§2.2), and first in every test helper process; never in an in-process unit test):

1. `host::reset_process_signals()` before any thread exists (§2.11). On Windows it re-enables Ctrl-C processing when the process has a console: a parent that ignores Ctrl-C (`start /b`, a `CREATE_NEW_PROCESS_GROUP` creation) hands that attribute down, and a foreground daemon must still stop on Ctrl-C (CL-9).
2. The panic hook (§2.13), installed with `std::panic::set_hook`.
3. The log subsystem: the global `tracing` subscriber and the `daemon-log` thread (§2.13).

Each is guarded by one `std::sync::Once`, so a second call does nothing. A failed signal reset is recorded, and `run` then refuses to start a daemon: exit 1, reason `internal`, `NeverTaken`, with "the inherited signal state could not be reset: <error>" (a daemon whose children could be reaped by the kernel, or that cannot receive its stop signals, never serves).

**Per run.** `run` creates its gate and registers it in the process's active-gate slot (`static ACTIVE_GATE: Mutex<Option<Weak<ShutdownGate>>>`), which the panic hook reads; it also owns the process log target (stderr in the foreground, the run's `daemon.log` when detached, §2.13). `run` is called once per process: by `dispatch`, or by a helper process in tests. Unit tests use `run_isolated`, which registers nothing process-wide, so any number of them run in parallel in one test process. Tests that touch process-wide state (the hook, the subscriber, signal state, signals, consoles, jobs) or that leave a never-returning task or a leaked lock behind run in helper processes (§7).

### 2.4 State Directory and Its Files

**Location.** `--state-dir`, else `CHALDEA_STATE_DIR`, else the default: `$HOME/.chaldea` on macOS and `<FOLDERID_LocalAppData>\Chaldea` on Windows (§8 D11). `state_dir::resolve` is used by every subcommand, so a client and the daemon agree.

**Private trustees.** One definition, used by every privacy check and by P-8: on macOS, the effective uid (root is not checked: it can read anything); on Windows, the user's SID, `SYSTEM`, and `BUILTIN\Administrators`, plus, on directories only, `CREATOR OWNER` on an inherit-only ACE (one that grants nothing on the directory itself; an effective `CREATOR OWNER` ACE refuses) and `OWNER RIGHTS`. "Private" means owned by the user and granting nothing to anyone outside this set.

**Creation and adoption** (`state_dir::prepare`, daemon only; clients never create it):

1. The absolute path loses its trailing separators and nothing else (a root keeps its own; no component is resolved, so a Windows verbatim path keeps its `..` literal and is refused as Windows refuses it), so `<link>/` names the link itself rather than its target; then `symlink_metadata` of the final component: a symlink or a Windows reparse point is refused (`FailReason::StateDir`); links in ancestors (such as macOS `/var` → `/private/var`) are allowed.
2. Absent: `host::create_private_dir` (Unix `mkdir` with mode `0700`; Windows `CreateDirectoryW` with an explicit owner and protected DACL `O:<user SID>D:P(A;OICI;FA;;;<user SID>)(A;OICI;FA;;;SY)`; the explicit owner keeps the privacy check's owner rule true when an elevated token's default owner is `Administrators`), then the marker (step 4). Only the last component is created; its parent must exist. On Windows every creation names its path in the `\\?\` form (`\\?\UNC\` for a share) of the absolute path, so a state directory or file beyond `MAX_PATH` is created as well as inspected (std's own calls add that form for long paths); nothing refuses a long path up front. `AlreadyExists` (a concurrent first start) continues with step 3 on what is there.
3. Present: `host::privacy(dir, Directory)` must be `Private`:
   - **macOS:** owned by the effective uid (checked first, so an ownership failure reports `NotOwned`), no group or other mode bits, and no extended ACL entry of type allow (`acl_get_link_np`, L20; deny-only entries such as the home directory's "everyone deny delete" pass).
   - **Windows:** owner is the user's SID; the DACL is present, and every allow ACE names a private trustee; any other allow ACE (`Users`, `Everyone`, another account) refuses. The default profile ACL and the DACL of step 2 both pass.
   Anything else refuses with a message naming the check (e.g. "run `chmod 700 <dir>` and remove its ACL entries") and nothing is changed: an existing directory is never chmodded or re-ACLed.
4. **Marker:** `<dir>/CHALDEA_STATE` holding `{"chaldea_state_dir":1}`. A directory is adopted only if (a) step 2 created it, (b) it is empty, ignoring unfinished marker temporaries (regular files named `.CHALDEA_STATE.tmp-*`, and one that a concurrent first start removed between the listing and its inspection; a link, directory, or other entry of that name makes it non-empty), or (c) it carries a marker that is a regular file with that content. For (a) and (b) the marker is published without replacing anything: write `.CHALDEA_STATE.tmp-<instance>` with `create_private_file` and `sync_all`, then `fs::hard_link` it to `CHALDEA_STATE`, which fails if the name exists (L4), then remove the temporary. A temporary is removed only by the call that created it: a `create_private_file` that fails with `AlreadyExists` leaves the existing entry alone. `AlreadyExists` from a concurrent start means a complete marker is there: it is read and validated as in (c). A crash leaves at most a temporary, which never makes a directory unadoptable. A non-empty directory without a valid marker is refused ("not a Chaldea state directory"), so a mistyped `--state-dir ~/Documents` never adopts unrelated files.

The canonical path is taken after these checks. From here every file operation names a child of the verified directory; because the directory is private, only the account's own processes can create entries in it after the check, and they are trusted (§2.1).

**Files** (directly in the state directory):

| Name | Content | Written by | Replaced | Removed |
|---|---|---|---|---|
| `CHALDEA_STATE` | the marker | `prepare` | never | never |
| `.CHALDEA_STATE.tmp-<instance>` | the marker's temporary | `prepare` | — | by `prepare` after the link; a crash leaves it |
| `daemon.lock` | empty | created if missing by `InstanceLock::acquire` (`open_no_follow`, mode `0600`), never truncated or written | never | never |
| `daemon.json` | discovery record (§2.6) | the lock holder only | atomically, at `starting` and at `serving` | by the lock holder at shutdown, only when its `instance` is this run's |
| `port` | the saved port in decimal + `\n` | the lock holder only, once it serves (§2.6) | atomically | never |
| `owner.token` | the CLI's owner token (`chd_…` + `\n`) | the lock holder only, before serving | atomically, when absent or invalid (§2.13) | never |
| `daemon.log`, `daemon.log.1` | log and panic lines of a detached daemon | the detached daemon, after it holds the lock | `daemon.log` is renamed to `daemon.log.1` (replacing it) at 8 MiB (§2.13) | never |
| `chaldea.db`, `-wal`, `-shm`, `-journal` | the store | `Store::open`, SQLite | — | never (store §5) |
| `.<name>.tmp-<instance>` | a temporary | `write_replace` | — | by `write_replace` on its own failure; a crash leaves it (never removed by a later run) |

**Opening.** Every open of a file in the state directory uses `host::open_no_follow` (or `create_private_file`), and every reader checks the opened handle is a regular file before reading: the lock, the discovery record (daemon and clients), the port file, the owner token, the log, and the marker. On macOS the open is non-blocking (`O_NONBLOCK`), so a FIFO or device under a known name fails the type check instead of blocking the open. The database is opened by SQLite by path, so before `Store::open` the daemon requires, for `chaldea.db` and its `-wal`, `-shm`, and `-journal` sidecars, `host::is_plain_file_or_absent` (refused otherwise, `FailReason::StoreOpen`, "a link where the database should be") and a link count of 1 (`host::hard_links`; a hard link would let a writer outside the state directory reach the store; refused with `StoreOpen`, "<path> has <n> hard links", directing the user to stop every writer of it and make a consistent copy with SQLite's backup before moving it into place).

**Secret files.** `create_private_file` creates with an explicit owner-only descriptor, never inheritance (L22): macOS `O_CREAT | O_EXCL | O_NOFOLLOW` with mode `0600`; Windows `CreateFileW(CREATE_NEW)` with `SECURITY_ATTRIBUTES` holding `O:<user SID>D:P(A;;FA;;;<user SID>)(A;;FA;;;SY)`. It then checks the opened handle with `host::handle_privacy` (macOS `fstat` owner and mode plus `acl_get_fd_np`; Windows `GetSecurityInfo` owner and DACL) before returning it, so no secret is written into a file whose effective access was not verified. Every temporary of `write_replace` is created this way, so `owner.token` carries this descriptor after its rename (a rename keeps the file's descriptor).

**Existing secret file.** `owner.token` is checked at step 6 (§2.7), before any mutation other than the marker and an empty `daemon.lock`: `host::privacy(path, File)` must be `Private`, else the start is refused (`FailReason::TokenFile`, "owner.token is readable by others; its token may be exposed. Removing the file does not revoke the token: revoke it, then remove the file") without reading it. The other files carry no secret; within a marked private directory a file of a known name is ours, and it is still parsed before use (§2.6, §2.13).

**`write_replace(dir, name, bytes)`** — the one way a file other than the lock, the marker, and the log is written:

1. `symlink_metadata(dir/name)`: absent, or a regular file → continue; a link, reparse point, directory, or anything else → refuse (`FileRefused { name }`), nothing written.
2. Create `.<name>.tmp-<instance>` with `host::create_private_file`, write, `sync_all`. A failure here removes the temporary if this call created it (an `AlreadyExists` leaves the existing entry alone) and returns the error; `name` is unchanged.
3. `fs::rename` onto `name` (L4: a std reader holding it open does not block it); with a caller's cutoff, no rename is attempted at or after it and a failure is retried every 50 ms until it; without one, a failure is retried every 50 ms for 500 ms from the first attempt; then the temporary is removed and the error returned; `name` is unchanged. The temporary's name carries this run's instance, which is new for every run, so one left by a crash is never read, written, or renamed by a later run; nothing removes it either (it stays as an owner-only file in the state directory).
4. **The rename is the commit.** Unix: `sync_all` on the directory; a failure is logged as a durability warning ("`<name>` was replaced but may not survive a power loss") and does not fail the call, because the new content is already visible.

### 2.5 Single-Instance Lock

```rust
pub struct InstanceLock { file: ManuallyDrop<File> }   // no Clone; Drop does nothing (the handle is leaked)
impl InstanceLock {
    /// open_no_follow(daemon.lock, read+write, create, mode 0600), then try_lock, retried every 50 ms
    /// within `retry` (2 s) on WouldBlock only.
    pub fn acquire(dir: &Path, retry: Duration) -> Result<InstanceLock, LockError>;   // Held | Io(io::Error)
    /// unlock(), then close. Only the coordinator calls it (§2.8 step 6).
    pub(crate) fn release(self);
}
/// Clients: open_no_follow read-only (never create), try_lock_shared: WouldBlock → Held; Ok → Free (unlock at once).
pub fn probe(dir: &Path) -> io::Result<LockProbe>;   // Held | Free | Missing
```

- **Mechanism.** `flock` on macOS, `LockFileEx` on Windows (L1), on a file that holds no data, because a Windows lock also blocks reads of the range (L2). The lock is per open file description / handle, so a second `acquire` in the same process also gets `WouldBlock` (the tests rely on it). std opens it close-on-exec / non-inheritable, and PR 3's `pre_exec` closes every inherited descriptor anyway, so no child keeps it alive after the daemon exits.
- **Never released by a drop.** `Drop` leaks the handle, so an unwind, an early return, or a forgotten value never releases the lock in-process; only `release` or process exit does.
- **Contention vs I/O.** `WouldBlock` is contention (`Held`, retried for 2 s); any other error (`EACCES`, `ENOSPC`, `EIO`) is `Io`, not retried, and fails the start with `FailReason::LockIo` and the error, distinct from "already running".
- **Retry.** The 2 s is the CLI's allowance for a client's momentary shared probe and for Windows releasing a crashed process's lock (L2 gives no upper bound; a release slower than 2 s reports "already running" and the user retries). It is not a wait for a live daemon.
- **A second `daemon run`** gets `Held` after the retry, reads `daemon.json` (§2.6 liveness rule), and exits `AlreadyRunning` (3) with "a daemon already holds `<dir>` (pid …, `http://127.0.0.1:<port>`)", or "(starting)". It created nothing but possibly an empty `daemon.lock`.
- **The store's own guard.** A second process opening the database directly (an older binary, a doctor) is serialized by SQLite's locks, and a projection version mismatch is refused per job (store §2.4); the instance lock is about daemons.

### 2.6 Discovery: Record, Port, Liveness

**Record** (`daemon.json`, internal: read by the same binary and by the doctor, not a public contract):

```json
{ "version": 1, "instance": "<uuid v4>", "pid": 4242, "start_time": "<ProcessIdentity.start_time>",
  "state": "starting" | "serving" | "stopping", "port": 7373 | null, "url": "http://127.0.0.1:7373" | null,
  "started_at": "<RFC 3339>", "detached": "launchd" | "setsid" | "windows" | null,
  "evidence": { "job": { "in_job": false, "immediate": null } | null, "console": false | null } }
```

`instance` is a fresh random UUID per run, created by `run` before startup. `pid` is the daemon's own (on macOS's launchd path, the forked daemon's, never the job process's). The record is written with `write_replace` at `starting` (step 7, after the stop listener exists), at `serving` (step 13), and at `stopping` (shutdown step 2, before HTTP shuts down, §2.8), so a record says `serving` only while the daemon has not begun to shut its HTTP surface down. It never contains a secret.

**Port.** The PWA's origin is `http://127.0.0.1:<port>` and its owner token lives in that origin's IndexedDB (mvp §2.5 "Secrets"), so a changed port loses the pairing and P-19's reconnect (§2.1 bounds what the stable origin proves):

1. The `port` file, if present, is validated at step 6, before the store opens: one decimal number in 1–65535 and a newline. A malformed file fails the start (`FailReason::PortFile`, "`<dir>/port` is not a port number; move it away and start again to choose a new port").
2. **Choice at step 10:** `--port <n>` if given (`0` is refused, `PortUnavailable`, "port 0 is not a valid port", nothing bound or saved; the CLI's parser refuses it first); else the saved port; else (first start) the first port of `7373..=7472` that binds. That range lies below the dynamic port range of macOS and Windows (49152–65535 by default), so the OS does not hand a first-start port to outgoing connections later; a taken or excluded port is skipped.
3. **Bind failure is reported, never moved around:** `FailReason::PortUnavailable` with the OS error. For the saved port: "port <n> (saved for `<dir>`) is unavailable: <error>; `--port <m>` starts on another port, which changes the pairing origin (re-run `chaldea open` after it)". When no port of the range binds: "no free port in 7373–7472 on 127.0.0.1 (last error: <error>); pass `--port <n>`". In every case `port` is unchanged.
4. **Publication point:** at step 13, after `serve` and before the `serving` record, `write_replace("port")` if the port differs from the saved one. A failure before its rename fails the start with `port` unchanged; once the rename happened, the port is committed (§2.4 `write_replace` step 4) and a later failure of the start does not undo it: the daemon did serve on it. Any startup that does not end `Ok` after that rename, whether it failed or was stopped, says so: `Started` records `port_saved: Some(n)`, the coordinator puts it into the readiness `fail` line as a `port_saved=<n>` field before the message (for `fail stopped` too), and the message, and the starter repeats it in every unsuccessful branch: "port <n> was saved for `<dir>` before the start ended; the next start uses it, so re-pair with `chaldea open`". No record says `serving` before the port is saved. A start that saves `--port <n>` over a different saved port logs "port <n> replaces the saved port <m> for `<dir>`; this changes the pairing origin: re-pair with `chaldea open`" (§8 D12).

The listener is `std::net::TcpListener::bind(SocketAddrV4::new(Ipv4Addr::LOCALHOST, port))` (L3), set nonblocking, and converted with `tokio::net::TcpListener::from_std` inside the runtime. `localhost` and `127.0.0.1` both satisfy the Host check (http §2.2 step 1); the record's `url` uses `127.0.0.1`.

**Liveness rule** (`client::Discovery::read`, every client): a record is used only when (a) `probe` says `Held`, (b) the record, opened without following links, parses with `version: 1`, (c) `host::process_identity(pid)` equals `(pid, start_time)`, (d) `probe` still says `Held` after (b) and (c), so a record read just before its daemon removed it and released the lock is not returned once the lock is free, and (e) the record read again after (d) equals the one read at (b), so a state published during the check (`stopping`) is never answered with the one before it. `Free` or `Missing` at (a) or (d) → `NotRunning` (a leftover record is ignored, never removed by a client); `Held` and (b)–(e) hold → `Starting(record)`, `Serving(record)`, or `Stopping(record)`; `Held` and (b), (c), or (e) fails → `Unknown` (the holder has not yet replaced an old record, which it does as its first act after the stop listener, or is changing it). A client sends a credential only to a `Serving` record (T3 Code drops dead-pid records before sending credentials, L11); what that does not prove is §2.1's.

### 2.7 Startup Sequence

`run` builds the runtime (`ManuallyDrop<Runtime>`, multi-thread), creates the gate and the `instance`, starts the signal listeners and the coordinator (§2.8), and spawns the **startup task**, whose steps run in order. The startup task owns everything it creates in one `Started` value (`lock`, `store`, `server`, `serve`, `participants`, `ready`, `port_saved`, `log_file`) and returns it with its outcome: `Ok` (serving), `Failed(FailReason)`, or `Stopped`. It is never aborted:

- Before each step after step 1 (so a detached child always holds its readiness writer), and once more before the readiness line of step 14, it checks `gate.fired()` and the console-end state; if either is set, it returns `Stopped` with what it has (after a console end the coordinator is already exiting, §2.8).
- What the coordinator needs even when the task panics is shared outside `Started` (`Shared`): whether step 5 began (`lock_attempted`), the canonical directory, and whether a record of this run was renamed into place (`record_published`, set once step 7's record write succeeded). A step in progress (a long `Store::open`, an admitted reconciler) runs to its end first.
- A failing step returns `Failed(reason)` at once; a step never decides a shutdown itself, the coordinator does (§2.8).

| # | Step | Publishes | On failure: reason; disk outcome |
|---|---|---|---|
| 1 | `DetachedChild`: open the readiness writer (§2.10); on macOS the launchd path already forked in `dispatch` (§2.2), and both macOS paths call `host::detach_session()` here | — | `Internal`; nothing. A failed `setsid` is reported through the readiness writer opened first |
| 2 | Windows parent job check (§2.12): `DetachedChild` requires `in_job == false`; `Foreground` warns | — | `ParentJob`; nothing |
| 3 | (done by `run` before the task starts, listed for the failure column) runtime, gate, signal listeners, coordinator | — | `Internal`; nothing |
| 4 | `state_dir::prepare` (§2.4) | the directory and marker, if new | `StateDir`; a created directory and marker stay (empty, private, ours) |
| 5 | `InstanceLock::acquire(dir, 2 s)` | `daemon.lock` if new | `AlreadyRunning` or `LockIo`; at most an empty `daemon.lock` |
| 6 | Checks before any further mutation: `owner.token` privacy and format (§2.4, §2.13), the `port` file and `--port` (§2.6), the database paths (§2.4). Then `DetachedChild`: open `daemon.log` and switch the log target (§2.13); `log_file` is set before the switch is handed to the log thread, so an unacknowledged switch still requires the switch away at shutdown | `daemon.log` | `TokenFile`, `PortFile`, `StoreOpen`; nothing beyond step 5; lock released |
| 7 | `host::listen_for_stop(instance, gate.request(StopRequest))`; `write_replace("daemon.json", starting)` | the stop listener, then the record | `Internal` (including an existing event name); the record unchanged or ours (removed at shutdown); lock released |
| 8 | `Store::open(StoreConfig { path: dir/chaldea.db, readers: 4, writer_queue: 256, busy_timeout: 5 s, SystemClock, RandomIds })` in `spawn_blocking`, awaited to its return (an open can rebuild projections; no deadline, store §2.8) | — | `StoreOpen` with the `OpenError` variant; a failed open can leave an empty or initialized database (store §2.8); lock released |
| 9 | `components.reconcilers(&store)`, in order, each one write job with `not_after = now + 30 s`, awaited to its reply: PR 8's `receipts_mark_unknown_after_crash` (count logged), then PR 10's `supervisor_launches` and `supervisor_buffers` (§2.14) | the reconciled rows (committed, idempotent) | a `WriteError` → `StoreOpen`; `CommitUnknown`, `WriterGone`, `Failed`, or `SubmitError::Failed` → `StoreFatal`; committed reconcilers stay committed |
| 10 | choose and bind the port (§2.6) | — | `PortUnavailable`; reconciliation stays, `port` unchanged |
| 11 | `components.build(&BuildCtx { store, gate, sink: GateSink, port, state_dir, instance })`; `HttpServer::new(HttpConfig::new(port), store.clone(), built.commands, sink, built.mounts)`; `Started.serve` takes `server.shutdown_handle()`, so the registry is drained even if the start ends before `serve` (step 12's token write registers its observer there) | — | a panic (a mount mismatch, http §2.2) → `Panic` (§2.9); `port` unchanged |
| 12 | `components.attach(&server)`; owner token verify or issue (§2.13) | `owner.token` if issued | `TokenFile`, `StoreOpen`, or `StoreFatal`; an issued token whose file write failed stays a valid unheld row (harmless, revocable, http §2.4) |
| 13 | `serve(listener)` → `ServeHandle`; `write_replace("port")` if changed (§2.6); `write_replace("daemon.json", serving)` | the listener, the port, the record | `Internal`; a port write that failed before its rename leaves `port` unchanged; a failure after it leaves the new port saved and the message says so (§2.6) |
| 14 | if the gate has not fired: `DetachedChild` writes `ready <port> <pid>` and closes the channel (§2.10); `Foreground` logs `listening on http://127.0.0.1:<port>` | the verdict | a write error is ignored (§2.10) |

Every outcome other than `Ok` ends in the coordinator's shutdown sequence (§2.8), which shuts down what `Started` holds, removes our record, decides the lock, and only then sends the verdict.

**Why this order.**

- **Reconciliation before the listener exists** (mvp §4 PR 8; formal-specs §7.4): step 9 commits before step 10 binds, so no connection can reach any route while a receipt from a crashed run is still `in_progress`. The listener is the gate: there is no socket to connect to.
- **Every refusal before the first mutation it could leave behind**: the privacy, format, and link checks of step 6 run before the log, the record, the store, and reconciliation, so a refused start leaves at most the marker and an empty `daemon.lock`.
- **The stop listener before the record**, so a client that sees a `starting` record can always stop it (§2.10).
- **The owner token before `serve`**: a client that reads `owner.token` only ever sees a token valid in the store it will reach.
- **The lock before any state write except the directory and marker**, and the log after the lock, so a losing concurrent start writes no log.
- **The port saved once the daemon serves, before the `serving` record**: a start that never served leaves the previous origin, and discovery never reports `serving` on an unsaved port.
- **Job check before the state directory**: a refused detached start leaves the state directory untouched.

### 2.8 The Gate, the Coordinator, and the Shutdown Sequence

```rust
pub enum StopCause {
    Signal(SignalName),                  // TERM, INT, HUP (Unix); CtrlC, CtrlBreak (Windows)
    StopRequest,                         // Windows stop event; Unix `daemon stop` arrives as Signal(TERM)
    StoreFatal(StoreFatal),              // from GateSink or a startup write
    Panic,
    StartupFailed(FailReason),
}
pub struct Stopping { pub cause: StopCause, pub cutoff: Instant }   // published together, once
pub struct ShutdownGate {
    first: OnceLock<Stopping>,           // the cause and the cutoff: set once, never changed
    worst: AtomicU8,                     // most severe later outcome: 0 none, 1 store_fatal, 2 panic (fetch_max)
    crash: OnceLock<ConsoleEvent>,       // Windows console end (below)
    wake: tokio::sync::Notify,           // notify_one after any of the above
}
impl ShutdownGate {
    /// Non-blocking and callable from any thread, a panic hook, or a LifecycleSink. Publishes first
    /// (Stopping or `worst`, then `wake`), then queues its diagnostic. Returns whether this call was the first.
    pub fn request(&self, cause: StopCause) -> bool;
    /// Windows console end: records the event and wakes the coordinator, which exits at once (below).
    pub fn crash_exit(&self, event: ConsoleEvent);
    pub fn fired(&self) -> bool;
}
pub struct Budgets {          // Budgets::DEFAULT; every end is measured back from the cutoff C = first request + total
    pub total: Duration,              // 10 s
    pub startup_join_before: Duration,// 6 s: the startup task has until C − 6 s to reach a step boundary
    pub http_before: Duration,        // 5 s: HTTP drains until C − 5 s
    pub store_before: Duration,       // 3 s: participants run until C − 3 s; the store has the last 3 s
    pub report_grace: Duration,       // 250 ms past C for the store report
    pub log_flush: Duration,          // 100 ms
}
```

`OnceLock::set` publishes the cause and its cutoff as one value, so no reader sees one without the other; a later `StoreFatal` or `Panic` raises `worst`, which only selects the exit reason (below). `GateSink(Arc<ShutdownGate>)` implements `LifecycleSink`: `store_fatal(f)` calls `request(StoreFatal(f))`, then logs `store fatal: <variant>` (a `ReceiptUncompleted` with its `command_id`, which is not a secret). Diagnostics go through the non-blocking log queue (§2.13), so a stalled stderr or disk cannot delay a request or the coordinator.

**Signal listeners** (`signals.rs`, tasks on the runtime, not registered in PR 7's registry, ended by process exit): Unix `tokio::signal::unix::signal` for `SIGTERM`, `SIGINT`, `SIGHUP`; Windows `tokio::signal::windows::{ctrl_c, ctrl_break}` call `gate.request`, and `{ctrl_close, ctrl_logoff, ctrl_shutdown}` call `gate.crash_exit`. A later signal is logged as "already stopping (<first cause>)". A detached Windows daemon has no console and receives only the stop event; at logoff or system shutdown the system ends it.

**Console end is a crash exit.** Windows kills the process about 5 s after a close event and delivers logoff and shutdown only sometimes (L7), so no graceful sequence could be guaranteed to finish. Once `crash` is observed, during startup, while serving, or in the middle of a shutdown, the coordinator starts no further step and returns with `ExitReport { code: Failed, reason: ConsoleEnd, lock }`, where `lock` is `Released` if step 6 already released it, `NeverTaken` if startup never reached step 5, and `HeldUntilExit` otherwise; the log queue is flushed for at most `log_flush`. The coordinator checks for it before each step, before each participant, before submitting the store's shutdown, before each attempt and during each wait of the record's removal, before queuing the log switch of step 6 and again after it (a console end there keeps the lock), and the startup task checks it at its step boundaries and in step 14's last check before the verdict. A step already started is not undone or awaited: the record may already be removed, and a `Store::shutdown` already submitted keeps running on its blocking thread until the exit ends it. Recovery is crash-only (AGENTS.md "PTY Seam"): an uncommitted transaction is rolled back by WAL recovery, a committed one survives without a checkpoint (store §2.9), and the next start acquires the lock once the OS released it (within the 2 s retry, §2.5, else "already running"), replaces a stale record left behind (once no other process holds it without delete sharing, §2.4 `write_replace` step 3), and reconciles receipts.

**The coordinator** (`Coordinator::run` in `lifecycle/shutdown.rs`, one task, the only caller of `ServeHandle::shutdown`, `Store::shutdown`, and `InstanceLock::release`) awaits `wake`, selecting on `crash` throughout. When the startup task returns `Ok`, it keeps waiting; when it returns `Failed(r)`, the coordinator calls `request(StartupFailed(r))`. The wait for the first request checks the join's end after it takes the startup task's result, while step 1's `deadline_first` checks it before each poll, so a poll that started before the cutoff can still be accepted; `Coordinator::run` and `Coordinator::guarded` (for the futures passed to it) decide the rest. Once `first` is set, with `C` its cutoff:

The startup task's result, the `stopping` rewrite (step 2), and the store's report are taken **deadline first** (`deadline_first`): the deadline is checked before every poll, and the startup result is also refused when the wait for the first request takes it after the join's end (a console end observed at that point is checked first and decides the exit, as in the join). A poll admitted before the cutoff can return `Ready`; nothing waits past it. The participants' wait is a `tokio::time::timeout_at`, which polls the participant before its timer; the clock is read once after a participant's result is taken, and a result taken at or after its end counts as not done by it; and the HTTP drain keeps PR 7's own deadline semantics (`ServeHandle::shutdown` returns by its deadline after requesting abort).

1. **Join the startup task** until `C − startup_join_before`. It ends at its next step boundary and returns `Started` (a panic in it is a `JoinError`, §2.9). **A missed join is a bare exit:** if it has not returned by then, the task may still own the lock, the store, the readiness writer, or a write in progress, so the coordinator returns at once with `ExitReport { code: Failed, reason: StartupUnjoined, lock: HeldUntilExit }`: no filesystem cleanup (the record stays), no verdict (a detached starter sees EOF and reports it, §2.10), no store call; only the log queue is flushed for at most `log_flush`. The next start waits for the OS to release the lock (the 2 s retry, §2.5), replaces the stale record (once its delete sharing allows it), and recovers the WAL.
2. If this run published a record, it is rewritten with `state: stopping` (`write_replace`, only while it names this instance), so no client takes this run for one that serves once its HTTP surface may be gone (§2.10 "What a reported start means"). The rewrite runs on a blocking thread, guarded like every step: a console end observed before it starts no rewrite, and one observed during it ends the wait. The coordinator waits for it at most 500 ms of HTTP's budget and never past `C − 5 s` (the rewrite's cutoff); a rewrite that fails or does not finish in time is logged and the shutdown continues. The thread checks the cutoff when it starts and again before it creates the temporary file, makes no rename attempt at or after it, and retries a failed rename only until the same cutoff (`mark_stopping`). The 500 ms bounds the coordinator's wait, not the filesystem: a call the thread already issued (the read, the metadata calls, the create, the write, a rename) may finish after the cutoff, and a temporary file created after it is removed, best effort, when its rename is refused, and later starts ignore one left behind (§2.10 "Scheduling limits"). Then, if `Started.serve` exists (from step 11, whether or not the server served): `ServeHandle::shutdown(C − http_before)`, awaited to its return (it returns by its deadline after requesting abort of what remains, L16; the coordinator never drops it). The `HttpShutdownReport` is logged.
3. Each `ShutdownParticipant` in order, until `C − store_before`; the participants share the time between the HTTP end and the store's share, so a later PR is never left with nothing (PR 8 has none). Each resolves to a `ParticipantEnd`: `Clean`, or `LeftRunning` when work it owns may still be running; one not done by its end, or whose result is taken at or after its end, is no longer awaited, and step 6 counts it as one that left work running.
4. If `Started.store` exists: `spawn_blocking(move || store.shutdown(C))`. `Store::shutdown` ends its timed waits by `C` (L16), but synchronous work around them is not bounded, so the coordinator caps its own wait: it observes the call until `C + report_grace`, and a report not seen by then counts as `writer_exited: false`, `readers_returned: false` (the call keeps running on its blocking thread until the process exits).
5. If this run published a record (`Shared.record_published`), remove `daemon.json` if it parses and names this `instance` (L11); never otherwise. A failed removal (Windows refuses it while another process holds the file without delete sharing) is retried every 50 ms within a 500 ms budget: the wait before a retry never runs past the budget, and the budget is checked before each retry and again just before each deletion, so no deletion is issued after it; a deletion the budget ended leaves the record, logged with the last refusal or failed re-read when there was one, else as "the discovery record `<path>` was left in place: its removal did not start within 500 ms". Every attempt re-reads the record first and removes it only while it still names this instance, so a record another instance wrote in between survives. That holds under the writer protocol: while this daemon holds the lock no other daemon writes the record and clients only read it, so only a same-account program outside the protocol could replace it between the re-read and the deletion (§2.1). A re-read that fails for now (a Windows sharing violation) is retried within the same 500 ms and, if it never succeeds, logged as "the discovery record `<path>` could not be verified for removal: <error>". A console end is checked at the start of each attempt and again after a successful re-read, just before the deletion: one observed by then leaves the record, and one arriving while a deletion is already issued may still see it removed. A removal still refused is logged: "the discovery record `<path>` could not be removed: <error>". A record left behind is stale: clients ignore it once the lock is free (§2.6), and the next holder replaces it once no other process holds it without delete sharing.
6. **Lock rule:** `InstanceLock::release` → `Released` only if all hold: the startup task returned (step 1), the HTTP report has no `abort_requested` task (or nothing served), no store was opened or the report has both `readers_returned` and `writer_exited` (an abandoned reader keeps a SQLite connection and its snapshot open, even after the writer retired), the log thread acknowledged switching away from `daemon.log` within `log_flush` (whenever step 6 handed it the file, acknowledged or not; so no rotation of ours runs after a successor opens the log), no participant answered `LeftRunning` or was not done by its end (step 3), and no console end was observed by then. Otherwise log "exiting with the instance lock held (<which condition>)" → `HeldUntilExit` (the handle stays leaked until exit). Nothing in this process touches the DB files after step 4.
7. **Verdict:** compute the outcome (below) and, for a `DetachedChild` whose startup outcome was not `Ok` (so it never sent `ready`), send `fail <verdict reason> <message>` on the writer `Started` returned (§2.10); a startup task that panicked took its writer with it, and the starter sees EOF. Then log `exiting: code <n> (<reason>)`, flush the log queue for at most `log_flush`, and return.

Readers in flight get the time between the HTTP drain and `C` to return; the store then abandons and reports them (store §5); notification receivers are not drained (store §4 row 8); committed transactions survive a skipped checkpoint (store §2.9).

**Outcome and reason.** Two results are computed, each from what the coordinator observed:

- **The daemon's exit reason** (`ExitReport::reason`), by precedence: `panic` (if `worst` or the cause says so) > `store_fatal` > the startup failure's reason (`state_dir`, `lock_io`, `already_running`, `parent_job`, `token_file`, `port_file`, `port_unavailable`, `store_open`, `internal`) > `lock_held_at_exit` (an otherwise clean stop that retains the lock, `HeldUntilExit`) > none. A signal or stop request is not a failure, whether it came before or after startup completed: a clean stop exits 0. `console_end` and `startup_unjoined` are set only by their own paths above. `FailReason` is exactly these tokens.
- **The detached verdict reason**, sent only when `Started`'s startup outcome was not `Ok`: the exit reason if there is one, else `stopped` ("stopped before it became ready"). Either carries `port_saved=<n>` when step 13 had already committed a new port (§2.6). `stopped` is a verdict token only; the starter turns it into its own exit 1, while the daemon itself may exit 0.

**Exit codes** (`ExitCode`, published; §8 D14). Only distinctions a caller acts on are codes; the reason is in the log and in the readiness line:

| Code | Name | When |
|---|---|---|
| 0 | `Ok` | `run`: a **clean stop**: stopped by a signal or stop request (before or after startup completed) with no exit reason and no retained lock, that is `NeverTaken` (stopped before step 5) or `Released`; `start`: a daemon serves the state directory; `stop`: the daemon stopped, or none was running; `open`: the URL was handed over or printed; any command's `--help` |
| 1 | `Failed` | anything else that ended a command: a startup failure, a fatal store outcome or panic, a console end, an unjoined startup, a shutdown that exited holding the lock, a daemon stopped before it was ready (`start`), a conflicting `--port`, a stop that could not be delivered |
| 2 | `Usage` | clap |
| 3 | `AlreadyRunning` | `run`: another daemon holds the state directory |
| 4 | `Timeout` | `start`: no verdict within 15 s, or a launchd submission whose outcome could not be resolved (the daemon may still be starting); `stop`: the daemon was still running 15 s after the stop began |

### 2.9 Panics and Unwinding

- **Startup task panics** end the task with a `JoinError`, which the coordinator maps to `request(Panic)`. What the task owned unwinds with it: `InstanceLock` leaks its handle, a `Store` dropped without `shutdown` lets its writer finish on its own (L16), so the lock outcome is `HeldUntilExit` whenever step 5 may have succeeded. The readiness writer unwinds too, so a detached starter sees EOF; the record, which the coordinator still removes (the task has ended, so nothing else writes it), is the only cleanup.
- **The coordinator** runs inside `runtime.block_on(AssertUnwindSafe(coordinator).catch_unwind())`; a panic there returns `ExitReport { code: Failed, reason: Panic, lock }` at once, with `HeldUntilExit` once startup's step 5 began (`Shared.lock_attempted`) and `NeverTaken` before.
- **Panics in `run` before the runtime exists** are caught by `run` with `catch_unwind` and reported the same way: `run` creates `Shared` before the runtime, so such a panic reports `NeverTaken`.
- **Panics in other tasks and threads** (PR 7's registered tasks, `spawn_blocking`, the store writer) are caught by tokio or by the store, and the panic hook requests `Panic` through the active gate (§2.13).
- **The runtime** is a `ManuallyDrop` that `run` ends with `shutdown_background()`: blocking tasks (an abandoned `Store::shutdown` or `Store::open`) are left running and end with the process, so neither a return nor an unwind waits for them.
- **`dispatch`** calls `run` inside `catch_unwind` as the last guard, maps an escaped panic to exit 1, and then calls `std::process::exit`. The exit code for any panic is 1 (`Failed`, reason `panic`), never Rust's 101.

### 2.10 `daemon start`, Readiness, `daemon stop`

**Readiness channel** (`host::ready_channel_in`). macOS: the starter creates a private directory `chd-<16 hex>` (`mkdir` mode `0700`, a fresh name on `EEXIST`, owner and mode verified) in `std::env::temp_dir()` made absolute against the working directory once per start (`--ready` carries an absolute path, and the same directory is the child's and the launchd job's working directory), or in `/tmp` when `<temp_dir>/chd-<16 hex>/r` would exceed 100 bytes (Darwin's `sun_path` holds 104 bytes with its NUL, L20), and binds a `std::os::unix::net::UnixListener` at `r` in it; `ReadyArg` is that path. Windows: the child's stdout pipe (`ReadyArg::Stdout`). When it is done, the starter removes only what it created: the socket `r` it bound and the plist `job.plist` if its own exclusive creation made it (`ReadyReader::write_plist`), then the directory with `rmdir`, which anything else in it keeps (no recursive removal); a plist the creation refused (`AlreadyExists`) and a socket path whose `bind` failed are left alone. The starter waits on the channel through `receive_before`, woken by a connection, data, or the channel's end (kqueue on macOS, which also wakes on the direct child's exit; the reader thread's channel on Windows). A child that connects after the starter removed the socket or stopped listening (`ENOENT`, `ECONNREFUSED` at step 1), or writes after the starter left, gets an error it ignores and keeps running (a serving daemon whose verdict nobody reads; binary test `daemon_start::late_child_serves`).

**The child's verdict** (`ready.rs`): exactly one line, then `ReadyWriter::close` (macOS: shut down and close the socket; Windows: close the stdout handle explicitly through `host`, since dropping Rust's `Stdout` does not close it):

- `ready <port> <pid>\n` at step 14, only after the port is saved and the `serving` record written, and only if the gate has not fired at that check (a stop arriving later is an ordinary stop of a serving daemon);
- `fail <reason> [port_saved=<n>] <message>\n` from the coordinator's step 7, after the lock was released or the hold decided, the record removed, and the reason chosen by §2.8's precedence. `<message>` goes through `log::diag` and then has its newlines replaced too (redacted, every control character a space) and is cut to 512 bytes at a character boundary.

A write error (a starter that stopped reading) is ignored: Rust ignores `SIGPIPE`, so a broken pipe is an error value, never a signal.

**Deadlines of start and stop.** `start` and `stop` each have one absolute deadline, and four shared helpers of `pty-runtime::host` decide every step against it; call sites add no checks of their own.

- **OS actions** (the daemon's native spawn, every `launchctl` spawn including `bootstrap` and `bootout`, `SIGTERM`, `SetEvent`) take the deadline as a parameter and run through `act_before`, whose check is the last step before the action: after the identity check for `SIGTERM`, after `OpenEventW` for `SetEvent`, and for a child's creation under the spawn lock (`spawn_before`). The lock itself is acquired only before the deadline: one not acquired by then, or asked for once the deadline has passed even while it is free, is a timeout, and nothing is created.
- **Waits a result can wake.** A wait that is one blocking call (a channel message: the Windows readiness verdict, `launchctl`'s output; a Windows process exit through `WaitForSingleObject`) goes through `receive_before`, which hands it the whole remaining time. A wait that looks before it blocks (the macOS readiness channel, woken by a connection, data, the peer's end, or the direct child's exit; a macOS child's exit) goes through `decided_before`: each look is classified like a poll, and the remaining time is read immediately before the blocking `kevent` call, so a pause after a look shortens the wait instead of carrying it past the deadline. Each return is classified with one clock sample: before the deadline its result counts; at or after it the wait timed out, whatever it returned. There is no sleep between looks in which a timely result could wait unseen. A Windows wait is at most `u32::MAX − 1` ms, never `INFINITE`. A `kevent` registration that fails comes back as an `EV_ERROR` event: `ESRCH` for a process is its exit, and any other error is returned.
- **Polls of state nothing can wake** (discovery, the lock, a target's identity, a label lookup, the serving check) go through `observed_before`: the deadline is checked before each observation and again after it, so a result first observed at or after the deadline loses.
- **Late results.** A result that claims a state of the daemon (serving, not running, exited, no listener, stopped; the absence of an event included) and is first observed at or after the cutoff is reported as a timeout, through the helpers above (`observed_before`, `receive_before`, `decided_before`, and the CLI's `poll_until` and `follow_up`). A `stop` delivery that reports its target gone (`ESRCH`) is such a claim. An error of the command's own operation (a job refusal or a failed lookup from `job_state()`, a failed signal delivery, an I/O error, a failed read of an HTTP response) is reported as that error, or, when first observed at or after the cutoff, may be reported as a timeout: a wait classifies whatever it returns at the deadline as a timeout, and `stop`'s identity lookup and `OpenEventW` failing then are `DeadlinePassed`, with nothing signalled. Either report tells the user that the attempt failed, and the next action is the same.

Past its deadline `host::launchctl` kills the command and leaves its reaping to a thread.

**Scheduling limits.** A check and the call it guards are separate instructions, so an action whose last check passed can still run one scheduling pause after the deadline: `CreateProcessW` after its handle list was set, any action behind `act_before`, and the creation of the readiness directory and the plist (`ready_channel_in`, `write_plist`, which take no deadline). Nothing closes that pause; its consequence is bounded instead. The starter reports a timeout (exit 4) while the daemon it launched carries on: the accepted late child of D10, which is never killed, serves, and is stopped by `chaldea daemon stop`. Every start timeout that may leave this start's own launch running says how to check for it and stop it: `chaldea daemon stop` stops a published daemon and says `not running` when none is left, and until the daemon publishes, the message names the pending launch (step 4). The `already_running` follow-up's timeout carries no such guidance: the daemon it waited on was launched by another start, which reports on its own launch. What a command reports about the daemon follows "Late results" above. Every blocking wait takes the absolute deadline down to the call that blocks and reads the time left immediately before that call (after any setup call that can block before it, such as creating the kqueue). A blocking setup call between the last check and the effect is the scheduling pause above, for example the stopping worker's metadata calls before it creates its temporary file (§2.8 step 2), and the client's `set_read_timeout` before a `read`. Their consequences are bounded: the stopping worker may create a `.daemon.json.tmp-<instance>` after its cutoff; its removal after a refused rename is best effort, and a file left behind (also when the daemon exits first) is never renamed and is ignored by later starts (§2.4, `write_replace` step 3); a client read may block up to one read interval past the cutoff, and its result is then discarded by the check after the read. A finding that an OS call between the last check and its effect consumes the budget is this stated limit; a state claim first observed late and reported as that state is a defect of the helper or of a path that bypasses it. The spawn lock's inner mutex is held only to update its flag and to hand the lock over through its condition variable, never across a spawn, so a pause there is the same scheduling pause. The lock is not FIFO: a later arrival can take a freed lock before a woken waiter, which then waits on until the lock is free or its deadline passes.

**Start** (`daemon_cmd::start`, in the CLI process), one deadline of **15 s** from its start (`READY_TIMEOUT`, herdr's bound, L9) that every step below shares:

1. Resolve the state directory to an absolute path. On Windows read `host::job_state()` and decide the breakaway (§2.12); a refusal exits 1 with the message before any spawn.
2. `host::ready_channel_in(<temp directory made absolute>)`.
3. **Launch** (in every case the working directory is that temp directory, so the daemon never holds the user's working directory open):
   - **Choosing the macOS path.** `host::gui_domain(deadline)`, with at most 3 s of the deadline: `Absent` when `SSH_CONNECTION` or `SSH_TTY` is set (the deliberate SSH path, no probe), or when `launchctl print gui/<uid>` completed and reported that the domain does not exist (exit 112, "Could not find domain", L23); `Available` when it exits 0; `ProbeFailed` for anything else (a timeout, a spawn error, another exit). `ProbeFailed` fails the start, exit 1: "could not determine whether a GUI session exists (<why>); run `chaldea daemon run` in a terminal you keep open". Only `Absent` takes the `setsid` path. `SSH_CONNECTION` and `SSH_TTY` are a heuristic for "no GUI session", trusted as they are. Stale values in a multiplexer or terminal launched from the GUI (a tmux server started from the GUI terminal whose environment still carries an earlier SSH attach's `SSH_TTY`) take the `setsid` path, and a daemon started there may not survive the terminal app quitting. PR 23 checks it on a real host: a tmux server started from the GUI terminal, a stale `SSH_TTY`, `daemon start`, then quit the terminal app.
   - **macOS with a GUI domain** (`Available`). The launch is a one-shot launchd job and nothing else:
     1. Label `dev.chaldea.daemon.<unix-ms>-<uuid>`. Program arguments `current_exe() daemon run --from-launchd --detached-child --ready <path> --state-dir <abs> [--port <n>]`; `EnvironmentVariables` the starter's environment; `WorkingDirectory` the temp directory resolved in step 2; the starter's umask; stdout and stderr `/dev/null`; `RunAtLoad` true, `KeepAlive` false, `AbandonProcessGroup` true. Strings are XML-escaped, and every control character (U+0001–U+001F, U+007F–U+009F) is written as a decimal character reference, which launchd reads back unchanged (terminal settings such as `LESS_TERMCAP_*` carry `ESC`); hexadecimal references are not used, since launchd does not read them back reliably. A value a plist cannot represent unchanged (a non-UTF-8 argument or variable, or U+FFFE or U+FFFF, which launchd alters) fails the start: "this environment cannot be passed to launchd (<name>); run `chaldea daemon run` in a terminal you keep open".
     2. The plist is created with `ReadyReader::write_plist` (`create_private_file`) in the readiness directory; `launchctl bootstrap gui/<uid> <plist>` runs through `host::launchctl` with the remaining deadline minus 3 s, which stay reserved for resolving the label. Exit 0 → submitted. Otherwise the attempt's unique label is looked up with `launchctl print gui/<uid>/<label>` within the reserve:
        - **`bootstrap` completed with a non-zero exit:** the command has finished, so nothing of this attempt is still in flight. Label present → submitted; absent → non-submission is established: the start fails, exit 1, with launchctl's message and "run `chaldea daemon run` in a terminal you keep open".
        - **`bootstrap` timed out:** the submission may still complete after any lookup, so one absent answer proves nothing. The label is polled every 250 ms for the whole reserve: present → submitted; still absent, or the lookups fail → indeterminate.
        - **Indeterminate** → exit 4 with "the launch may still be pending as `<label>`: `launchctl print gui/<uid>/<label>` shows it; until the daemon forks, `launchctl bootout gui/<uid>/<label>` cancels it; once it has published its record, use `chaldea daemon stop`". There is no retry and no other launch path on a GUI host, so a start never reports a daemon that dies when the terminal app quits.
     3. **Job process.** `dispatch` sees `daemon run --from-launchd` (§2.2) and calls `host::leave_launchd_job()` before any thread exists: `fork`; the parent calls `_exit(0)` (no destructors or stdio flushing in the job's process), so launchd sees a finished one-shot job and does not restart it; the child continues, calls `setsid` at step 1, and becomes the daemon, outside the terminal app's launchd job and coalition (L10). A failed `fork` is reported by the job process itself: it opens the readiness writer, sends `fail internal fork failed: <error>`, and exits 1.
     4. **Cleanup.** After a verdict (which only the forked daemon sends, so the handoff happened), the starter removes its own label with `launchctl bootout gui/<uid>/<label>` within the remaining deadline and says so ("removed the launchd job `<label>`"). On EOF, a timeout, or a `bootout` that fails or runs out of time, it leaves the label to a later start's scavenging. Before bootstrapping, within at most 2 s of the deadline, it removes labels proven stale, which takes positive evidence: a `dev.chaldea.daemon.*` label whose timestamp is more than 60 s old (beyond any attempt's 15 s deadline) and whose `launchctl print gui/<uid>/<label>` shows, at its top level, `state = not running` with a numeric `last exit code`, and program arguments `<program> daemon run --from-launchd …` whose program resolves (`canonicalize`) to this starter's resolved executable. An empty or unrecognised listing proves nothing, a job that never exited (`(never exited)`) is kept, and so is a job of any other executable, including another copy of Chaldea at another path; a lookup or removal that the cleanup's share ended stops the cleanup. What is checked is therefore this executable, this argument shape, and the label prefix: a stale job of another installation is left for that installation's starts. Nothing else is removed.
   - **macOS without a GUI domain** (`Absent`): `current_exe()` with the same arguments minus `--from-launchd`, stdin, stdout, and stderr null, through `host::spawn_detached` (std's spawn through `spawn_before`); the child calls `setsid` at step 1, so it is in its own session and survives the SSH connection's end. There is no terminal app to quit on this path.
   - **Windows:** the same arguments with `--ready stdout` through `host::spawn_detached`: `CreateProcessW` in `windows::sys` through `spawn_before`, with this process's environment, the working directory without a verbatim prefix when the stripped form names the same directory (the rule the PTY backend applies, pty-windows §2), the §2.12 creation flags, stdin and stderr the null device, stdout a pipe whose read end the reader takes, and `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` naming exactly those handles, so the daemon inherits no other handle of the starter or of the starter's caller (a caller reading the starter's output to EOF would otherwise wait for the daemon's exit; Windows test `daemon_windows::daemon_holds_no_caller_handle`). A spawn with an explicit breakaway that fails with `ERROR_ACCESS_DENIED` is refused with §2.12's message, with no second spawn. On both direct paths, a spawn the deadline ended (`TimedOut`: nothing was created) exits 4: "the daemon was not launched within 15 s".
4. **Wait for the verdict** until the deadline:
   - **What a reported start means.** `start` reports success when, at the check, its `serving` record named the daemon with the lock held (`Discovery::read`), an owner-token `GET /api/threads` to its port answered 200, and a discovery made after that answer still showed a `serving` record of the same instance with the lock held; checked every 50 ms. Success therefore means that the daemon answered the authenticated request at the check instant and that its record then named the same serving instance with the lock held. A shutdown that has begun but not yet published `stopping` (§2.8 step 2), or whose `stopping` rewrite failed while HTTP still answers, cannot be told apart at that instant and may still be reported as started. Later commands see the shutdown once it shows: after `stopping` is published, a discovery finds the daemon stopping, not serving; after its HTTP surface closes, the daemon no longer answers, whether or not the rewrite succeeded. Before either, a later command can take the daemon for one that serves too. The client reads the response only up to its status line and never reads its body, so the check does not wait on a large thread list (the server still builds the full response; no endpoint is added for it). A `stopping` record, or a daemon that does not answer, is not serving, and the check continues until the daemon is gone or the deadline.
   - `ready <port> <pid>` → if `--port <n>` was given and differs → exit 1 ("a daemon serves `<dir>` on port <port>, not <n>"); else, after the launchd label's removal, wait until that daemon (`pid` and `port` as the verdict named them) serves, then print `daemon started: http://127.0.0.1:<port> (pid <pid>)` and exit 0. No daemon, or the record naming another process → exit 1 ("the daemon (pid <pid>) reported ready but stopped before the start finished; see `<dir>/daemon.log`"); the deadline → exit 4 ("the daemon (pid <pid>) reported ready, but its serving on port <port> was not confirmed within 15 s; it may still be running: `chaldea daemon stop` stops it (and says `not running` when no daemon is left)"), also when the 200 came in time and the discovery after it only at or after the deadline.
   - `fail already_running …` → print "another daemon holds `<dir>`; waiting until it serves" and wait until the recorded daemon serves: the port check above, then `daemon already running: http://127.0.0.1:<port> (pid <pid>)`, exit 0; `NotRunning` (the winner exited during its startup or its shutdown) → exit 1 ("the daemon starting for `<dir>` exited; see `<dir>/daemon.log`"); the deadline → exit 4 ("no daemon was confirmed serving `<dir>` within 15 s; another start's daemon may still be starting"). A timeout message names only what could not be confirmed before the deadline, never a state no observation showed in time.
   - `fail stopped …` → "the daemon was stopped before it became ready", exit 1.
   - Any `fail` line with `port_saved=<n>` → the starter also prints the re-pairing notice of §2.6, whatever the reason.
   - `fail <other> <message>` → print the message, exit 1.
   - EOF without a verdict → the readiness channel closed before a verdict, which by itself says nothing of the daemon's state: on Windows wait for the child's exit (woken by it), on macOS poll the lock every 50 ms, for at most 2 s and never at or past the deadline; print "the daemon closed its readiness channel without a verdict" with what was observed before the cutoff (an exit or a free lock as soon as it is seen; on macOS, the last poll made before it, such as the lock still held; on Windows, that the exit was not observed before the cutoff, since the wait's end is no observation) and the log path; exit 1.
   - the deadline → "the daemon did not report readiness within 15 s; it may still be starting", exit 4, with what the owner can do: once it has published its record, `chaldea daemon stop` stops it (and says `not running` when no daemon is left); before that, the pending launch is the child pid <pid> (direct spawn) or the launchd label `<label>` (`launchctl bootout gui/<uid>/<label>` cancels a launch that has not forked yet). The child is not killed: it may be rebuilding projections.

**Windows detach.** `DETACHED_PROCESS` (no console; `CREATE_NO_WINDOW` would be ignored with it), `CREATE_NEW_PROCESS_GROUP`, and the breakaway of §2.12 (the spike's flags, L12). Console events never reach it.

**Stop** (`daemon_cmd::stop`), one deadline of **15 s** from its start (`STOP_WAIT` = the 10 s shutdown budget + 5 s for process exit). It targets a **published** daemon: the process a `starting`, `serving`, or `stopping` record names (on macOS's launchd path, the forked daemon; the launchd job is never touched). A launch that a timed-out `start` submitted is invisible until it publishes: while it has not taken the lock, `Discovery::read` gives `NotRunning` and `stop` reports "not running"; once it holds the lock but has not yet written its record (steps 5–7), `Discovery::read` gives `Unknown` and `stop` waits for the record (step 1 below). The starter's timeout message names the pending launch.

1. `Discovery::read`: `NotRunning` → print "not running", exit 0. `Unknown` → poll every 50 ms until `Starting`, `Serving`, `Stopping`, `NotRunning`, or the deadline (exit 4: "no daemon of `<dir>` could be identified within 15 s").
2. `Stopping`: no request (the daemon is already shutting down); step 3 waits for it. `Starting` or `Serving`: `host::send_stop(&StopTarget { pid, start_time, instance }, deadline)`; a delivery the deadline ended (`DeadlinePassed`, nothing sent, also when the identity lookup or `OpenEventW` fails at or after the deadline) exits 4: "the stop request was not sent within 15 s (pid …)":
   - **Unix:** `host::process_identity(pid)` must equal `(pid, start_time)` (a zombie does not match: it has exited), then `kill(pid, SIGTERM)` through `act_before`; `ESRCH` observed before the deadline → `Exited` (the target exited after the check; observed at or after it → `DeadlinePassed`); `EPERM` → `AccessDenied`. The window between the identity check and the signal is the PID race pty-unix §2.5 describes: if the daemon exited and its pid was reused by another of the account's processes in between, that process gets `SIGTERM` (§6.2).
   - **Windows:** `OpenEventW(EVENT_MODIFY_STATE, "Global\chaldea-stop-<instance>")` then `SetEvent` through `act_before`. The daemon creates that event at step 7 with `CreateEventW` and an explicit security descriptor `D:P(A;;0x1F0003;;;<user SID>)` (all event rights for the account only); `Global\` needs no privilege for events and is shared by every session (L19), so a stop from an SSH or second desktop session of the same account reaches it; an existing name fails the daemon's step 7 (`ERROR_ALREADY_EXISTS`). The instance UUID in the name ties the request to the selected instance. `ERROR_ACCESS_DENIED` → `AccessDenied`.
   - **When the request did not land** (`OpenEventW` finds no event, or the Unix identity check fails), `send_stop` re-checks the selected identity: gone → `Exited`; the pid alive with another `start_time` → `IdentityMismatch` (nothing was signalled; the selected identity no longer exists); alive and matching with no event → `NoListener`.
   - `Sent`, `Exited`, or `IdentityMismatch` → step 3 (the last two print "the daemon had already exited"). `AccessDenied` → exit 1: "access denied; the daemon may run elevated: run `chaldea daemon stop` from an elevated terminal" (Windows, L19) or "…as the daemon's user" (Unix). `NoListener` → exit 1 ("the daemon (pid …) is running without a stop listener; see `<dir>/daemon.log`").
3. **Completion is generation-aware:** poll every 50 ms until the target `(pid, start_time)` is gone, then print "stopped" and exit 0 — whether or not a new daemon has since taken the lock (that one is reported: "a new daemon (pid …) now holds `<dir>`"). At the deadline → exit 4, naming only the check that expired: "the daemon's exit (pid …) was not observed within 15 s" after `Sent`, and "the completion check did not confirm within 15 s that pid … is gone" after `Exited` or `IdentityMismatch`, which step 2 already reported.

`stop` sends one request and never kills; the daemon ends by itself, because its shutdown is bounded by its budget and ends in `std::process::exit`.

### 2.11 Process Rules (mvp §4 PR 8, kept by PR 10)

**Spawn lock.** Every child the daemon creates is created through `chaldea_daemon::lifecycle::spawn_locked(cmd: &mut Command) -> io::Result<Child>` = `chaldea_pty_runtime::with_spawn_lock(|| cmd.spawn())`, which the CLI uses too for any child it creates itself; PR 8's CLI creates none: `pty-runtime::host` creates its children (`spawn_detached`, `launchctl`, `open_url`) under the same lock, acquired through `spawn_before` within the caller's deadline (§2.10). `crates/daemon/clippy.toml` and `crates/cli/clippy.toml` list `std::process::Command::spawn`, `output`, and `status` under `disallowed-methods`; `spawn_locked` and `spawn_locked_before(cmd, deadline, under_lock) -> Option<io::Result<Child>>` (the lock waited for only until `deadline`, and the child created only when `under_lock`, run while the lock is held, returns true and `deadline` has not passed after it, checked by `host::act_before` as the last step before the OS spawn; `None` when nothing was created) carry the daemon's only `#[allow(clippy::disallowed_methods)]`s. `host`'s children (`/bin/launchctl`, `/usr/bin/open` by absolute path, and the detached daemon) are created under the lock inside `pty-runtime`. tokio's `process` feature stays off (CI check, §1), so `tokio::process` cannot be used; the PR records `cargo tree -p chaldea-daemon -e normal` in its description, and a dependency that spawns would need review against this rule. `tests/lints.rs` in `crates/cli` checks both `clippy.toml` files keep these entries. PR 8's children: `launchctl`, `open`, the detached daemon; none in the daemon process itself.

**Wait ownership (macOS).** `prepare_process` calls `host::reset_process_signals()` before any thread exists: `SIGCHLD` is set to `SIG_DFL` with no flags, because an inherited `SIG_IGN` (L15) would let the kernel reap every child and break PR 3's ownership rule; `SIGTERM`, `SIGINT`, `SIGHUP`, and `SIGCHLD` are unblocked so the listeners receive them. Neither crate calls a wildcard wait: the only waits are `std::process::Child::wait` / `try_wait` (exact pid) in the CLI and `host`, and PR 3's backend in the daemon. No code sets `SIGCHLD` to `SIG_IGN` or uses `SA_NOCLDWAIT`; PR 8 never registers a `SIGCHLD` handler.

**Signal handlers.** The only handlers the process installs are tokio's for `SIGTERM`, `SIGINT`, and `SIGHUP` (L6): an atomic store and a nonblocking pipe write, both async-signal-safe and non-blocking (a source fact about tokio, not something a test of PR 8 proves). A handler that runs in a forked child before PR 3's `pre_exec` resets dispositions writes one byte to the child's copy of the pipe, which only wakes the daemon's driver without an event. The panic hook is not a signal handler.

**Windows.** `CreatePseudoConsole` and `CreateProcessW` run under the lock inside the backend (PR 4); the detached daemon's `CreateProcessW` (`windows::sys::create_detached`, with its handle list) runs under the same lock. The daemon and the CLI close no handle they did not open: both crates forbid `unsafe`, so a raw `CloseHandle` is impossible outside `pty-runtime`'s `sys` modules. A parent job that refuses nesting makes PTY spawns fail with no uncontained running child (PR 4, L14); PR 8 adds no check for it.

### 2.12 Windows Parent Job

**What the hazard is.** A daemon inside a job with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` dies, with every PTY session it owns, when the job's last handle closes, typically when the launching terminal exits (prior-art row 8). Nesting is not the issue: PTY spawns nest under such a job, including one with UI limits (L14, A13); a parent that refused nesting would make spawns fail without an uncontained child (PR 4), which the doctor reports (PR 21). The check is about the daemon's **lifetime**.

**What can be proven.** Only the immediate job's limits are visible, and no API names a parent job (L13), so "outside every kill-on-close job" can be proven only as **in no job at all**: `IsProcessInJob(self, NULL) == false`.

**Starter** (`daemon start`, from `host::job_state()` of the CLI process):

| CLI process | Launch | Then |
|---|---|---|
| not in a job | `DETACHED_PROCESS \| CREATE_NEW_PROCESS_GROUP` | child in no job |
| immediate job has `BREAKAWAY_OK` | + `CREATE_BREAKAWAY_FROM_JOB` | child leaves the chain up to the first job without breakaway (L13) |
| immediate job has `SILENT_BREAKAWAY_OK` only | no breakaway flag (the explicit flag requires `BREAKAWAY_OK`, L13) | the child breaks away implicitly as above |
| immediate job allows neither | — | refused before spawning, exit 1: "this terminal runs inside a job that Chaldea cannot leave, so a detached daemon could be killed when the terminal closes; run `chaldea daemon run` in a window you keep open, or start Chaldea from a terminal outside such a job" |

A spawn with `CREATE_BREAKAWAY_FROM_JOB` that fails with `ERROR_ACCESS_DENIED` is not retried without the flag (the spike's retry, L12, could start a daemon tied to the terminal): it is refused with the same message.

**The child decides.** Step 2 reads `host::job_state()` in the daemon itself and records it in `daemon.json`'s `evidence.job` (with `evidence.console` from `host::has_console()`). In `DetachedChild` mode it requires `in_job == false`; otherwise it fails with `parent_job` (an outer job that refused the breakaway, nested or not). In `Foreground` mode a job is logged as a warning ("this daemon runs inside a job and may be killed with it, with its sessions") and the daemon runs: a foreground daemon's lifetime is the window's by the user's choice, and its sessions are recovered at the next start like after any crash.

**CI assumption (A-W1).** The Windows tests that need a successful detached start (CL-11, CL-12's starter cases, the caller-handle EOF case, CL-13's console case, and the nested-job case) need the test process to be in no job or in jobs that let a child leave them. Neither of the Windows CI contexts gives that. The GitHub-hosted runner's own job forbids breakaway: run 45256283858 recorded `in_job: true, kill_on_close: false, breakaway_ok: false, silent_breakaway_ok: false` for a test executable started directly from a step. cargo puts itself and every process it starts in a kill-on-close job of its own when it can set one up, and continues without one otherwise (cargo `src/cargo/util/job.rs`); on the hosted runner it does: the same run recorded `kill_on_close: true, breakaway_ok: false, silent_breakaway_ok: false` under `cargo test`. A `daemon start` under `cargo run`, `cargo test`, or a plain runner step is therefore refused, by design. Those tests run from the WMI lane of `scripts/windows-tests.ps1` (§7) instead, in a wrapper that WMI `Win32_Process.Create` starts outside any job. `host::windows::tests::runner_can_break_away` runs there first, as a real smoke test that decides the lane: it records `job_state()`, launches a helper with the flags the starter would choose, and asserts the helper reports `IsProcessInJob(self, NULL) == false`. The detach tests depend on that precondition and fail with the recorded state in their message (never skip). This is a choice about how the tests are launched; the product's launch path is unchanged (§8 D5).

### 2.13 Logging, the Panic Hook, Owner Token, `chaldea open`

**Log subsystem** (installed once by `prepare_process`):

- **Queue and thread.** Every diagnostic is a line pushed with `try_send` onto a bounded `std::sync::mpsc::sync_channel` (1024 lines) drained by the `daemon-log` thread; a full queue drops the line and counts it (the count is logged when space returns). The thread writes each line to the current `LogTarget` with one `write_all`, ignoring errors. A stalled stderr or disk therefore blocks only the log thread, never a request, the gate, or the coordinator.
- **Target.** Per run: stderr in `Foreground`; in `DetachedChild` mode nothing until step 6, then `daemon.log` opened after the lock (`open_no_follow`, append, create `0600`). The coordinator switches the target away from `daemon.log` at shutdown step 6 and waits up to `log_flush` for the thread's acknowledgement (§2.8).
- **Rotation.** When `daemon.log` reaches its cap (8 MiB; a `cfg(test)` override sets a smaller one), the log thread checks `daemon.log.1` is absent or a regular file, renames `daemon.log` onto it, and creates a new `daemon.log`. If the check, the rename, or the creation fails (a held destination on Windows, a filesystem error), the thread stops writing to the file, counts the dropped lines, and retries every 60 s: only the creation when the rename already committed, the whole rotation otherwise. It starts no write to a file that already holds 8 MiB, so a file holds at most 8 MiB plus one line. The size it counts is what the file holds: a write that fails resets the count from the file's length (or to the cap when that cannot be read), so a partial line counts too. A detached daemon therefore keeps at most 16 MiB plus two lines of logs.
- **Subscriber.** `tracing_subscriber::fmt()` with `with_writer(QueueWriter)`, `with_ansi(false)`, level `INFO`, as the global default. `QueueWriter::make_writer` returns a `LineBuf` that collects one event's bytes (L8) and, on drop, converts them lossily to UTF-8, applies `http::trace::redact_secrets` to the whole formatted line (message, fields, and span fields alike), and pushes it.
- **Other diagnostics.** Text that reaches the user outside `tracing` (clap's rendered errors, a refusal printed by the CLI, the readiness `fail` message, the starter's own output) goes through one function, `log::diag(&str) -> String`, that applies `redact_secrets` and replaces control characters other than `\n` with spaces (clap's multi-line help and errors keep their lines); nothing else prints a diagnostic.

**Panic hook** (installed once by `prepare_process`, replacing the default hook, which would print the payload):

- Requests `Panic` on the active gate (§2.3) first, if one is registered.
- Then pushes one line: `chaldea: panic in <kind> at <file>:<line>:<column> (payload omitted)`, passed through `redact_secrets`. `<kind>` is a fixed label: the task kind of the registered task being polled on this thread (`accept`, `connection`, `socket`, `write`, `runner`), else one of the daemon's own thread names (`store-writer`, `daemon-log`, `daemon-stop`, `main`), else `runtime` for a tokio thread or `thread` for any other; a thread's name itself is never printed. The payload, its message, and a backtrace are never formatted.
- **Lock discipline.** The hook uses no `tracing`. It takes exactly two locks, each only for a fixed sequence of std operations that call no user code and cannot panic: the `ACTIVE_GATE` mutex, held only to upgrade the `Weak` (a poisoned mutex is read through `into_inner`), and tokio `Notify`'s internal mutex inside `notify_one`. `OnceLock::set` and `AtomicU8::fetch_max` take none, and `try_send` never blocks. A panic raised while one of those locks is held cannot happen, so the hook cannot deadlock on a lock its own thread holds.

The task kind comes from a thread-local that PR 7's registry wrapper sets for the duration of each `poll` of a registered task (a `Cell<Option<TaskKind>>` with a guard that restores the previous value), an internal change to `http/registry.rs`.

**Every panic stops the daemon.** A panicking runner leaves its receipt `in_progress` (like `ReceiptUncompleted`), and the hook cannot tell a harmless panic from that one, so the first panic starts the shutdown (cause `Panic`), later ones raise `worst`; exit 1 with reason `panic`. A writer job's panic is still rolled back by the store (`Panicked`, store §2.2) and the shutdown then drains normally.

**Owner token.** Step 6 checks an existing `owner.token`'s privacy (§2.4) and format, reading it through `open_no_follow` (at most 128 bytes): not of the form `chd_[A-Za-z0-9_-]{43}\n` → refuse (`TokenFile`, "owner.token is not a Chaldea token file; move it away"), nothing written. Step 12, before `serve`:

1. `owner.token` absent → issue.
2. Present (and checked at step 6): verify it in one store read run in `spawn_blocking`: `http::verify_secret_in(tx, secret)` with kind `owner`. `Ok` → keep the file unchanged. `AuthFailure::Invalid` (revoked, unknown in this database) → issue. `AuthFailure::Store(_)` or a read error → fail the start (`StoreOpen`): a store error is never taken as "invalid", so a transient failure never replaces a valid token.
3. **Issue:** `server.tokens().issue_owner(None, now + 5 s)` (one write job: `token_insert` of an `owner` token; http §2.4), then `write_replace("owner.token", secret + "\n")` (its temporary is created by `create_private_file`, §2.4).

The file's token lives until it is revoked (mvp §2.5: owner tokens last "until revoked"); a revoked or unknown token is replaced at the next start, and a missing file is reissued. The daemon never revokes a token on its own, so a paired PWA and every CLI holding the token keep working across restarts (§8 D8).

**`chaldea open [--print-url]`** (http §8 D12):

1. `Discovery::read` → `Serving`, else exit 1 ("daemon not running; run `chaldea daemon start`").
2. Read `owner.token` with the checks above.
3. One HTTP/1.1 request on a new connection: `POST /api/pair-codes`, `Host: 127.0.0.1:<port>`, `Authorization: Bearer <token>`, `Content-Length: 0`, no `Origin`, `Connection: close`, 5 s deadline, the response read completely before it (a response whose last part arrives at or after the deadline is a timeout); `200` with `PairCodeResponse { code, expires_in }`, else print the `ErrorBody` code and exit 1.
4. URL `http://127.0.0.1:<port>/#pair=<code>`. `--print-url` prints it to stdout and exits 0. Otherwise `open::run` hands it to its launcher, `host::open_url` in the binary:
   - **macOS:** `/usr/bin/open <url>` through `with_spawn_lock`, waited for up to 5 s; Launch Services passes the URL to the default browser.
   - **Windows:** `ShellExecuteExW` with `lpVerb = "open"`, `lpFile = <url>`, `SEE_MASK_NOASYNC | SEE_MASK_FLAG_NO_UI` (L21): a system API with no `PATH` lookup.
   The URL, and so the code, may appear in a launcher's or the browser's arguments (§2.1). A launcher error or a non-zero `open` exit → print the URL with "could not open a browser; open this URL yourself" and exit 0. The code is never logged. Until PR 18 mounts the PWA, `/` answers 501.

`open::run` takes the launcher as a parameter (`&dyn Fn(&str) -> io::Result<()>`), so tests observe the URL handed over without launching a browser.

`client.rs`'s HTTP client is std-only (one request per connection, as http §2.2 requires of clients), reads the status line, headers, and a `Content-Length` body of at most 1 MiB, each read bounded by the remaining deadline (`set_read_timeout`, `connect_timeout`).

### 2.15 Single Deciding Points

| Operation that can happen concurrently | Decided by | Why a second actor cannot act |
|---|---|---|
| Which process owns a state directory | the OS file lock (`try_lock`) | the OS grants it to one handle; a second gets `WouldBlock` |
| Whether an existing directory is adopted | `state_dir::prepare` (privacy + marker) | the marker is published with a no-replace `hard_link`; a concurrent start that loses reads the complete winner's |
| Shutdown start, cause, and cutoff | `ShutdownGate::first` (`OnceLock::set` of `Stopping`) | only the first `set` succeeds; later requests log and raise `worst` |
| Crash exit on a console end | `ShutdownGate::crash` → the coordinator returns | no further shutdown step starts after it is observed |
| Bare exit on a missed join | the coordinator at `C − 6 s` | it touches nothing the unjoined task may still own |
| Ownership of what startup created | the startup task, until it returns `Started` to the coordinator | the task is never aborted; the coordinator acts only on what it returned |
| Calling `ServeHandle::shutdown`, `Store::shutdown`, releasing the lock | the coordinator | no other code holds the `ServeHandle` or calls `Store::shutdown`; `release` is crate-private and called only there |
| Lock release vs exit with the lock | §2.8 step 6's conditions, read once | released only then; `Drop` never releases |
| Writing `daemon.json`, `port`, `owner.token` | the lock holder, in its startup steps | only the holder writes; replacement is `write_replace` |
| Removing `daemon.json` | the coordinator with an `instance` match | a record of another instance is never removed |
| Serving vs unreconciled receipts | startup order: step 9 before step 10 | no listener exists before reconciliation commits |
| Detached verdict | the startup task's `ready`, or the coordinator's `fail` after the lock decision | one owner of the writer at a time; the starter only reads it, EOF, or times out |
| Parent job verdict | the child's step 2 | the starter's check only chooses the launch and refuses early |
| Stop delivery | the OS (signal, event) → the gate | the gate is the only effect a stop request has |
| Stop completion | the target identity's disappearance | a new daemon's lock does not count as the old one's |
| Panics | the panic hook → the gate; startup and coordinator panics caught by `run` | as above |

**Waits.**

| Wait | Bound |
|---|---|
| Lock acquisition | 2 s of retries on contention, polled every 50 ms (a CLI allowance; L2 has no OS bound) |
| `Store::open` (including a projection rebuild) | none of its own (store §2.8); a stop during it is bounded by the startup join (`C − 6 s`), after which the process exits holding the lock |
| Each reconciler job | admission `not_after` 30 s; the reply is guaranteed by the writer (store §5); bounded by the startup join as above |
| Owner token issue | `issue_owner` deadline 5 s + PR 7's reply grace |
| `write_replace` rename retries | the caller's cutoff: 500 ms from the first attempt at startup, the rewrite's cutoff for `stopping` |
| Startup join | until `C − 6 s`, deadline first (§2.8) |
| HTTP drain | `ServeHandle::shutdown(C − 5 s)`, which returns by its deadline |
| Participants | until `C − 3 s` |
| `Store::shutdown` | `C` (its own bound), observed until `C + 250 ms`, deadline first |
| Record removal (shutdown step 5) | 500 ms budget, retried every 50 ms; no deletion issued after it |
| Log target switch and flush at exit | 100 ms each |
| Readiness (starter) | 15 s from the start, covering the GUI-domain probe (at most 3 s), stale-label scavenging (at most 2 s), `bootstrap` (all but the last 3 s), the label `print` (the reserved 3 s), `bootout`, and the verdict; EOF follow-up at most 2 s within it |
| `daemon stop` | 15 s from the start |
| `open`: request 5 s; `/usr/bin/open` 5 s; `ShellExecuteExW` | as listed; `ShellExecuteExW` has no bound of ours (§2.1 rule 6) |
| Signal listeners, stop listener thread, log thread | unbounded by design: they end with the process |

**Windows and macOS differences.** Lock: `flock` vs `LockFileEx` (released lazily after a crash on Windows). Detach: launchd job + fork + `setsid` on a GUI host (`setsid` alone without a GUI domain) vs `DETACHED_PROCESS` + breakaway. Readiness: Unix socket vs stdout pipe. Stop: `SIGTERM` to a verified identity vs a `Global\` event per instance. Console end: Windows only, a crash exit (Unix has `SIGHUP`, a graceful stop). Parent job: Windows only. Privacy: owner, mode, and ACL vs owner and DACL. Browser: `/usr/bin/open` vs `ShellExecuteExW`. Wait ownership: macOS only (Windows has no reaping, PR 4 §2.1).

**Known limits** (no test, by design):

- **Other OS accounts** (§2.1): the CLI does not authenticate the server, so a process of another account that holds the port can receive the CLI's Bearer token or serve the PWA origin; the pair code may appear in a launcher's arguments. Reopen when Chaldea runs on a host shared with other OS accounts.
- **Unix stop PID race**: between `daemon stop`'s identity check and its `SIGTERM`, the daemon can exit and its pid be reused by another process of the account, which then gets `SIGTERM` (pty-unix §2.5 describes the same window). A private control socket per instance (§3) closes it.
- **Elevation on Windows**: a daemon started elevated cannot be stopped from a non-elevated terminal of the same account (L19); `daemon stop` reports access denied.
- **Windows jobs**: a daemon inside any job is refused when detached, even if no kill-on-close job is in its chain, because the chain is not visible (L13); logoff and system shutdown end a detached daemon without a shutdown (crash-only recovery applies).
- **Console end**: a foreground Windows daemon whose console closes exits without a graceful shutdown; the next start recovers.
- **Pending launch**: `daemon stop` sees only a published daemon; a launch that a timed-out `start` submitted and that has not yet published its record is invisible to it until it does (the starter's timeout message names the pending pid or launchd label).
- **Slow startup step at a stop**: a stop while a step runs longer than 4 s (a projection rebuild in `Store::open`) ends in a bare exit holding the lock; the next start recovers.
- **Discovery race** (§2.6): between a daemon's death and a new holder's first record write, a client that checked the old identity just before the death can send one request to a port nobody or a new process holds.
- **Lock release after a Windows crash** can take longer than the 2 s allowance (L2); `daemon run` then reports "already running" and succeeds once the OS released it.
- **A stalled log target** loses lines once the 1024-line queue is full; the drop count is logged when space returns.
- **Same-account processes** can plant links in the private state directory between the checks and the opens; they are trusted (§2.1).

## 7. Tests and Completion Commands

**Kinds of tests.**

- **Unit tests** in `crates/daemon/src/lifecycle/tests/` (one file per lifecycle part; the daemon crate's helper-process tests are together in `helpers.rs`) call `run_isolated` and the lifecycle's parts in-process with `cfg(test)` fault points (a parked step, a barrier inside a step, a writer job held past the cutoff, the merged `IoErrAfterCommit`, a rename, write, or directory-sync failure, a bind failure, a panicking component), the test's own state directory, and the gate triggered directly. A test that needs a port of its own binds `127.0.0.1:0` and keeps the listener for the test binary's lifetime (`faults::hold_port`); step 10 takes a clone of that listener instead of binding, so the port is never released between the test's choice and the daemon's bind. A test that binds a port of the range (the scan, or a saved port the scan chose) holds the port range (`faults::hold_range`) for its whole run, so no other test of the process binds a range port while that test's port is free between its starts; in test builds, step 10 refuses a range port while no test of the process holds the range (a process-wide check: it catches a range bind with no holder, not a second test binding while another holds it). They never call `prepare_process` or `run`, register nothing process-wide, and leave no task running after they return.
- **Helper-process tests.** Everything that touches process-wide state (the panic hook, the global subscriber, signal dispositions and masks, signals, consoles, jobs), leaks a lock, or leaves a never-returning task runs in a helper: the test binary re-executes itself with an environment variable selecting the helper (the pattern of PR4-CL-27), the helper calls `prepare_process` and then `run` (in the daemon crate its `cfg(test)` twin `run_process_with`, which differs only in taking the fault points) as `dispatch` does, and exits through the same `std::process::exit` call, and the parent observes exit codes, output, files, and the lock, and kills the helper by pid if it outlives the test's timeout (30 s unless stated). A detached helper run whose test is not about job membership sets its step-2 job state to "in no job" through the fault points (`cfg(test)` only), so the job `cargo test` puts its processes in on Windows cannot refuse it; the job check is covered by `startup::detached_child_in_a_job_fails_parent_job` and the Windows CL-12 cases.

No test picks a port by binding and releasing it: a daemon chooses its own (the range of §2.6, or its saved port), the test reads it from the `listening` line or the record, and a later run that needs a port uses that one. `daemon_run`'s tests run one at a time, so a port one of them expects (the first free one of the range, or its saved port) is not taken by another's daemon in between. `daemon_start`, `daemon_stop`, and `daemon_macos` are `harness = false` binaries with a shared runner (`tests/support/runner.rs`): with `CHALDEA_TEST_AS_CHALDEA` set the test binary runs as `chaldea` through `dispatch_with` (`tests/support/faults.rs`), so the starter's `current_exe()` child, launchd job included, is the test binary and carries the fault seams the release binary lacks: `Seams` (components that park a step, slow the shutdown, hold a store reader, or log secret markers; ## 8. Decisions

**D1. `crates/cli` is the binary; the lifecycle is `chaldea_daemon::lifecycle`.** `main` is one call to `chaldea_cli::dispatch`, which decides `hook-emit` first, runs `prepare_process` once, parses with `try_parse_from`, then calls `run`, which returns an `ExitReport`; unit tests use `run_isolated`. Dependencies: `clap =4.6.8` (no color, no suggestions); `tokio` gains `rt-multi-thread` and `signal`; `tracing-subscriber =0.3.23` becomes a normal daemon dependency; `windows-sys` gains the features of §1; `daemon` depends on `pty-runtime`. The `CommandRegistry` reaches `HttpServer::new` through `Built::commands` (§2.14).

**D2. OS primitives go in `pty-runtime::host`**, safe functions over new `unix::sys` / `windows::sys` entries, including the launchd calls, the readiness channel, privacy checks and private file creation, the stop event, and the browser launch; `daemon` and `cli` keep `forbid(unsafe_code)`. `host::process_identity` is the public identity lookup PR3 D7 deferred to its first consumer.

**D3. One daemon per state directory is `File::try_lock` on a data-less `daemon.lock` that is never removed and never released by a drop**, retried for 2 s on contention, released in-process only under §2.8 step 6's conditions (the startup task joined, no aborted HTTP task, `readers_returned` and `writer_exited`, the log target switched).

**D4. Stop goes through the OS**: `SIGTERM` to a verified identity on Unix (with the stated PID race), a `Global\` event per instance with an account-only DACL on Windows; it works during startup; `daemon stop` has one 15 s deadline, completes when the target identity is gone, reports exited, denied, and listener-less targets distinctly, and never kills.

**D5. On Windows a detached daemon must be in no job.** The starter breaks away explicitly with `BREAKAWAY_OK`, implicitly with `SILENT_BREAKAWAY_OK`, and refuses otherwise; the child verifies `IsProcessInJob(self, NULL) == false`; a foreground run warns. Reconciled with PR 4's A13: nesting works under any job tested, so the check guards the daemon's lifetime only. The GitHub-hosted runner's own job forbids breakaway (A-W1, §2.12); the product stays as it is, and CI runs the detached-start tests from a job-free process that WMI starts (§7). The reasons: the refusal is the designed answer in a job that forbids breakaway; a CI runner is not a supported user launch context; and WMI as the launch path (option B of §3) would add COM, a separate readiness channel (WMI can neither pass the inherited stdout handle list nor return the process handle), deadline uncertainty in `ConnectServer` and `ExecMethod`, and a deliberate change to what a job's owner allows. Reopen (WMI `Win32_Process.Create` as a launch path, herdr's route) if a supported user launch context (a terminal, an editor's integrated terminal, Windows OpenSSH if supported) runs the shell inside a job without breakaway. A CI runner decides only how the tests are launched.

**D6. On a macOS GUI host, `daemon start` submits a one-shot launchd job in the user's GUI domain whose process forks the daemon and exits**, so quitting the terminal app does not kill the daemon (the daemon is a persistent agent host reached from the PWA, and quitting a terminal app is ordinary use). A GUI-domain probe failure or a refused submission fails the start with a pointer to `daemon run`, and a submission that cannot be resolved by its label is a timeout naming the label; there is no silent fallback. Only a confirmed absent GUI domain or an SSH session uses a direct child that calls `setsid`. The record says which path ran.

**D7. One coordinator, one budget.** The first trigger fixes the cause and the cutoff (10 s) together; the startup task is never aborted and is joined until `C − 6 s`, after which the process exits bare, holding the lock; HTTP, participants, and the store end at `C − 5 s`, `C − 3 s`, and `C`, and neither HTTP's nor the store's shutdown is cut short; a Windows console end starts no further step and exits holding whatever lock is still held; a clean stop exits 0 whether it came before or after startup completed; every panic stops the daemon, and startup and coordinator panics are caught.

**D8. The owner token file holds one owner token that lives until revoked**, kept only while private, reissued at start when missing or `Invalid` (never on a store error); no automatic rotation.

**D9. The state directory and secret files are private by mechanism**: created with explicit owner-only descriptors (mode `0700` / `0600`; protected DACLs) verified on the handle, existing ones checked against one private-trustee set and never modified; directories adopted only when created, empty, or marked, with the marker published without replacement.

**D10. Readiness is one verdict line** (stdout pipe on Windows, a Unix socket in a short private directory on macOS) within 15 s, sent after the lock decision with one reason chosen by precedence (`stopped` when a clean stop came before readiness, a verdict token separate from the daemon's exit status); a timeout never kills the child, and a late child ignores a missing channel.

**D11. The default state directory is `$HOME/.chaldea` (macOS) and `%LOCALAPPDATA%\Chaldea` (Windows).** Short, non-roaming paths: mvp §2.6's `worktree_base` defaults to `<state_dir>/wt` (MSVC's 260-character limit, arch §5), and SQLite WAL needs a local, non-synced filesystem (store S7). Moving it later needs a migration of the database and worktrees.

**D12. The first port is the first free one of `7373..=7472`, saved once the daemon serves (the rename is the commit), kept across starts that never served; a taken saved port or an exhausted range is reported, never moved.** Below the OS dynamic range, so it is not handed to outgoing connections; an override changes the pairing origin and says so.

**D13. Other OS accounts are outside the threat model** (§2.1): the CLI does not authenticate the server, the PWA origin is not an authenticated server, and the pair code may appear in a launcher's arguments; reversible by a server-authentication handshake or a revised browser credential, reopened when Chaldea runs on a host shared with other accounts. Private state and the adoption rules are kept regardless.

**D14. The public CLI names PR 8 adds.** `--state-dir` (global) with `CHALDEA_STATE_DIR`; `daemon run [--port]`, `daemon start [--port]`, `daemon stop`; `open [--print-url]`; exit codes 0 `Ok`, 1 `Failed`, 2 `Usage`, 3 `AlreadyRunning`, 4 `Timeout`, with the failure reason in the output instead of the code. Reason: scripts can tell "already running" and "still starting" from failure, tests run isolated daemons through the flag or the variable, and the surface stays small. Alternatives: no environment variable (avoids a `CHALDEA_*` variable, which is scrubbed from children anyway, mvp §2.5, but lengthens every non-default invocation); one code per failure reason (more precise, but a wider contract with no named consumer). Adding codes or flags later is additive; renaming or removing these breaks scripts.
