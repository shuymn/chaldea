## 1. Scope and Non-Goals

**Goal (issue #2).** A Rust Sans-IO core (`crates/core`, `crates/pty-runtime`, `crates/daemon`), daemon-owned PTYs, authenticated hook ingest, an SQLite append-only event store, the `chaldea` CLI (`spawn`, `send`, `wait`, `stop`, `mailbox`, `inspect`, `hook-emit`), and a local single-origin PWA (`packages/contracts`, `packages/web`) with a web terminal view, on macOS and native Windows hosts.

**In scope.** The irreversible core of arch §2 (§2 below); the five seams of arch §4 at the depth the milestones M1–M3 of §4 need; the minimum UI (thread list, timeline with events and state, plain `<textarea>` composer with IME guards, attention banner, the web terminal view with a phone key bar, usable on mobile viewports); the external-agent Rescue surface (§2.8).

**Non-goals.** The Phase 2 relay (`packages/relay`) and therefore Android remote access; the local PWA binds to `127.0.0.1` only, and contracts leave room for the relay without implementing it. These reversible layers of arch §2: Tauri / Capacitor, the diff view and split panes, visual styling, and a separate PTY-owning process; `docs/design/chaldea.pen` remains wireframes only. A terminal emulator other than the web terminal view (invariant 2: ghostty-web over prebuilt libghostty-vt WASM in `packages/web`, never a state source). Orchestration strategy in daemon code (invariant 2). Every item of §4 "Deferred".

JSON Schema is generated alongside with `schemars` for runtime validation in `packages/contracts`.

### 2.1 Event Envelope, Event Kinds, Store

**Streams.** Every event belongs to one stream: `host` (thread registration and closing, worktrees, host- and workspace-scoped surfaces, unbound `raw_unknown`) or `thread:<thread_id>` (everything about that thread, across all its launches). `seq` is per-stream, gapless, monotonic from 1, assigned inside the append transaction. An internal `global_seq` orders events across streams and is not exposed.

| Option | Precedent | Verdict |
|---|---|---|
| A. One global sequence; clients filter by thread | T3 Code orchestration v2: `sequence INTEGER PRIMARY KEY AUTOINCREMENT` with `thread_id` indexes (`apps/server/src/persistence/Migrations/055_OrchestrationV2.ts:20-38`) | Rejected: gaps inside one thread are not detectable, and a Phase 2 per-thread cache must re-derive order. |
| B. Per-stream version plus global sequence | T3 Code orchestration v1: `stream_id`, `stream_version`, unique `(aggregate_kind, stream_id, stream_version)`, global `sequence` (`Migrations/001_OrchestrationEvents.ts:8-28`) | **Adopted** as `stream_id` + `seq`; it matches arch §4.1's `stream_id + after_seq` directly. |
| C. Per-item notifications with no replay cursor | Codex app-server `thread/status/changed`, `turn/started`, `item/completed` (`src/protocol/common.rs:2087`, `:2116`, `:2127`) | Rejected for storage (a live protocol, not a log); its vocabulary informs §2.2. |

**Envelope** (public):

| Field | Type | Meaning |
|---|---|---|
| `stream_id` | string | `host` or `thread:<uuid>` |
| `seq` | u64 | per-stream, gapless, from 1 |
| `event_id` | UUID | unique per event; generated by the daemon and passed into core |
| `schema_version` | u32 | version of the event schema set |
| `idempotency_key` | string | dedupe key, unique per stream |
| `kind` | string | event kind; an open set on the wire |
| `thread_id`, `launch_id`, `command_id` | UUID or null | the thread, the launch (one process lifetime of a thread), and the causing command |
| `source` | object | `{ kind, agent, cli_version, transcript: { generation, path, file_id, offset_end } \| null }`; the known `kind` values are `hook`, `transcript`, `process`, `command`, `daemon`, `extension`, and readers keep an unknown `kind` or `agent` string as received (`Open<T>`) |
| `occurred_at`, `recorded_at` | RFC 3339 UTC, ms | source time (or `recorded_at` when the source states none); append time |
| `payload` | object | kind-specific |

**Open envelope and forward-compatible decoding.** Readers validate the envelope first, with `kind` as a string and `payload` as raw JSON, then decode the payload by kind. An unknown `kind`, a `schema_version` above the reader's, or a payload that fails its schema becomes a `GenericEvent` (envelope plus raw payload), rendered as "unknown event" in the PWA and printed as JSON by the CLI; it never fails a page or a stream. Rust: `EventEnvelope { kind: EventKindTag, payload: Box<RawValue>, … }` with `TypedEvent::decode(&EventEnvelope) -> Result<TypedEvent, GenericEvent>`. TypeScript: `packages/contracts` validates the open envelope with the generated JSON Schema, then maps it to the generated union of known kinds or to `GenericEvent`. No `#[serde(flatten)]` is used on the envelope.

**`Content`** (public) is the type of every payload field that can be large (`text`, `prompt`, `input`, `output`, `body`, `raw`, VT grids): `{ "inline": string, "encoding": "utf8" | "base64" } | { "blob": { "sha256", "size", "media_type" }, "preview": string, "preview_lossy": bool }`. `utf8` carries text, `base64` bytes that are not valid UTF-8. Above 64 KiB the content moves to a blob; `preview` is its first 1 KiB decoded as UTF-8 with each invalid sequence replaced by U+FFFD (`preview_lossy: true` when any was); a valid character that crosses the 1 KiB boundary is left out, not replaced, so a cut alone never sets `preview_lossy`. The rest of the payload stays inline (arch §4.2 size-bounded outputs).

**`schema_version`** is one integer for the whole schema set, starting at 1. Additive changes (an optional field, a new kind) do not bump it; a change of meaning or type of an existing field does, except before any producer has persisted events: such a change (D9's `vt_snapshot_taken.grid`, `docs/design/pty-runtime.md`) keeps version 1. Per-kind versions were rejected: no client can use the extra precision.

**Idempotency keys** are deterministic so that replaying a source yields the same key; the store rejects duplicates (`UNIQUE (stream_id, idempotency_key)`):

| Source | Key |
|---|---|
| Hook payload | `hook:<emit_id>`. `emit_id` is a UUID the emitter generates once per invocation (`X-Chaldea-Emit-Id`) and reuses for its own retries. Deduplication happens on `(launch_id, emit_id)` **before** routing to a stream: each delivery stores, durably before the response, its immutable first reply, a receipt ordinal, and its current routing (`appended` with stream and seq, `buffered` while its launch is unbound, or `raw_unknown`); a retry replays the first reply, and only the routing changes when a `buffered` delivery is promoted (§2.9). A CLI that runs a hook again starts a new emitter with a new `emit_id`, which is a second event; content is never deduplicated (two identical prompts are both real). |
| Transcript line | `transcript:<generation>:<offset>` of the line start |
| Process lifecycle | `launch:<launch_id>:<reserved\|started\|exited\|death_confirmed>`; a check's evidence `launch:<launch_id>:evidence:<spawn_failed\|close\|probe:<attempt>>`, the attempt a UUID the daemon mints per probe |
| Command | `command:<command_id>:<n>` for the n-th event of the command |
| Derived event | `derived:<cause key>:<name>` |
| Extension `POST /events` (deferred, §2.8) | `ext:<caller key>`, required from the caller |

`turn_ref` is the CLI's own turn identifier when its payload has one (Codex `turn_id`, `hooks/src/events/permission_request.rs:39`; Claude `prompt_id` among the common input fields of the hooks reference, presence per event **unverified**). `workspace_id` is derived from the canonical path of the repository's common git directory (`git rev-parse --git-common-dir`), so a repository and all its worktrees share one; outside git it is derived from the canonical cwd. A diff kind (`artifact_diff`, arch §4.2) is not defined in the MVP: the diff view is a reversible layer, and adding a kind later does not bump `schema_version`.

**Store** (internal). SQLite in WAL mode with `synchronous=FULL` and one writer task. `events` holds the envelope columns plus `payload_bytes` and a per-stream running `cum_bytes` (an O(1) replay size). Update and delete triggers abort with `RAISE(ROLLBACK)`, `recursive_triggers=ON` makes a conflicting `INSERT OR REPLACE` hit the delete trigger, and the store never issues `REPLACE` or `UPSERT` on `events`; triggers and checks also enforce the gapless per-stream `seq`, the global order, `cum_bytes`, stream membership, and the transcript generation order and path (`docs/design/event-store.md` §2.4). Blobs live in `blobs`, with each stream's references in `blob_refs` (layout: `docs/design/event-store.md` §2.4). `command_receipts`, `hook_deliveries (launch_id, emit_id, first_reply, receipt and commit ordinals, routing)`, and `tokens` are their own tables. Internal values that projections need but no client sees (the readiness write basis, transcript continuity) live in an immutable per-event annex column, so rebuild reproduces them.

**Projections** (`threads`, `launches`, `inputs`, `approvals`, `surfaces`, `worktrees`, `transcript_cursors`) change only with the event that changes them, in its transaction, and dropping them and replaying `events` reproduces them:

| Projected column | Event payload |
|---|---|
| thread agent, cwd, `workspace_id`, parent, role, closed | `thread_registered`, `thread_closed` |
| axes, attention set | `status_changed` for process, turn, and attention; `task_set` for `task_state` (the paired `status_changed(TaskState)` is checked at write time and changes nothing) |
| current and reserved launch, pid, start time, manual, exit reason, death confirmed | `launch_reserved`, `launch_started`, `launch_exited`, `launch_death_confirmed` |
| `session_id`, `transcript_path` | `session_bound` |
| gate evidence (last readiness, its kind, and its write basis; last write of any origin; last human write that closes the gate; last turn start) | `readiness_observed`, which also stores the write basis: the PTY writer's `last_started(counted)` captured at the evidence's intake, checked by the writer at dispatch (VT replies count by default; `docs/design/pty-runtime.md` §2.3); `input_state_changed` to `sending` and every `human_write` for the last write of any origin (a `card_key` advances only this one); `human_write` with origin `attach` or `key` for the last gate-closing human write; `user_message` (from `UserPromptSubmit`) and `session_bound` for the last turn start |
| input text, encoding, launch, `created_by`, state, `sent_after_seq`, attribution | `input_created`, `input_state_changed`, `user_message.input_id` |
| approval card, correlation, outcome | `approval_requested`, `approval_resolved` |
| current surfaces | `surface_update` |
| worktree record and owner | `worktree_changed` |
| transcript generation, path, `file_id`; offset | `transcript_generation`; `source.transcript.offset_end` of the last transcript event |

An offset applies only to the generation and `file_id` of its event. A cursor offset that advanced past lines producing no event is not in any event; after a rebuild the cursor rewinds to the last event's `offset_end` in the current generation (or 0 after its `transcript_generation`), which is the only permitted rewind: the tailer re-reads only the bytes after the last stored event, which produced no event, so nothing is stored twice. A resubmitted stored line never reaches the key check: the cursor checks run first and refuse it (`StaleCursor` against an old cursor, a refused batch against the rebuilt one), and the transcript idempotency keys catch only a line whose batch passed them. Tokens, receipts, and hook deliveries are not projections.

**Transcript cursor rules.** A path is accepted only from a hook bound to the thread's current session; never from directory guessing (arch §4.2). `file_id` (device + inode on Unix, volume serial + file index on Windows) comes from the same open handle the tailer reads. `offset` is just after the last complete line. A new generation starts whenever continuity with the cursor is disproved: the path or `file_id` changed, the file is shorter than `offset`, or the bytes before `offset` changed (truncate-and-regrow); how each case is detected is a C1 / X1 obligation. The change is appended as `transcript_generation` before any line of the new generation is read, so every generation the events refer to is durable and rebuildable; the alternative, keeping the checkpoint table out of rebuild, was rejected because a lost checkpoint could not tell which file the offsets meant. A batch of events and the cursor advance commit in one transaction that first checks the stored `(generation, file_id, offset)` still matches. A trailing partial line after `launch_exited` becomes `raw_unknown` (`partial_line`). `transcript_path: null` (Codex, arch §5) creates no cursor. Rejected alternatives: a cursor without generation (a replaced file mixes histories), a line-count cursor, a last-line hash.

**Public vs internal.** Public: envelope, kinds, payloads, `Content`, `GenericEvent`, `schema_version` rules, `X-Chaldea-Emit-Id`, the `ext:` key format. Internal: SQL schema, projections, `global_seq`, blob layout, other key formats.

### 2.2 Thread State: Three Axes and Attention

Three independent axes (arch §2, §4.2) plus an attention set. Every change has an explicit, typed cause; the reducer's input type has no variant built from PTY output, so screen text cannot drive state (invariant 1). VT snapshots and DECSET 2004 are read only to gate input and to show a human what the CLI shows.

| Axis | States | Driven by |
|---|---|---|
| `process_state` | `starting`, `running`, `stopping`, `exited` | `launch_reserved` (§2.9); `launch_started`; `stop` accepted; `launch_exited` (also for a spawn failure) |
| `turn_state` | `unknown`, `idle`, `running`, `awaiting_approval` | `unknown` before a launch's first signal, on `Stop` until its readiness evidence (§2.7 `readiness_evidence`), on an interrupt, and after `exited`; `idle` on `readiness_observed`; `running` on a bound `UserPromptSubmit`, and when the last open card resolves while the turn is active (§2.10); `awaiting_approval` on `approval_requested`. The interrupt input comes only from an explicit event: Codex's `Interrupt` hook (spike §3; v0.171.0 `hooks/src/engine/discovery.rs:957`); Claude's adapter hook list (§2.7) has no interrupt event, so an Esc interrupt leaves `running` until the next evidence. |
| `task_state` | `none`, `active`, `blocked`, `completed`, `failed`, `cancelled` | set at registration, then only by `task_set` (thread itself, its parent, or a human; §8 D2) |

**Attention** is a set of causes, separate from `turn_state`, so clearing a cause never has to guess the turn. Each cause has its own clearing event:

| Cause | Raised on | Cleared on |
|---|---|---|
| `session_start_timeout` | no `session_bound` 20 s after `launch_started` of a non-manual launch (spike §4.7); a `SessionStart` that does not bind, such as `foreign_session`, does not stop it | `session_bound`, or `launch_exited` |
| `startup_stall` | an expected Codex `Hooks need review` after a CLI upgrade (arch §5) | `session_bound`, or `launch_exited` |
| `input_unconfirmed(input_id)` | that input entered `unconfirmed` | that input left `unconfirmed` |
| `input_gate_timeout(input_id)` | that input `queued` for 60 s | that input left `queued` |
| `resume_blocked` | a resume refused because the old launch's death is not confirmed (§2.9) | `launch_death_confirmed` |

Every raise and clear is a `status_changed` event (the outbound `attention` extension hook that would run on it is deferred, §2.8). Timers are explicit inputs (`Tick(now)` fed by the daemon). A **relaunch** sets `process` to `starting` and `turn` to `unknown`, keeps `task`, and emits no `thread_registered`. Process exit and relaunch never change `task_state`; an orchestrator sees "exited, task still active" and decides (invariant 2).

| Option | Precedent | Verdict |
|---|---|---|
| One status enum | herdr `AgentState { Idle, Working, Blocked, Unknown }` from screen detection (`src/detect/mod.rs:11-20`) | Rejected: mixes the axes and is fed by screen scraping. |
| Thread status + turn status | Codex app-server `ThreadStatus { NotLoaded, Idle, SystemError, Active { active_flags: [WaitingOnApproval, WaitingOnUserInput] } }` (`src/protocol/v2/thread.rs:1810-1827`), `TurnStatus { Completed, Interrupted, Failed, InProgress }` (`v2/turn.rs:34-39`) | Partly adopted: its flags map to `awaiting_approval` and attention. No task axis, because it has no orchestration outcome. |
| Three axes + attention set | arch §2 | **Adopted.** |

Public: field names, state and cause values, `status_changed` / `task_set` payloads. Internal: reducer, timer defaults.

### 2.3 Input State Machine and Gate

An input is one prompt sent through `chaldea send` or the PWA composer. `send` writes the adapter-encoded text plus one submit. A paste recognised on the attach WebSocket (the web terminal view's paste) is encoded text only and never carries a submit; what the human's next Enter does is the CLI's (it normally submits the prompt, but on Codex for Windows a pasted trailing `@token` can make it pick a file, `docs/design/input-encoders.md` D10) (§4, T1).

```
queued ──(gate open; attempt persisted)──▶ sending ──(text + submit written)──▶ sent ──(attributed ack)──▶ acked
  │                                          └───────(write outcome unknown, daemon restart, launch_exited)────┐   │
  │                                                                     (window expired, ack not attributable)─┴─▶ unconfirmed
  ├─(validation failed, zero bytes)──▶ rejected                                  late attributed ack ──▶ acked ◀─┤
  └─(cancel, launch exited, daemon restart; zero bytes)──▶ cancelled             input resolve ──▶ acked (by human) | dismissed
     (also sending ──(writer recheck failed before the first byte)──▶ cancelled)
```

**Gate (one conservative rule).** A queued input is written only when the current launch has **positive readiness evidence** newer than the last write of any origin: a `readiness_observed` event from the adapter's `readiness_evidence` capability (§2.7) or an owner's explicit `chaldea ready <thread>` (`evidence: owner_asserted`, accepted only for the current bound launch; for an unbound launch, e.g. a manual Codex launch, it is refused and writes nothing; it asserts that the CLI's composer is in its normal edit mode and empty, with no search or popup open, which no signal shows (`docs/design/input-encoders.md` §2.6); a send made when that does not hold follows the ordinary ack rules and is never resent). In addition, `turn_state = idle`, no other input of the current launch is `sending`, `sent`, or `unconfirmed` (inputs of earlier launches never block), and for bracketed paste `TermMode::BRACKETED_PASTE` is set (prior-art row 4a).

- **`readiness_evidence` modes** (per adapter, §2.7): `post_decision` — a signal that the CLI emits only after every `Stop` hook decided (none is verified yet; the C1 and X1 fixtures look for one); `stop_settle` — a `Stop` followed by a settle interval with no further event of the launch, with a known race: a user `Stop` hook that blocks after the interval (Claude per the hooks reference; Codex `hooks/src/events/stop.rs:83`) makes the next prompt land in a running turn, where it is attributed or left `unconfirmed`, never resent; `owner_only` — only `chaldea ready` (Claude's `SessionStart` is no evidence either). The MVP default is §8 D8.
- Any human write (terminal view input over the attach WebSocket, raw `key`) after the evidence closes the gate (`human_write`). A key sent from an open approval card (D1; it carries that card's `launch_id` and `approval_id`) answers a dialog while the turn awaits approval, not the composer, so it is recorded with origin `card_key` and does not close the gate; the turn's next readiness evidence opens it. It reopens only on `chaldea ready` or on evidence from a later turn, i.e. with a `UserPromptSubmit` or `SessionStart` of the launch between the human write and the evidence; evidence of the same turn as the human write, however late it arrives, does not reopen it. Detaching does not reopen it.
- The gate also stays closed, with the input `queued`, while a counted write started after the evidence's write basis, while a human unit is submitted and not yet recorded, and while an input unit of the launch may still write. An attempt that wrote zero bytes leaves the gate as it was. A settle completion counts only for a `Stop` whose turn start follows an end the daemon saw; otherwise the owner runs `chaldea ready` (`docs/design/supervisor-send.md` §2.4; its accepted gap is under "Residual constraint"). `chaldea ready` is accepted for the current, bound, `running` launch of an open thread (optional `expected_launch_id`), and refused with `unit_running` while an input unit may still write.
- Unknown readiness means closed: no evidence yet, or an interrupt.
- After 60 s in `queued` the input raises `input_gate_timeout` with a `vt_snapshot_taken` and stays `queued`, zero bytes written.
- **Writer revalidation.** The open job decides the gate on the store; the PTY writer then refuses the unit with zero bytes at its first write permission when a hook was taken in after the gate was read (the launch's hook fence), when a counted write (VT replies included by default) started after the write basis stored with the readiness evidence, when DECSET 2004 changed, or when the launch exited or was sealed, and writes the text and its submit as one unit that no human write can interleave. A refused unit cancels the input with zero bytes. Human writes queued during that unit go after it and make a later ack non-attributable if their order against the hook is ambiguous, so the input stays `unconfirmed`.

**States.**

- **`sending`**: the transaction that records `sending` and `sent_after_seq` (the thread stream's head) commits before the bytes go to the PTY writer.
- **Ack**: a `UserPromptSubmit` of the same launch with `seq > sent_after_seq` whose prompt is the input's expected form as `core::input::encode::prompt_matches` decides it (the text after the adapter's documented transforms: Claude's TAB expansion, NFC, and paste wrapper, arch §5; Codex's `win_keys` composition, trimming, and the positional prompt's LF newlines; `docs/design/input-encoders.md` §2.4), and only if, at the hook's intake, this input's write had dispatched and no other counted write (attach, `key`, another input, and by default a VT reply) had started after it, by the PTY writer's position (the Codex positional prompt is anchored at the writer position sampled when the launch was published, and only attach, `key`, and input writes above it count), and only if no earlier submission of indistinguishable text could account for the hook: a human write, or an earlier dispatch whose own hook has not been attributed and whose input's `prompt_matches` accepts the hook's prompt, is such a submission, and unknown history (a raw human write whose submission the daemon cannot see) counts as one, so the input stays `unconfirmed`. Neither the hook's arrival order nor its intake facts tell which submission it belongs to (docs/design/hook-ingest.md §2.6 "Retries"). Position, not wall time, orders candidates. A hook whose prompt matches no in-flight input is a `user_message` without `input_id`; one that matches more than one input acks none. An input still `sending` is acked only by a hook taken in after its unit completed, in that hook's job; an earlier input of matching text that the owner resolved (`acked` by human, `dismissed`) counts as a competing submission. A permitted unit with no completion 30 s after its first write permission shows its input `unconfirmed`, and the next send waits for that unit.
- **`unconfirmed`**: the 30 s window (spike §4.7) expired, the candidate is not attributable (it stays a `user_message` without `input_id`), the write outcome is unknown, the daemon restarted, or the launch exited while `sending`/`sent`. **Never resent** (arch §4.3). A late attributable ack moves it to `acked`. `chaldea input resolve <id> --outcome delivered|dismissed` settles delivery only: `acked` (`by: human`) or `dismissed`, keeping the history and clearing `input_unconfirmed`; it does not assert readiness, which is `chaldea ready`. Both `ready` and `input resolve` are recovery commands that write no PTY bytes.
- **Prompt limit.** `send` and recognised attach pastes refuse prompt text above `core::input::MAX_PROMPT_BYTES` (256 KiB UTF-8) before admission, with zero bytes and no input created.
- **`rejected`** (`docs/design/input-encoders.md` §2.5: ESC or C0 other than TAB/CR/LF, prior-art row 4b; DEL on Codex's paste and `win_keys` and C1 on Codex's paste, as `lossy_text`; an empty `send`, or a whitespace-only one, as `empty_prompt` on every adapter unless an earlier rule of §2.5 applies (`U+0085` alone is `lossy_text` on Codex's paste), and an empty attach paste; for Codex on Windows, trimmable leading/trailing whitespace and TAB, spike F-1d, §8 D6) and **`cancelled`** are terminal with zero bytes written. `cancelled` comes from `queued` (`chaldea input cancel <id>`, the launch exited, a daemon restart) or from `sending` only when the writer's recheck fails before the first byte.
- **Codex positional first prompt**: its `input_created` (`initial_state: sending`) commits with `launch_reserved`, since its bytes travel in argv; `launch_started` moves it to `sent` with `sent_after_seq` = that event's seq, in the same transaction and before any waiting hook is released. If the spawn is confirmed not to have started (e.g. the executable was not found, `spawn_failed` before the child existed), it goes `sending` → `rejected` with that reason; only an indeterminate spawn (a crash between reservation and `launch_started`) is recovered as `unconfirmed`. Its ack window is suspended while `session_start_timeout` or `startup_stall` is active.

**Residual constraint.** Hooks are asynchronous processes and carry no CLI-side ordering against the daemon's PTY writes, so ack attribution and readiness remain inferences. The contract guarantees only that (a) no input is ever resent automatically, (b) no input is acked without a text match, and (c) any ambiguity leaves the gate closed or the input `unconfirmed`, with one accepted exception (`docs/design/supervisor-send.md` L-11): when a turn's `UserPromptSubmit` was lost, or a turn had a second `Stop`, a late `Stop` of that turn taken in after the next turn's `UserPromptSubmit` can settle while the next turn runs, and the next queued prompt and its Return may then be written into the running CLI (it is attributed or left `unconfirmed`, never resent). Later PRs do not need to close this gap.

Alternatives: auto-resend (rejected by arch §4.3; an extra Return can accept a popup, arch §5); ack by screen echo (invariant 1); readiness inferred from DECSET 2004 or the screen (invariant 1; Codex sets 2004 while a review dialog is up, spike §3; no test covers this yet, and X1 owns Codex startup stalls); special-case rules per input source (rejected: the gate requires the same positive evidence from every source).

Public: state names, payloads, `send`, `ready`, `input resolve`, `input cancel`, the `readiness_evidence` modes. Internal: window, timeout, and settle defaults. The states beyond the architecture's four are §8 D3.

### 2.4 Sync API and Commands

**Replay.** `GET /api/events?stream_id=<id>&after_seq=<N>&limit=<L>[&epoch=<E>]` (arch §4.1). `limit` 1–1000, default 200 (else 400). `epoch` is a random id stored at database creation; the client omits it on its first fetch and sends the last one it saw afterwards. Response (public `EventsResponse`):

```json
{ "mode": "replay", "stream_id": "thread:…", "epoch": "…", "events": [ … ], "head_seq": 812, "has_more": false, "has_more_before": true }
{ "mode": "snapshot", "stream_id": "thread:…", "epoch": "…", "snapshot": { … }, "as_of_seq": 812, "reason": "epoch_changed" }
```

Snapshot fallback when the given `epoch` differs from the server's, `after_seq > head_seq`, or the replay would exceed 10 000 events or 8 MiB (from `cum_bytes`). The decision is one pure function, `decide_replay`, as T3 Code's `decideThreadResume` (`apps/server/src/orchestration-v2/ThreadStream.ts:99-118`, bounds at `:18-20`). The client also checks every response's `epoch` against the one it holds. Its first successful forward response (a replay page or a snapshot) establishes its epoch; afterwards the client sends that epoch, so a forward response with another epoch is a snapshot (`epoch_changed`), and the client switches epoch and local state together: it drops every local copy, the snapshot becomes that stream's copy, and every other followed stream is refetched. A failed read (408, 503), a backward page, and a response from an older request generation never set the epoch. A client keeps one current request per stream and direction (forward, backward): the latest it issued. Before it processes a response, the client checks that the response's request is still current; if so, processing the response ends the request. A request stops being current earlier when it times out or is cancelled; when the client establishes or switches the epoch, or opens a WebSocket (the first one included), for every request issued before, on every stream; and when the client replaces a stream's copy with a snapshot or stops following the stream, for that stream's requests issued before. A response to a request that is not current is from an older request generation: the client discards it, and it changes no local state, the epoch included. Opening a WebSocket keeps the local copies as they are; it costs a forward refetch of every followed stream and the discard of every response not yet processed, backward pages included, so a client that still wants older events of a displayed stream fetches them again from its current copy. Snapshot and `as_of_seq` come from one read transaction. A **thread snapshot** is the thread's projection (axes, attention, launch, session, gate evidence, inputs not yet terminal, open approval cards, worktree, current thread surfaces, and, while any attention cause is active or an approval card is open, the latest `vt_snapshot_taken`) plus the last 50 events; a **host snapshot** is the thread list, worktrees, and current host- and workspace-scoped surfaces. A snapshot's `as_of_seq` is the head of the requested stream, and the client renders that stream from the snapshot and the events after `as_of_seq`. A field the snapshot carries that another stream owns is that stream's value at the same database read, and it does not advance with the requested stream; the same holds for data a stream's own events do not carry, such as a thread's initial `task_state` from `thread_registered` on the host stream. The client uses such a value as the initial one and takes later changes from the owning stream once it follows that stream and holds a valid copy of it; until then it shows the snapshot's value. Owners: a thread's axes and attention, the thread stream; thread list membership and `closed`, the host stream, or `GET /api/threads` for an agent token allowed that route; the current launch's worktree, the thread stream for the association and the host stream or `GET /api/worktrees` for the worktree record. A snapshot shows a worktree record only to a token that `GET /api/worktrees` shows it to: for an agent token, a thread snapshot's `worktree` is `null` unless the worktree's current owner is in self+ (§2.5); the thread's `cwd` and the launch's `worktree_id` (in the thread stream's `launch_reserved`) stay readable. A stream that does not exist or that the token may not read is 404; an empty stream returns `replay` with `events: []`, `head_seq: 0`.

**Backward history.** `GET /api/events?stream_id=<id>&before_seq=<N>&limit=<L>[&epoch=<E>]` returns the nearest `L` events preceding `N` (`seq < N`), in ascending order, with `has_more_before`. An epoch mismatch on a backward page does not switch the client: it triggers a forward resync, and the client switches epoch and local state together on that forward response. The resync stays due until the client issues a forward request after it or stops following the stream. A forward response to a request issued before it is processed only if that request is still current, and even then it does not satisfy the resync. `after_seq` with `before_seq` is 400.

**Live notifications.** `POST /api/ws-ticket` (Bearer) returns a ticket; `GET /api/ws?ticket=<t>` upgrades. Server → client: `{ "type": "hello", "epoch", "server_time" }`, `{ "type": "stream_advanced", "stream_id", "head_seq" }`, `{ "type": "heads", "heads": [{ "stream_id", "head_seq" }] }`; client → server: `{ "type": "subscribe", "stream_ids": [...] }`. Notify-then-pull: the client fetches with `GET /api/events`. Each `subscribe` replaces the socket's subscription set, and the server answers with `heads` for the latest set; subscribes in quick succession may be answered by one `heads` frame for the latest set. A heads refresh becomes due every 30 s. Every `heads` frame carries the heads known to the socket for the subscription set at the frame's selection (from the last subscribe whose read had merged by then), and the client treats it as such a snapshot: a frame already selected can arrive after a later subscribe takes effect, and the heads known to the socket can lag the database. For a stream that stays subscribed, while the socket remains in its open loop, within 30 s plus the socket's read and send bounds (60 s with PR 7's defaults) of a commit whose notification was lost, the server completes the send of a corrective `heads` frame from a refresh that read the commit to the transport, or drops the socket; if the socket begins closing meanwhile, `close_grace` applies from the start of closing instead. The client recovers when it processes that frame and pulls, or when it reconnects, since it refetches on every reconnect. Inline event push is deferred; it can be added as an optional field.

**Commands** (public). Every command request is `POST /api/commands/<name>` with `{ "command_id": <client-generated>, "args": { … } }` (`core::http::CommandRequest`; `args` is an object with no duplicate member at any depth). `<name>` is one of `spawn`, `resume`, `send`, `ready`, `key`, `stop`, `close`, `input_resolve`, `input_cancel`, `task_set`, `mailbox_send`, and, for deferred features (§4 "Deferred"), `worktree_remove`, `doctor_run`, `surface_action` (the CLI spells the multi-word ones `input resolve`, `task set`, and so on). Receipts follow T3 Code's `orchestration_v2_command_receipts` keyed by `command_id` (`Migrations/055_OrchestrationV2.ts:42-50`), with:

- **Insert.** The receipt is inserted `in_progress` in the transaction that records the command's intent; the primary key makes a concurrent duplicate fail its insert, so only one request can act.
- **Completion.** `send` appends `input_created` and its completed receipt (with `input_id`) in one transaction; delivery is then the input's state. Synchronous side-effect commands (`key`, `spawn`, `resume`, `stop`, `close`, and the deferred `worktree remove`) stay `in_progress` until the effect finished or failed. Each of these commands' PRs states the bounds of its effect; a result saying the effect did not happen means it cannot happen later. For `spawn`, `resume`, `stop`, and `close` the bound is stated per stage rather than for the whole effect (`docs/design/supervisor.md` §2.3 "The reply deadline"): the effect runs in a `LaunchOp` that outlives the command runner and awaits each admitted write's ticket to the writer's answer; the HTTP reply follows the runner's progress at `reply_by` (409 `in_progress`, 503 `outcome_unknown`), and the receipt stays `in_progress` until the effect's result completes it.
- **`ReceiptLookup`** (core) and HTTP: `New` → the command runs; `InProgress` → 409 `{ code: "in_progress", retry_after }`; `Replay(result)` (same token and request hash) → the stored status and body; `Conflict` (other hash or other token) → 409 `{ code: "conflict" }`, revealing nothing; `UnknownAfterCrash` → 409 `{ code: "unknown_after_crash" }`. An intent whose outcome is not known at reply time (the writer has not replied by the deadline plus 100 ms, the commit outcome is unknown, or the receipt's completion failed after the effect) → 503 `{ code: "outcome_unknown", retry_after }`; the client retries with the same `command_id`. A 408 describes the current attempt only: its deadline prevented its intent from running. This list is the one status mapping for commands; §2.5 refers to it.
- **Launch commands** (`docs/design/supervisor.md` §2.2). Args: `spawn { agent, cwd, prompt?, task? }` (`cwd` an absolute path to a directory, else 400 `bad_args`), `resume { thread_id, expected_launch_id, prompt? }`, `stop { thread_id, expected_launch_id?, assume_dead? }`, `close { thread_id, expected_launch_id, stop? }`; results: `SpawnResult`, `ResumeResult`, `StopResult { launch_id, outcome: stopped | already_exited | asserted, death_confirmed, confirmed_within_deadline, exit_code, signal }` with every field present on every branch (`exit_code` and `signal` `null` when unknown), and `CloseResult { thread_id, stop }`, whose `stop` is the `StopResult` of the stop a `close --stop` ran, else `null`. `resume`, `stop`, and `close` check the target thread against the token's grant before they read anything else of it (a refusal is 404, as for a missing thread). Codes: `thread_closed`, `launch_changed`, `launch_live`, `death_unconfirmed`, `worktree_unavailable`, `no_session` (409); `prompt_rejected`, `prompt_too_large` (400); `launch_busy` (504: a stop that could not take its launch's lock and re-read it within 10 s, with nothing changed). `stop` with `assume_dead: true` is the owner's assertion that an exited launch's processes ended (`docs/design/supervisor-recovery.md` §2.5): it requires `expected_launch_id` (else 400 `bad_args`) and an owner token (else 403 `forbidden`), answers `launch_live` for a running launch, and records `launch_death_confirmed { method: "owner_asserted" }` at most once per launch, answering `asserted`; `assume_dead` is omitted from the arguments when false, so a plain stop keeps its canonical form, and a plain stop of an asserted launch answers `already_exited` with `confirmed_within_deadline: false`. `confirmed_within_deadline` reports P-3's 5 s, counted from `RequestStart` (the connection's first head byte) of the HTTP attempt the daemon accepted; it bounds no work. `chaldea stop` exits 0 when it is true; when death is confirmed but not within 5 s (a late `already_exited` included, whose line says the owner's assertion may have confirmed it) it prints one warning line and exits 4; when death is not confirmed it prints the `death_unconfirmed` message and exits 1. On `death_unconfirmed`, `chaldea resume` and `close` print a message chosen by the launch's `exit_reason` (after a daemon restart, or when it stopped), else a general one, and exit 1; every such message ends by naming `chaldea stop <thread> --assume-dead` to review what was checked and `--launch <id>` to confirm. `chaldea stop <thread> --assume-dead` without `--launch` sends nothing: it prints the current launch's exit, death state, recorded identity, and evidence, read backward through the thread stream within one serving daemon run, and exits 0, or 1 when the read was interrupted; with `--launch <id>` it sends the assertion and exits 0 on `asserted`. `chaldea wait <thread> [--until exited|idle|attention] [--timeout <dur>]` (default `exited`, 10 min) polls `GET /api/threads/{thread_id}` and exits 0 with the summary when the condition holds, 1 when the launch exited without it or the read is refused, and 4 at the timeout.
- **Send-side commands** (`docs/design/supervisor-send.md` §2.2). Args: `send { thread_id, text, origin? }`, `ready { thread_id, expected_launch_id? }`, `key { thread_id, launch_id, keys, approval_id? }` (`keys`: 1 to 32 of `enter`, `escape`, `tab`, `backspace`, `ctrl_c`, `up`, `down`, `left`, `right`, or `{ "char": c }` with one printable ASCII character; with `approval_id`, navigation keys and at most one deciding key, last), `input_resolve { input_id, delivered }`, `input_cancel { input_id }`; results: `SendResult { input_id, state, reject_reason }` (a text `check` refuses is created and `rejected`, not refused), `ReadyResult { launch_id }`, `KeyResult { outcome: written | incomplete | pending, bytes_written }`, `InputCommandResult { input_id, state }`. Claude's `spawn --prompt` and `resume --prompt` are a queued input created with the launch. Codes: `no_live_launch`, `not_bound`, `card_closed`, `key_not_written`, `input_state`, `unit_running` (409); `launch_busy` (504) for a `ready` whose basis could not be sampled because the launch's session was busy, with nothing written. `input_cancel` acts only on a `queued` input, `input_resolve` only on an `unconfirmed` one; an agent cancels only an input it created (403 for another creator's input on a thread it can read).
- **Restart.** Every `in_progress` receipt becomes `unknown_after_crash` and is never re-executed. Inputs are recovered from the `inputs` table, independent of receipts: `queued` → `cancelled` (zero bytes), `sending`/`sent` → `unconfirmed` (unknown). Launches and worktrees follow §2.9 and §2.6.

**Offline.** When the daemon is unreachable, the PWA keeps the last state, locks input, and shows the time of the last successful sync (arch §4.1).

`stream_id`, `epoch`, and `command_id` are public now so the Phase 2 relay can cache per stream and forward commands unchanged. Quint Q-B checks the protocol (`docs/design/formal-specs.md` §7); a `stateright` model of the Rust sync code is deferred to the Phase 2 relay.

### 2.5 HTTP Surface and Authorization

The daemon listens on `127.0.0.1:<port>` only, on `axum` + `hyper` + `tower-http` (arch §3), so request parsing is hyper's (prior-art row 5a's reason). Token comparison uses `subtle` (prior-art row 5d); tokens are stored as SHA-256 hashes (`sha2`, row 5c).

**Common checks.** `Host`: one header, `127.0.0.1:<port>` or `localhost:<port>`, else 421 (DNS rebinding; spike B-8). `Origin`, where checked: absent, or exactly `http://` + the received `Host`, else 403. Bearer: one `Authorization: Bearer` header, else 401. **Connections.** The daemon speaks HTTP/1.1; HTTP/1.0 requests get the same rules once parsed (one request per connection, no upgrade), and hyper answers one carrying `Transfer-Encoding` with its own 400 before the `Host` check. It serves one request per connection: every final response except a successful `101` carries `Connection: close`, and a `101` carries exactly `Connection: Upgrade` (WebKit and `tungstenite` reject any other value), except a `101` racing daemon shutdown, which can carry `close` too (a known limit of `docs/design/http-surface.md` §6.2); clients do not reuse connections. **Deadlines:** each request's deadline is measured from its connection's first head byte; `/hook` and short non-streaming routes have a 5 s whole-request deadline; WebSockets (the attach WebSocket included) and the long synchronous commands (`spawn`, `resume`, `stop`, `close`, and the deferred `worktree remove` and `doctor run`) each have their own bounded deadline (values in their PRs). A read ends at its deadline (408). A submitted write's reply is awaited up to 100 ms past the deadline, which never extends the write's admission. The deadline and the intent commit are decided in one step: a command answers 408 only if its deadline prevented the commit; once the intent committed, the reply follows §2.4's command mapping, and a retry with the same `command_id` is the recovery path.

Tickets are single use, valid 30 s, and die with their token.

**Bodies** (public, `core::http`): `CommandRequest`, `ErrorBody { code, retry_after? }` for every rejection the daemon decides (hyper's own 400 and 431 and the empty body of any `HEAD` response, whatever its status, a `HEAD` with a bad `Host` included, are not `ErrorBody`), `WsTicketRequest` / `WsTicketResponse`, `PairCodeResponse`, `PairRequest` / `PairResponse`, `ThreadsResponse`, `WorktreesResponse`. Every response the daemon generates, success and error (rejections and empty `HEAD` responses included), carries `Cache-Control: no-store`, replacing a handler's own value; only the PWA's routes (`/`, `/assets/*`) keep their own caching (W1), and hyper's own parser responses carry no daemon header. Blob responses use the stored type only if it is `text/plain; charset=utf-8` or `application/json`, else `application/octet-stream`, with `X-Content-Type-Options: nosniff`, `Content-Disposition: attachment`, `Cache-Control: no-store`.

**Actions** ("self+" = the thread itself and its descendants):

The rows `worktree remove`, `POST /events`, `surface_action`, and doctor, `--role rescue`, and the `rescue` and `extension` columns belong to deferred features (§4 "Deferred"); the matrix keeps them so that adding a feature changes no authorization rule.

**Order.** The route and the token kind are checked before any body byte is consumed; object authorization runs on the validated body before any effect, and for an update or delete it also checks the stored object's scope (e.g. a surface replaced by `POST /events` must already be in the caller's scope). An object the token cannot read answers 404, identical to a missing one; an object it can read but not act on answers 403. Agents get 404 on the `host` stream and read threads and worktrees through `/api/threads` and `/api/worktrees`. A receipt is visible only to the token that created it. Hook binding also requires the emitter ancestry rule (§2.9; prior-art row 6c).

**Secrets.** Logs redact `Authorization`, the `ticket` parameter, and pair codes, and never contain `/hook` or `/api/pair` bodies. `chaldea open` obtains a code from `POST /api/pair-codes` and opens `http://127.0.0.1:<port>/#pair=<code>` (single use, 60 s, refused once its issuing token is revoked); the fragment never reaches the server, the page exchanges it via `POST /api/pair`, stores the `owner` token in IndexedDB, and removes the fragment with `history.replaceState`. Rejected: an `HttpOnly` cookie (needs CSRF defences on every route; invariant 5 names Bearer). T3 Code uses the same shape: scoped sessions, single-use pairing links (`Migrations/031_AuthAuthorizationScopes.ts:4`, `:12-48`), `timingSafeEqual` (`apps/server/src/auth/utils.ts:83-89`). herdr's socket API has no token (`src/ipc.rs:10-11`); rejected because Chaldea's API is HTTP. CF Access and host Service Tokens (arch §2) are Phase 2; the token enum leaves room.

**Rejections (spike B-8 on hyper).** Two layers, neither with side effects (no event, fixture, or readiness change):

- **Parser layer (hyper)**, before any middleware runs: malformed framing such as `Content-Length: +5` → 400 (RFC 9112 §6.3); an oversized head → hyper's status; a slow head → connection closed within its budget, observed by the client as EOF, never inferred from a client timeout or `status: 0`. Duplicate equal `Content-Length` and `Transfer-Encoding` follow hyper's framing rules and the guard's (`docs/design/hook-ingest.md` K1, §2.11); `crates/daemon/tests/hook_b8.rs` asserts each case (hook-ingest §7.1), and CI prints the per-OS outcomes of the in-flight-body cases as `B8-OBSERVED` lines.
- **Middleware layer**, for parsed requests only, in order Host → Origin → Bearer → scope → framing → size, before any body byte is used: a missing `Content-Length` on POST → 411, any remaining `Transfer-Encoding` → 400, a body over 4 MiB → 413, the request deadline → 408.

### 2.6 Worktree Ownership

`chaldea spawn --worktree [--base <ref>]` creates a git worktree with the git CLI (as herdr and T3 Code do), through `process-wrap` with `CREATE_NO_WINDOW` on Windows (prior-art rows 1c, 9). Metadata (public, in `worktree_changed` and `GET /api/worktrees`): `worktree_id` (8 hex, also the directory name), `repo`, `workspace_id`, `path`, `branch` (`chaldea/<id>` unless given), `base_ref`, `base_commit` (resolved SHA), `owner_thread_id`, `created_by` (`human` or `thread:<id>`), `state` (`creating`, `active`, `released`, `removing`, `uncertain`, `removed`, `failed`).

- **Short base path.** `worktree_base` is configurable per workspace, default `<state_dir>/wt`, so a Windows user can pick a short root such as `C:\wt` for MSVC's 260-character limit (arch §5).
- **Ownership.** On `thread_closed`, ownership passes to the parent thread, or to the human owner when there is none.
- **Crash safety.** The `creating` intent commits before git runs; restart reconciles against git and never deletes anything.
- **Reservation guard.** A launch reservation that uses the worktree takes the worktree row in its transaction and requires the worktree to be `active` or `released` (§2.9).
- **Never auto-delete.** No exit, close, restart, or timer removes a worktree. In the MVP nothing in Chaldea removes one: the owner runs `git worktree remove` by hand, and `GET /api/worktrees` keeps listing the record, whose path is then missing.
- **Deferred removal** (§4 "Deferred"). One transaction takes the same worktree row as a reservation, checks the worktree is not in use (a reserved or live launch, or one whose death is unconfirmed, blocks it), and records the `removing` intent; git runs only after that commit. `chaldea worktree remove <id>` is **refused**, with nothing changed, when a check before any mutation fails: tracked or untracked changes; ignored files without `--discard-ignored` (owner only, §8 D7); a commit reachable from the worktree's `HEAD` (detached included) or its registered branch that is not on a remote-tracking ref (`git rev-list --max-count=1 HEAD <branch> --not --remotes`, the check T3 Code runs before forced removal, `apps/server/src/storageCleanup.ts:1004-1022`); a launch that uses it and is reserved, live, or not yet confirmed dead; or a git error during these checks. If git fails after it started changing files, the result is `uncertain`, not a refusal; the record stays `uncertain` and is reconciled from the intent before any retry. `--force` (owner only) skips the content checks but never the in-use check, and is recorded. herdr relies on git's dirty refusal (`src/worktree.rs:194-215`), which misses unpushed commits.
- **Branches are never deleted** (herdr does the same, `src/worktree.rs:175-192`); an explicit opt-in is a later, reversible addition.

### 2.8 Extension & Rescue Surface

**MVP: external-agent Rescue.** An agent on the PC (e.g. Claude or Codex desktop apps) diagnoses a thread through `GET /api/threads/{thread_id}/screen` (the live screen) and `chaldea inspect <thread> [--json]`, and intervenes with the existing commands (`send`, `key`, `ready`, `input resolve`, `input cancel`, `stop`, `resume`). The existing authorization rules apply unchanged (§2.5): owner-only commands stay owner-only, and terminal writes are owner-only; which token kinds the diagnostic surface accepts, and its output, are C1's design. `skills/chaldea-rescue/SKILL.md` tells it what to read and when to act or hand back to the human. C1 adds the route and `inspect`, T2 the skill.

**Deferred** (§4 "Deferred"); the contracts below stay so that adding them is additive:

- **One-shot hooks** (outbound, arch §4.4): `before_spawn`, `after_close`, and `attention` (run on every attention raise and clear). Each gets on stdin `{ "hook", "host_id", "thread": { "thread_id", "agent", "cwd", "workspace_id", "parent_thread_id", "role" }, "attention": { "cause", "raised" } | null }` and the env `CHALDEA_URL`, `CHALDEA_EXTENSION_TOKEN`, `CHALDEA_THREAD_ID`; each run is bounded by a timeout (10 s proposed); only `before_spawn`'s stdout `{ "decision": "allow" | "deny", "reason" }` is read. Failure policy: §8 D4.
- **A2UI surfaces**: `{ surface_id, scope: { kind: "host" } | { kind: "workspace", workspace_id } | { kind: "thread", thread_id }, components }` with `text`, `markdown`, `vt_snapshot` (its grid encoded and fetched as in `vt_snapshot_taken`), `button`, `text_input`, `list`. A `button` carries `surface_action { action_id, kind: "send_input" | "send_key" | "stop" | "ready" | "open_attach", args }`, run only when a human with an owner token clicks it, through the command API. This is how the built-in Rescue Agent would act on a PTY.

### 2.9 Launch Contract

- **Reservation.** One transaction checks the thread's current `launch_id` against the one the command expected, checks the thread is not closed, the previous launch is `exited` with death confirmed, and the worktree (if any) is `active` or `released` (so `creating`, `removing`, `uncertain`, `removed`, and `failed` all refuse, §2.6), and appends `launch_reserved` and inserts the launch's hook token (`token_insert`); `launch_reserved` carries no token hash, the command's receipt is written earlier by the runner's intent job, and agent tokens are minted by O1, in the same transaction. Only then is `PtyRuntime::spawn` called. `launch_started` records pid, start time, and pgid or job. `close` takes the same thread row, so a close and a resume cannot both succeed.
- **Early hooks.** A hook with a valid token whose launch has no recorded pid waits, bounded and inside the request deadline, for the pid; then the ancestry rule runs; past the bound it is `raw_unknown` (`unbound`).
- **Binding.** Claude binds by its `--session-id`. Codex hook processes run concurrently, so `UserPromptSubmit` can arrive before `SessionStart`: authenticated hooks of an unbound launch are stored with the `buffered` disposition (bounded count, size, and time), ordered by receipt order at the daemon (an ordinal PR 9 assigns at intake and the store keeps with the delivery), since hook processes carry no shared sequence; the first `SessionStart` whose emitter's nearest CLI ancestor is the launched pid binds it; each buffered event's ancestry is evaluated at receipt, while its emitter is alive, and that result is checked again before promotion, and those with that `session_id` that pass are appended in that order in the binding transaction, while the rest become `raw_unknown` (`foreign_session`). An overflow or timeout turns the buffer into `raw_unknown` (`unbound`), and so does a restart for every launch that can no longer bind. Rejected: binding from the first hook of any type, because only the `SessionStart` rule was verified (spike §4.3, B-11).
- **Daemon restart.** Before accepting commands, the daemon records `launch_exited` (`daemon_restart`, or `unknown_after_crash` without a recorded pid) for every open launch, with `death_confirmed: false`, and revokes the tokens of every launch, not only the open ones; In each start that reaches its probe, the daemon signals by verified identity the recorded leader of every unconfirmed `daemon_restart` launch and the recorded child of every unconfirmed `spawn_failed` launch whose `failed_start` names a pid and a start time, and records what it observed as `launch_evidence`; the probe unlocks nothing. Such a launch's death is confirmed only by the owner (`owner_asserted`), after reading the evidence (`docs/design/supervisor-recovery.md`). A **resume is refused**, with `resume_blocked` raised, until then; such a launch also counts as in use for worktree removal.
- **Resume** (`chaldea resume <thread> [--prompt …]`) is an explicit relaunch through the reservation: a new `launch_id` and tokens, the bound `session_id` passed to the adapter's resume flag, and the transcript cursor carried over. For Codex, `--prompt` is passed positionally after `--`, as `codex resume <flags…> <id> -- <prompt>` (a positional prompt parses: parser test `resume_with_session_id_accepts_prompt_positional`, `cli/src/main.rs:4069-4078`, v0.171.0; that `--` keeps a prompt such as `--version` from being read as an option is X1's check, `docs/design/input-encoders.md` §2.4; the hooks a resumed launch emits are X1's fixtures); without it the launch is a manual launch (§8 D5).

### 2.10 Approval Cards

An approval card has an `approval_id`. In the MVP a card is resolved coarsely: the adapter designs (C1, X1) state which evidence resolves an open card; the matching by `approval_id`, supersession, and expiry below stay binding.

**Deferred: `tool_use_id` correlation** (§4 "Deferred"). Claude's `PermissionRequest` input has `tool_name` and `tool_input` "like PreToolUse hooks, but without `tool_use_id`" (Claude hooks reference, `PermissionRequest input`); Codex's request has `turn_id` and no tool id (`hooks/src/events/permission_request.rs:37-51`). The correlation is therefore the `tool_use_id` of the latest `PreToolUse` of the **same turn** (same `turn_ref`, or no turn boundary in between) with equal `tool_name` and `tool_input`, when exactly one matches (that ordering is an inference, **unverified** until the C1 and X1 fixtures); otherwise the card is uncorrelated. With correlation, a card is resolved only on evidence correlated to it: a `PostToolUse` with its `tool_use_id` (`outcome: ran`).

**Card rules.**

- **Open:** `approval_requested`; `turn_state` → `awaiting_approval`.
- **Resolved** (`outcome: ran`) on the evidence the adapter design names for that card (coarse in the MVP).
- **Superseded / expired:** `Stop` or an interrupt (§2.2) closes every open card with `outcome: superseded`; `launch_exited` closes them with `expired`, in the exit job, at a daemon restart too. These take precedence over resolution, and the turn follows §2.2.
- When the last open card resolves while the turn is active, `turn_state` returns to `running`. A key sent from a card carries `launch_id` and `approval_id` and is refused when that card is no longer open (409 `card_closed`), and with zero bytes (`key_not_written`) when a hook was taken in after the card was read, or when any human unit started after the card was observed, until new card evidence arrives.

### 2.11 Thread Close

`chaldea close <thread> [--stop]` (owner, or an agent for self+) closes a thread whose current launch is `exited` with death confirmed (with `--stop`, it stops it first). It takes the thread row as in §2.9, emits `thread_closed`, passes worktree ownership on (§2.6), and revokes the thread's tokens. `closed` is terminal: no `send`, `resume`, or `spawn` into it. Closed threads stay readable.

**Verdicts of evidence-collecting harnesses** (deferred with `chaldea doctor` and `doctor capture`; the dogfooding checklist records its evidence by hand). `chaldea doctor`, `doctor capture`, and scripted real-host runs decide their verdict in one function, `core::verdict::evaluate(plan: &CheckPlan, evidence: &[Check]) -> Verdict`, lifted from the spike's [`src/verdict.rs`](https://github.com/shuymn/chaldea/blob/03b00b8c0462c032f5f4a4f057feafa8e366d1b5/spikes/pty-hooks/src/verdict.rs). Outcomes are typed: `Pass`, `PlatformFail { cause }` (positive evidence of what the CLI or OS did), `HarnessFail { cause }`, `Missing`, `NotExercised { reason }`.

- The plan (required evidence keys and expected context: run, launch, OS build, CLI version) is fixed before observation. An empty plan is `Inconclusive`.
- Each required key must appear exactly once, with its content checked; a second observation of the same key, even with the same outcome, is `HarnessFail`. This replaces the spike's "last check per key wins" (`verdict.rs:116-135`). Evidence outside the plan is recorded and does not affect the verdict, also a change from the spike.
- A context mismatch or null evidence is `HarnessFail`.
- Completeness first: any required key `Missing`, `HarnessFail`, or `NotExercised` → `Inconclusive`; else `Pass` when all passed, else `Fail`. Missing evidence, an observation failure, or a check that did not run is never `Pass` (spike §1).

## 8. Decisions

Decisions that change public behaviour or are irreversible. D1, D3, D7, and D8 were decided by the owner on 2026-11-22; D2, D4, D5, and D6 are reversible or additive and were decided on the facts, recorded with the condition that would reopen them.

**D1. Approvals are answered with keys** (owner). The card shows tool and arguments, and the user answers with keys (§2.10), in the MVP from the terminal view's key bar, whose layout and transport are T2's design; it works the same for both CLIs and needs no emitter change. A key bound to an open card answers the dialog, not the composer, so it is recorded as a `card_key`, carries the card's `launch_id` and `approval_id`, is refused once the card closed, and does not close the input gate (§2.3); these rules bind every card-bound key, from the key bar included. Rejected alternative: a hook decision, where `hook-emit` waits for the user and prints the CLI's decision JSON (Claude `hookSpecificOutput.decision.behavior`, hooks reference; Codex allow/deny, `hooks/src/events/permission_request.rs:55-58`). It would give one-tap answers but needs the emitter's 3 s budget (CL-23) and `/hook`'s 5 s deadline lifted for human time, and its answer is still only one input to the CLI's final decision. Switch later: add an `approval_answered` kind (additive), the `PermissionRequest` exception to CL-23 and the `/hook` deadline, and a long-poll path. Codex hashes the hook timeout with the handler (`hooks/src/engine/discovery.rs:715-718`, `:847`), so X1 registers the `PermissionRequest` entry with its final command string and timeout now, and the switch costs no hook review.

**D2. `chaldea task set <state> [--summary] [--thread]` sets `task_state`.** Explicit and greppable in agent instructions; issue #2's command list is not closed. Rejected: a `--task-state` flag on `mailbox send`, which couples a state change to a message. The commands this design adds beyond issue #2 are `open`, `ready`, `resume`, `close`, `inspect`, `input resolve`, `input cancel`, `task set`, and `daemon run/start/stop`, and, deferred, `worktree remove` and `doctor capture`.

**D3. The eight input states of §2.3 are public** (owner). Crash recovery and human resolution stay exact, and `unconfirmed` means only "may have reached the CLI", which the never-resend rule depends on. Rejected alternatives: the architecture's four states with a reason on `unconfirmed` (every reader must check the reason before treating it as a possible delivery, and the gate must skip zero-byte cases), and a mapped public set with a terminal `closed` (a mapping layer for little gain).

**D4. `before_spawn` fails open by default, with a per-hook `fail_closed = true` key** (applies when the deferred one-shot hooks are added, §2.8). A broken extension never blocks all spawns, and policy hooks can still fail closed; doctor lists fail-closed hooks and their last failure. Reopen if `before_spawn` turns out to be used mainly for security policy.

**D5. A Codex `spawn` requires a first prompt.** Every spawned launch is controllable from turn 1 (arch §5). A Codex `resume` without `--prompt` stays a manual launch (§2.9). Known costs: the prompt is in argv and shows in process listings, and Windows limits a command line to 32,767 UTF-16 units (`CreateProcessW` docs; the usable length after quoting is unmeasured). A manual `spawn` with the resume path's behaviour can be added later; it is additive.

**D6. Codex-on-Windows text with trimmable leading/trailing whitespace or TAB is rejected** with zero bytes written (spike F-1d), for `send` and recognised attach pastes. Codex trims such whitespace and takes TAB as its queue key (arch §5), so sending it would change the prompt silently. An explicit transform (`--transform trim,tab-to-spaces`) can be added later if rejections prove frequent; it is additive.

**D7. A normal worktree remove refuses when ignored files exist** (owner; applies when the deferred `worktree remove` is added, §2.6), unless the owner passes `--discard-ignored` or `--force`; agents can pass neither. `git worktree remove` would delete ignored files such as `.env`, and deleted files are unrecoverable (arch §1, invariant 3). Cost: nearly every built worktree (`target/`, `node_modules/`) needs the flag.

**D8. Readiness after a turn defaults to `stop_settle`** (owner), with `post_decision` and `owner_only` selectable per adapter (§2.3, §2.7). Orchestration runs unattended across turns. Known race: a user `Stop` hook that blocks after the settle interval makes the next prompt land in a running turn; the input is then attributed or left `unconfirmed`, never resent. Switching the default is a capability-table change.

**Also decided.**

- Raw PTY writes (`key`), the attach WebSocket, and the recovery commands `ready` and `input resolve` (which write no bytes) are owner-only; agents keep `send`, `stop`, and the other rows of the action matrix (§2.5). An external rescue agent acts through the existing commands under the same rules (§2.8); the built-in Rescue would act on a PTY only through scoped A2UI `surface_action`s that a human clicks (deferred). Reason: a raw key can approve a dialog or submit into another thread's composer; granting more later is additive.
- A resume is refused until the old launch's death is confirmed (§2.9). Reason: two live CLIs on one session corrupt it; refusing is safe and can be relaxed.
- B-8 expectations follow RFC 9112: `Content-Length: +5` → 400; a slow head → connection closed within its budget, observed as EOF, never inferred from a client timeout or `status: 0` (§2.5). Reason: the spike's 411 contradicts RFC 9112 §6.3, and an incomplete request has no response to observe.
